# 서버 후속 — 2026-11-09 (스냅숏 요청 수 제한·멤버 ETag·요청 기록 색인)

[개선-서버-2026-11-08](개선-서버-2026-11-08.md)의 후속이다. 기준은 같다: Cloudflare **무료 요금제**(요청당 CPU 10ms, D1 하루 읽기 500만 행·쓰기 10만 행).

표기: [확인] = 테스트·타입 검사·린트로 확인함, [미확인] = 실제 Cloudflare에서 해 보지 않음.

## 1. 왜

가장 비싼 GET(모임 전체를 읽는 스냅숏)에 요청 수 제한이 없었다.
- 운영자 스냅숏 `GET /api/groups/:gid/snapshot`은 "화면이 자주 부르는 가벼운 경로"라며 일부러 세지 않았다.
- 멤버 스냅숏 `GET /api/member/:gid/snapshot`은 ETag도 제한도 없었다.

ETag가 있어도 `If-None-Match`를 빼고 부르면 매번 본문을 만든다. 한 계정이 큰 모임(522경기면 한 번에 대략 6천~7천 행
[미확인: 추정])을 반복 호출하면 D1 하루 읽기 500만 행을 몇십 분 만에 다 써 **사이트 전체**가 멈춘다.

## 2. 요청 수 제한(200만 셈)

조회 링크(`/api/view/:token`, 2026-11-08 4절)와 같은 방식이다: ETag 비교 → 304면 세지 않고 끝 → 아니면 세기 → 본문.
- 버킷: `snapshot-account`(기본 **60**/분, 쓰기 한도 `write-account`와 같음), `snapshot-ip`(기본 **120**/분, 다른 버킷처럼 계정의 두 배).
  운영·staging도 같은 값(`wrangler.jsonc`의 `RATE_SNAPSHOT_PER_ACCOUNT`·`RATE_SNAPSHOT_PER_IP`), 로컬은 5000.
- 세는 곳은 공통 앞단이 아니라 경로 안(`src/server/index.ts` `countSnapshot`). 권한 확인(운영자·멤버) 뒤에 센다.
- 세기를 ETag 헤더보다 먼저 한다(429에 `ETag`·`private`가 붙지 않게, 429는 `no-store`). 한도에 걸려도 같은 ETag의 304는 된다.
- `/api/me`는 그대로 세지 않는다(가볍다).

**한계(정할 것)**
- 분당 한도는 속도만 묶는다. 계정 60이면 큰 모임 기준 분당 약 40만 행이라, 한 계정이 하루 종일 한도 끝까지 부르면
  여전히 하루 500만 행을 넘길 수 있다(약 13분). 완전히 막으려면 계정별 "하루 읽기 행 예산"(대량 쓰기 예산 같은 것)이나
  본문 캐시(snapshot.ts `snapshotBody`의 확장 자리)가 필요하다.
- 화면은 자기 저장 뒤마다 스냅숏을 다시 읽는다(예: 티어 화면에서 사람마다 누름). 저장은 바뀐 자료라 200이므로,
  스냅숏 한도를 쓰기 한도(60)보다 작게 두면 저장은 되고 그 뒤 다시 읽기만 429가 난다. 그래서 처음 잡은 30을 60으로 올렸다.

## 3. 멤버 스냅숏 ETag/304

- 응답 헤더: `ETag`(약한), `Cache-Control: private, no-cache`, `Vary: Cookie`(계정마다 본문이 다르다).
  화면(`src/web/api.ts`)은 GET을 `cache: "no-cache"`로 부르므로 바꿀 것이 없다.
- ETag 재료(`src/server/members.ts` `memberSnapshotEtag`): 조회 응답의 재료(`snapshotEtag` "viewer": 응답 모양, 배포 버전,
  모임 ID, `data_version`, 진행 상태 버전, 세대, 설정 버전, 점검 여부, 이름·시간대·조회 토큰) + `"member"` + **계정 ID** + **참가자 ID**.
- 멤버 응답에만 있는 값(`me`)의 출처와 바뀜 감지:

  | 값 | 표 | data_version 트리거(0021) |
  |---|---|---|
  | `me.avoidPositions` | `participants.avoid_positions` | 있음 |
  | `me.avoidBySelf` | `participant_links.avoid_self_at` | 있음 |
  | `me.requests`(그 사람의 요청·처리 상태·답) | `participant_requests` | 있음 |

  세 표 모두 트리거가 있어 따로 읽지 않는다(304 판단은 모임 행 1행 읽기). 시각에 따라 바뀌는 값은 없다.
- 연결이 끊기면 권한 확인(`requireMember`)에서 404라 예전 ETag로도 304를 받지 못한다.

## 4. `requests (group_id, created_at)` 색인 — migrations/0024

쓰기 공통 경로(`runMutation`)가 저장마다 `DELETE FROM requests WHERE group_id = ? AND created_at < ?`를 돈다.
예전 색인(기본 키 `(group_id, request_id)`, `created_at` 단독)으로는 그 모임의 기록 전부나 모든 모임의 오래된 기록을 훑었다.
새 색인으로 `SEARCH requests USING INDEX idx_requests_group_created (group_id=? AND created_at<?)`(로컬 EXPLAIN QUERY PLAN) [확인].
표를 다시 쓰지 않는다. 이 색인 없이도 코드는 동작한다.
