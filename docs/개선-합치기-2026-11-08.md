# 합치기 되돌리기와 본인 연결 (2026-11-08)

## 문제

참가자 합치기(`src/server/merge.ts`)는 합칠 대상(source)의 본인 연결(`participant_links`)을 남길 대상(target)에게
옮기고(남길 대상에 연결이 없을 때), 이미 있으면 합칠 대상의 연결을 지웠다. 무엇을 했는지 합치기 기록에 남기지 않아
**되돌려도 연결이 돌아가지 않았고**, 테스트(`test/members.test.ts`)가 이 동작을 의도로 고정하고 있었다.

실패 시나리오: 운영자가 본인 연결된 '김철수'를 다른 사람 '김철'에 잘못 합침 → 되돌림 → 기록은 돌아오지만 철수의 계정이
김철의 "본인"으로 남는다. 철수가 김철의 기피 라인을 바꾸고(편성에 반영) 김철 이름으로 정정·삭제 요청을 보낼 수 있고,
운영자 화면에서는 보이지 않는다. 되돌리기를 쓰는 상황이 곧 "같은 사람이 아니었다"이므로 바로 그 경우에 틀린다.

## 결정

원칙: **잘못된 "본인"이 남지 않게 하는 것이 먼저**, 애매하면 연결하지 않고 결과로 알린다.

- 연결은 참가자 하나에 계정 하나(`participant_links` 기본 키 `(group_id, participant_id)`), 계정은 모임마다 하나.
  `participant_claims`는 연결 링크(1회용 토큰)라 합칠 때처럼 지우기만 한다(되돌리지 않음).
- 합칠 때 `participant_merges.moved_link`(migrations/0023, JSON)에 합칠 대상의 연결과 처리를 남긴다.
  - `NULL` 기록 없음(이전 합치기·복원한 합치기), `{}` 연결 없었음,
    `{accountId, linkedAt, avoidSelfAt, action: "moved"|"removed", requestIds}`.
  - 읽은 뒤 연결이 바뀌면 기록과 실제가 어긋나므로 batch 안의 보호 문장으로 막는다(409).
  - 옮기는 요청은 읽은 ID 목록만 옮긴다(되돌릴 때 같은 목록을 쓴다).
- 되돌릴 때(`undoLinkPlan`):

  | 합칠 때 | 지금 상태 | 처리 | 응답 `link.outcome` |
  |---|---|---|---|
  | moved | 그 계정이 아직 남길 대상의 본인 | 원래 사람에게 돌려놓음(`avoid_self_at`도 합치기 전 값) | `returned` |
  | moved | 위와 같으나 원래 사람에게 다른 연결이 있음(정상 경로로는 생기지 않음) | 남길 대상에서 끊음 | `cut` |
  | moved | 끊겼거나 다른 계정이 연결됨 | 손대지 않음(누군가 일부러 바꾼 것) | `not_returned` |
  | removed | 원래 사람·계정 모두 연결 없음, 계정 있음, 연결 한도 안, 익명 처리 안 됨 | 다시 만듦(원래 연결 시각) | `returned` |
  | removed | 그 밖 | 만들지 않음 | `not_returned` |
  | 기록 없음 | 남길 대상에 합치기 전부터 있던 연결 | 손대지 않음 | `unknown`(운영자가 확인) |
  | `{}` | - | 없음 | `link: null` |

- 요청(정정·삭제 요청):
  - 합칠 때 옮긴 요청은 원래 사람이 쓴 것이고 정정 요청은 원래 사람의 경기를 가리키므로 **연결 결과와 관계없이**
    원래 사람에게 돌려놓는다.
  - 합쳐져 있는 동안 남길 대상 이름으로 들어온 요청은 연결이 합칠 때 그대로(같은 계정·같은 연결 시각)일 때만
    그 계정이 쓴 것이 확실하므로 함께 돌려놓는다. 아니면 누가 썼는지 알 수 없어 남길 대상에 둔다.
- 본인 확인 참가 신청: 연결을 돌려놓으면 그 계정이 남길 대상 이름으로 낸 신청의 본인 확인 표시를 지운다. 합칠 때
  지운 표시(removed)는 되살리지 않는다(익명 신청으로 남는 것은 권한이 줄어드는 쪽).
- 기피 라인: 합쳐져 있는 동안 그 계정이 남길 대상의 기피 라인을 직접 바꿨으면(`avoid_self_at`이 합칠 때 값과 다르고
  NULL이 아님) `avoidChanged: true`로 알린다. 합치기 전 값을 기록하지 않았고 그 사이 운영자가 고쳤을 수도 있어
  자동으로 되돌리지 않는다.
- 변경 이력: 연결은 경기 변경 이력(`match_revisions`)의 대상이 아니라 남기지 않는다. 결과는 되돌리기 응답의 `link`와
  요청 기록(같은 요청 ID 재전송 시 같은 응답)에 남는다.
- 백업: `moved_link`는 계정 ID라 백업에 넣지 않는다(README 5절 "참가자 연결은 백업에 들어가지 않습니다").
  내보내기는 열을 골라 읽고 복원은 이 열을 넣지 않으므로 복원한 합치기는 기록 없음(`unknown` 경로)이 된다.

## 바꾼 것

- `migrations/0023_merge_claims.sql`: `participant_merges.moved_link` 추가.
- `src/server/merge.ts`: `loadMovedLink`·`linkMergeStatements`(합치기), `undoLinkPlan`(되돌리기), 되돌리기 응답에
  `link: { outcome, avoidChanged } | null`.
- `src/server/members.ts`: `ANON_NAME_PATTERN` 내보내기(익명 처리된 사람에게 연결을 다시 만들지 않으려고).
- `src/server/groups.ts`: 백업 내보내기에 `moved_link`를 넣지 않는 이유 주석.
- `src/web/screens/Merge.tsx`: 미리보기에 본인 연결 안내 한 줄(합칠 대상에 연결이 있을 때) + 접힌 도움말,
  되돌리기 확인 창 한 줄, 되돌린 뒤 알림에 연결 결과·기피 라인 확인 안내.
- README 5절 연결·백업 줄에 합치기 되돌리기 한 문장.

## 테스트 (`test/members.test.ts`)

- 기존 "합치기 … 되돌려도 연결은 남은 사람에게 남는다"를 "되돌리면 연결·요청이 원래 사람에게 돌아온다"로 바꿈.
- "합치기 되돌리기와 본인 연결" 묶음:
  - 김철수 → 김철 합침, 합쳐진 동안 기피 라인·요청 → 되돌림: `/api/me` memberships와 멤버 읽기가 철수를 가리킴,
    합치기 전·후 요청 모두 철수에게, 철수의 기피 라인 표시는 합치기 전 그대로, `avoidChanged: true`,
    이후 그 계정의 기피 라인 변경은 철수에게만 적용.
  - 같은 요청 ID 재전송은 같은 응답(link 포함).
  - 그 사이 남는 사람에게 다른 계정이 연결됨 → 그 연결 유지, 원래 계정 연결 없음(`not_returned`), 옮긴 요청은 원래 사람에게.
  - 남는 사람에게 이미 연결이 있어 지운 연결 → 되돌리면 다시 만듦.
  - 합칠 대상에 연결 없음 → `link: null`.
  - 원래 사람에게 돌려놓을 수 없음 → 끊음(`cut`).
  - 기록 없는 예전 합치기 → 연결 그대로, `unknown`.

## 남은 판단

- 기록 없는 예전 합치기(이 변경 전·복원한 것)는 어떤 계정을 옮겼는지 알 수 없어 자동으로 고치지 못한다. 운영 DB에
  이미 "되돌렸는데 연결이 남아 있는" 경우가 있을 수 있으니 배포 뒤 한 번 확인할 만하다
  (`participant_merges`의 `undone_at IS NOT NULL` 행의 target에 연결이 있고 그 연결 시각이 합친 시각보다 이른 것).
- 되돌린 결과(`link`)는 알림으로만 보여 주고 합친 기록 목록에는 남기지 않는다(스냅숏 `merges`는 이번에 손대지 않음).
