## 1. 로그인 CPU 10ms 대응(비밀번호 해시)

**동작**
- 비밀번호를 PBKDF2에 넣기 전에 서버 비밀값으로 HMAC-SHA-256을 한 번 씌운다(페퍼). 키는 `"password-pepper:" + SESSION_SECRET`(세션 서명·요청 수 제한의 IP 해시와 접두어로 구분). 이전에는 페퍼가 없었다(165줄 근처의 `SESSION_SECRET` 사용은 틀린 시도 횟수 키를 만드는 HMAC이었다).
- 저장 형식에 방식 이름을 넣어 구분한다: 새 형식 `pbkdf2p-sha256$횟수$솔트$해시`, 예전 형식 `pbkdf2-sha256$…`. 예전 형식도 검증되고, 맞으면 그 로그인에서 새 형식(지금 설정 횟수)으로 다시 저장된다. 새 형식은 지금 설정보다 횟수가 적을 때만 다시 저장한다(설정을 낮춰도 강한 해시를 약하게 바꾸지 않는다).
- 운영·staging 설정 `PASSWORD_PBKDF2_ITERATIONS: "20000"`(wrangler.jsonc 주석: Paid로 올리면 100000). 로컬·테스트는 기본값 100000 그대로.

**측정(로컬 workerd, 이 PC, 중앙값)** [확인] `test/local-accounts.test.ts`의 "[측정]" 사례(`npx vitest run test/local-accounts.test.ts -t 측정 --silent=false`)
- 20,000회: **약 7ms**
- 100,000회: **약 31ms**

**파일**: `src/server/local.ts`(pepper, pbkdf2, hashPassword, verifyPassword, dummyVerify), `src/server/env.ts`, `wrangler.jsonc`, `docs/배포안내.md` 4-1·6·11절.

**테스트**: 예전 형식으로 로그인 → 새 형식 갱신, 틀린 비밀번호는 갱신하지 않음, 20000 설정에서 가입·예전 형식 갱신·강한 해시 유지, 다른 `SESSION_SECRET`이면 새 형식이 맞지 않음(페퍼가 실제로 쓰임), 저장 형식 정규식.

**한계**
- 20,000회도 10ms에 가깝다. 실제 설비 시간은 [미확인]. staging에서 Workers Logs의 CPU 초과를 보고 필요하면 10,000(최소)으로 낮춘다.
- **`SESSION_SECRET`을 바꾸면 새 형식 비밀번호가 모두 맞지 않는다**(복구 코드로만 다시 정할 수 있다). 지시대로 `SESSION_SECRET`을 페퍼로 썼다. 비밀값을 나눠 쓰려면 별도 비밀값(`PASSWORD_PEPPER`)을 두고 형식 이름을 하나 더 늘리는 방법이 있다(정하지 않음, 9절).

## 2. 공개 읽기 보호(스냅숏 batch, ETag·304, 한도)

**동작**
- `buildSnapshot`의 순차 쿼리(운영자 기준 약 20번 왕복)를 **D1 batch 한 번**으로 묶었다. batch는 한 트랜잭션이라 경기·명단·순환이 같은 시점이다. 활성 순환 주기·보정값처럼 앞 결과에 기대던 읽기는 하위 질의로 바꿨다. 응답 본문은 그대로다(운영자 참가자에 `version` 하나가 늘었다, 3절).
- 참가 신청 공개 응답(`publicView`)도 명단·신청·내 연결을 batch 한 번으로 읽는다.
- **ETag·304**: `GET /api/view/:token`, `GET /api/groups/:gid/snapshot`(운영자), `GET /api/join/:token`.
  - 모임 행 **1행만** 읽어 ETag를 만들고, `If-None-Match`가 같으면 본문 없이 304. 경기·명단은 읽지 않는다.
  - 응답 헤더 `ETag: W/"…"`, `Cache-Control: private, no-cache`(브라우저가 저장하되 매번 서버에 확인). 브라우저 fetch는 304를 저장해 둔 본문의 200으로 바꿔 주므로 **웹 변경 없이 동작한다**. 다른 API는 여전히 `no-store`.
  - ETag 재료: 역할, 모임 ID, **`groups.data_version`**, `live_version`, `generation`, 설정 버전 ID, 점검 여부, 모임 이름·시간대·조회 토큰, 배포 버전(`CF_VERSION_METADATA.id`). 운영자 스냅숏은 1분 단위 시각도 넣는다(참가자 연결 링크의 만료가 시간에 따라 바뀐다). 참가 신청은 링크 해시·열림 여부·계정(로그인한 멤버의 "내 신청" 표시)도 넣고 `Vary: Cookie`.
  - **왜 `data_version`이 필요한가**: `live_version`은 진행 상태(시작·결과·순환)에서만 오르고 참가자 이름·시즌·시리즈·메모·정정·신청에서는 오르지 않는다. 쓰기 경로가 여러 파일에 70곳 넘게 있어 코드에서 하나하나 올리면 빠뜨리기 쉽다. 그래서 **migrations/0021의 트리거 48개**(화면 자료 표 16개 × 넣기·고치기·지우기)가 `groups.data_version`을 올린다. 경기 명단(`match_roster`)·변경 이력(`match_revisions`)은 늘 경기 행이나 합치기 기록과 같은 batch에서 바뀌므로 트리거를 두지 않았다(큰 가져오기의 쓰기 행 수를 줄이려고). 설정 저장은 `settings_version_id`가 바뀌므로 ETag가 직접 본다.
  - 조회 토큰을 다시 만들면 예전 토큰은 모임 행을 찾지 못해 **ETag가 같아도 404**다.
- `RATE_VIEW_PER_IP` 운영값 120 → **30**(staging도 30).

**파일**: `src/server/snapshot.ts`(buildSnapshot batch, `loadEtagHead`, `loadEtagHeadByViewToken`, `snapshotEtag`, `etagMatches`), `src/server/join.ts`(`publicView` batch, `joinInfoConditional`), `src/server/index.ts`(세 경로, Cache-Control 미들웨어), `src/server/supportCounts.ts`(`foldAdjustments`), `migrations/0021_server_hardening.sql`, `wrangler.jsonc`(`version_metadata`, `RATE_VIEW_PER_IP`).

**테스트**(`test/server-hardening.test.ts`): ETag 같으면 304·본문 없음, 여러 값·강한 비교 꼴도 맞춤, 경기 저장 뒤 ETag 바뀜, 참가자 이름·시즌·설정·모임 이름이 바뀌어도 ETag 바뀜, 조회 토큰 재발급 뒤 예전 토큰 404 유지, 운영자 스냅숏 304·비운영자 404, 참가 신청 304 → 신청 뒤 200, 트리거 48개 생성·`data_version` 증가, 다른 API는 `no-store`. 기존 스냅숏 테스트 전부 통과.

**한계**
- 304여도 **요청 수 제한 자체가 D1 쓰기 1행 이상**을 쓴다(`rate_limits` UPSERT). 조회가 많으면 읽기보다 이 쓰기가 무료 한도(하루 10만 행)를 먼저 쓴다. 더 줄이려면 Workers Rate Limiting 바인딩이나 KV로 옮기는 것을 검토한다(이번에 하지 않음).
- 트리거 때문에 화면 자료 표의 쓰기 한 행마다 `groups` 행 쓰기가 1행 더 든다. 가져오기 1,000경기 ≈ +1,000행, 모임 삭제·복원도 행 수만큼 는다.
- 304 응답의 본문(브라우저가 저장한 것)의 `serverTime`은 그 본문을 받은 시각이다(명단 텍스트의 "… 기준" 시각에만 쓰인다).
- 스냅숏에 새 표를 싣게 되면 그 표에도 `data_version` 트리거를 만들어야 한다. 표를 다시 만드는 마이그레이션은 트리거를 다시 만들어야 한다(0021 머리말).
- 로컬처럼 `CF_VERSION_METADATA`가 비는 곳에서 응답 모양을 바꾸면 `snapshot.ts`의 `ETAG_SHAPE`를 올린다.

## 3. 쓰기 경로 통일과 동시 수정 보호

**동작**
- `runMutation`(요청 ID 멱등성·점검 확인·batch)으로 옮긴 경로(`src/server/groups.ts`): 모임 이름 바꾸기(`renameGroup`), 참가자 만들기(`ensureParticipants`), 참가자 수정(`updateParticipant`), 시즌 만들기·지우기(`createSeason`·`deleteSeason`), 조회 토큰 다시 만들기(`regenerateViewToken`).
- 요청 ID는 **선택**이다(`optionalRequestId`): 보내면 같은 요청을 한 번만 처리하고, 안 보내면 서버가 이 요청만의 ID를 만든다(예전 화면 그대로 동작, 재전송 안전은 없음). 웹이 모두 보내게 되면 필수로 바꾼다.
- 모임 만들기(`createGroup`)는 모임이 아직 없어 모임별 요청 기록(runMutation)을 쓸 수 없다. 대신 요청 ID를 보내면 모임 ID를 (계정, 요청 ID)의 해시로 정해(백업으로 새 모임과 같은 방식) 재전송해도 같은 모임을 돌려준다.
- **참가자 수정의 동시 수정**: `participants.version` 열(0021). 참가자 행을 바꾸는 모든 코드가 `version = version + 1`(groups.ts, merge.ts 합치기·되돌리기, members.ts 내 기피 라인·익명 처리).
  - 서버 안의 경쟁: 읽은 버전을 batch 안의 보호 문장(`guard_version_conflict`)으로 다시 확인 → 다르면 409 `VERSION_CONFLICT`(details.version = 지금 버전). 화면 변경 없이 동작.
  - 화면이 `baseVersion`(운영자 스냅숏 `participants[].version`)을 보내면 화면이 본 값과도 비교한다(다른 기기의 수정을 덮어쓰지 않음).
- **모임 수 한도 경쟁**: `guard.group_limit` 열과 `groupLimitGuard`(groups.ts). "개수 확인 → 넣기" 사이에 끼어든 요청을 batch 안에서 막는다. 적용: 모임 만들기, 운영자 넘겨받기(`acceptTransfer`, 그 모임의 공동 운영자 행은 빼고 셈), 백업으로 새 모임(`restore.ts importAsNewGroup` 첫 batch). 공동 운영자 수락은 원래 같은 보호 문장이 있었다.
- 시즌 겹침 보호 문장은 runMutation이 `VERSION_CONFLICT`로 바꾸므로 시즌 경로에서 `SEASON_OVERLAP`으로 되돌린다.
- 백업 파일에는 `version`을 넣지 않는다(`exportBackup`에서 뺌, 형식 그대로).

**파일**: `src/server/groups.ts`, `src/server/merge.ts`, `src/server/members.ts`, `src/server/restore.ts`, `src/server/http.ts`(`readOptionalJsonBody`: 본문 없는 DELETE·POST 허용), `src/server/index.ts`, `src/shared/types.ts`(`ParticipantView.version?`), `migrations/0021_server_hardening.sql`.

**테스트**(`test/server-hardening.test.ts`): 같은 baseVersion 동시 두 건 → [200, 409], 버전 1, baseVersion 없이도 성공 / 동시 4건(버전 없이) → 200 또는 409이고 성공 수만큼 버전 증가(잃어버린 수정 없음) / 요청 ID 재전송: 모임 만들기(같은 모임·하나만 생김, 다른 계정은 다른 모임), 이름 바꾸기(같은 ID 다른 내용 → 409 `REQUEST_ID_REUSED`), 참가자, 시즌(재전송은 같은 결과, 새 ID는 `SEASON_OVERLAP`), 조회 토큰(같은 토큰, 본문 없으면 매번 새 토큰), 시즌 지우기(본문 없이도) / 모임 4개인 계정이 동시에 4건 → 성공 1건·나머지 409 `TOO_MANY_GROUPS`, 총 5개 / 한도에 닿은 계정의 보호 문장이 batch 전체를 되돌림.

**runMutation으로 옮기지 않은 쓰기(이유)**
- 토큰 원문을 돌려주는 경로(요청 기록에 토큰을 남기지 않으려고 원래 제외): 운영자 인수 링크 `createTransfer`, 공동 운영자 초대 `createCoInvite`, 참가 신청 링크 `createJoinLink`, 참가자 연결 링크 `createClaimLink`.
- 모임 권한 밖의 계정 단위 경로(보호 문장으로 경쟁을 막음): `acceptTransfer`, `acceptCoInvite`, `acceptClaim`, `removeCoOperator`, `unlinkSelf`, 멤버의 `setOwnAvoid`·`createMemberRequest`.
- 로그인 없는 공개 경로: `joinAdd`·`joinCancel`(링크·상한 보호 문장).
- 운영자 경로지만 이번 범위 밖: `unlinkByOperator`, `resolveMemberRequest`(members.ts), `deleteGroup`(자체 단계 실행). 다음에 같은 방식(`optionalRequestId`)으로 옮길 수 있다.

## 4. 보안 헤더

**동작**
- API: Hono 미들웨어(가장 바깥, 오류 응답 포함)가 `securityHeaders`(`src/server/http.ts`)를 붙인다.
  - `Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline' https://cdn.jsdelivr.net; font-src 'self' https://cdn.jsdelivr.net data:; img-src 'self' data: blob:; connect-src 'self'; object-src 'none'; frame-ancestors 'none'; base-uri 'self'; form-action 'self'`
  - `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy: camera=(), microphone=(), geolocation=(), payment=(), usb=()`, `X-Frame-Options: DENY`
  - `Strict-Transport-Security: max-age=31536000` — `DEPLOY_ENV=production`에서만.
- 화면: `public/_headers`(같은 값 + HSTS). vite의 `root`가 `src/web`이라 기본 public 폴더는 `src/web/public`이다. 웹 폴더를 건드리지 않으려고 **`vite.config.ts`에 `publicDir: "../../public"` 한 줄을 더했다**. [확인] `vite build`가 `_headers`를 빌드 결과에 복사함.
- 외부 출처 확인: `src/web/index.html`이 Pretendard CSS를 `cdn.jsdelivr.net`에서 부르고(SRI), 그 CSS가 같은 곳의 글꼴 파일을 부른다 → `style-src`·`font-src`에 넣었다. 화면 코드의 `fetch`는 모두 같은 출처(`/api/...`). 공유 이미지·백업 내려받기는 `blob:`. [확인] 빌드된 `index.html`에 **인라인 스크립트 없음**(모듈 스크립트 파일 하나). React의 `style={{…}}`는 CSSOM이라 CSP에 막히지 않지만 `'unsafe-inline'`을 style-src에 두었다.

**테스트**(`test/security.test.ts`): 정상·없는 경로·415 오류 응답에 다섯 헤더, CSP의 필수 지시어와 script-src에 unsafe-inline 없음, 운영 설정에서 HSTS(설정 오류 503에도).

**한계**: Workers Static Assets의 `_headers` 지원은 [미확인](기억 기반, 문서 https://developers.cloudflare.com/workers/static-assets/headers/ 로 기억). `wrangler deploy --dry-run`은 통과. staging에서 `curl -I`로 확인한다(docs/배포안내.md 15절). 화면이 실제로 깨지지 않는지는 브라우저 테스트(e2e)로 확인하지 않았다 — e2e는 정적 자산을 `wrangler dev`로 내므로 `_headers`가 적용되면 거기서 드러난다.

## 5. 자동 백업(예정 작업 + R2)

**동작**(`src/server/backupCron.ts`)
- 크론 `*/5 18-20 * * *`(UTC, 한국 03:00~05:55, 5분마다, 트리거 1개). 한 실행에 `BACKUP_GROUPS_PER_RUN`(기본 5)개 모임까지, 모임 하나씩: 시도 시각 기록 → `exportBackup`(화면 "백업 내려받기"와 **같은 함수·형식**) → R2 `backups/{모임 ID}/{KST 날짜}.json` → 끝난 시각 기록 → 그 모임의 30일 지난 파일 삭제 → 로그 `{backup:"done", group, day, chars, ms, pruned}`.
- 고르는 순서: 오늘(KST) 끝나지 않은 모임 중 마지막 시도가 오래된 것부터. 시도 시각을 먼저 적으므로 한 모임에서 실행이 끊겨도(CPU 한도) 다음 실행은 그 모임을 맨 뒤로 미룬다. 점검 중인 모임은 건너뛴다. 남은 모임은 다음 실행(5분 뒤)이 잇는다 → 하루 최대 36 × 5 = 180개 모임.
- `BACKUPS` 바인딩이 없으면 로그만 남기고 아무것도 하지 않는다.
- 사이트 현황 `GET /api/admin/overview`에 `backup: { enabled, lastBackupAt, backedUpToday, pendingToday }`(시각·개수만, 모임 이름 없음).
- Worker 진입점이 `{ fetch, scheduled }` 객체가 됐다(`src/server/index.ts`). `fetch`는 그대로 Hono 앱.

**파일**: `src/server/backupCron.ts`(새 파일), `src/server/index.ts`, `src/server/siteAdmin.ts`, `src/server/env.ts`, `wrangler.jsonc`(`r2_buckets`, `triggers`), `migrations/0021`(`backup_tried_at`, `backup_done_at`, 색인).

**테스트**(`test/server-hardening.test.ts`, miniflare 로컬 R2): 백업 파일 생성·내용이 내려받기와 같은 형식·키 목록 동일, 30일 지난 파일 삭제·5일 전 파일 유지, 같은 날 다시 돌려도 다시 하지 않음 / 한 실행에 N개까지(`more: true`) → 이어서 모두, 점검 중 모임 건너뜀 / `scheduled` 진입점(`createScheduledController`) 호출로 파일 생성, 사이트 현황 `backup.lastBackupAt` 채워짐.

**한계**
- CPU 시간은 Worker 안에서 잴 수 없어 로그의 `ms`는 벽시계 시간(D1·R2 대기 포함)이다. CPU는 Workers Logs의 실행 기록에서 본다. 큰 모임(경기 수천)은 `exportBackup`의 JSON 만들기만으로 10ms를 넘을 수 있다 [미확인] — 그 모임은 계속 실패하고 다른 모임은 막지 않는다. 이 경우 Paid로 올리는 것이 답이다.
- 지운 모임의 지난 백업은 코드가 지우지 않는다 → R2 수명 주기 규칙(접두어 `backups/`, 30일)을 건다(docs/배포안내.md 13-4절). 처리방침 문구 확인 필요.
- `exportBackup`은 아직 순차 쿼리(약 12번 왕복)다. 스냅숏처럼 batch로 묶을 수 있다(이번에 하지 않음).

## 6. staging 환경

`wrangler.jsonc`의 `env.staging`: 이름 `naejeon-v2-staging`, D1 `naejeon-staging`, R2 `naejeon-staging-backups`, `PUBLIC_ORIGIN` 자리 표시, 운영과 같은 vars(`DEPLOY_ENV=production` 포함, 같은 안전장치), 크론은 하루 한 번(`0 18 * * *`). 배포 순서(staging 배포 → 마이그레이션 → 스파이크·손 확인 → production)와 0020·0021 리허설(d1 export → 새 DB에 가져오기 → 마이그레이션 → 개수 비교)은 docs/배포안내.md 7-0·8-1절. [확인] `wrangler deploy --dry-run --env production|staging`이 바인딩(D1·R2·버전 정보·vars)을 오류 없이 읽음. 실제 리소스는 만들지 않았다.

## 7. 웹 쪽에서 맞출 것(웹 작업자)

지금 웹을 바꾸지 않아도 모두 동작한다. 아래를 하면 재전송 안전·동시 수정 보호가 완성된다.

| 화면·호출 | 할 일 |
|---|---|
| 모임 만들기 `POST /api/groups` | 본문에 `requestId`(확인 창을 열 때 한 번 만들고 재시도에 같은 값, `newRequestId()`) |
| 모임 이름 바꾸기 `PATCH /api/groups/:gid` | `requestId` |
| 참가자 추가 `POST /api/groups/:gid/participants` | `requestId` |
| 참가자 수정 `PATCH /api/groups/:gid/participants/:pid` | `requestId` + `baseVersion`(운영자 스냅숏의 `participants[].version`). 409 `VERSION_CONFLICT`면 새로 고친 뒤 다시(이미 다른 쓰기의 409 처리와 같은 문구 가능) |
| 시즌 만들기 `POST /api/groups/:gid/seasons` | `requestId` |
| 시즌 지우기 `DELETE /api/groups/:gid/seasons/:sid` | 본문 `{ requestId }`(Content-Type: application/json) |
| 조회 링크 다시 만들기 `POST /api/groups/:gid/view-token` | 본문 `{ requestId }` |
| `src/web/api.ts` `mutate()` | 지금 POST·PUT만 받는다. PATCH·DELETE도 같은 재시도(같은 요청 ID로 최대 2회)를 쓰려면 method 타입을 넓힌다 |
| 사이트 현황(#/admin) | 응답에 새 필드 `backup: { enabled, lastBackupAt, backedUpToday, pendingToday }` — 보여 줄지 정한다 |
| 운영자 스냅숏 | 참가자에 새 필드 `version`(숫자). 화면 상태 비교·저장(초안)에 영향이 없는지 확인 |
| 조회·신청 화면 | 변경 없음. 304는 브라우저가 처리한다. fetch에 `cache: "no-store"`를 넣지 않는다(넣으면 304 이득이 사라질 뿐 동작은 같다) |
| 외부 자원 | 새 외부 출처(이미지·스크립트·분석 도구)를 쓰면 CSP(`src/server/http.ts`, `public/_headers`)에 더해야 한다 |

웹이 모두 요청 ID를 보내게 되면 `optionalRequestId`를 필수(`requireString`)로 바꾼다.

## 8. 운영에서 사람이 할 일

1. R2 버킷: `npx wrangler r2 bucket create naejeon-prod-backups`, `npx wrangler r2 bucket create naejeon-staging-backups`. 수명 주기 규칙(접두어 `backups/`, 30일) [명령 미확인].
2. staging: `npx wrangler d1 create naejeon-staging` → ID를 `wrangler.jsonc`에, `PUBLIC_ORIGIN`을 staging 주소로, `npx wrangler secret put SESSION_SECRET --env staging`(운영과 다른 값).
3. 마이그레이션 0021을 staging → 운영 순서로 적용(새 코드와 함께).
4. staging에서: 자체 계정 가입·로그인 CPU 확인(Workers Logs), `curl -I`로 정적 화면 `content-security-policy` 확인, 조회 링크 두 번째 요청 304 확인, 다음 날 R2에 `backups/…` 파일이 생겼는지와 사이트 현황 `backup.lastBackupAt`.
5. `SESSION_SECRET`은 바꾸지 않는다(바꾸면 자체 계정 비밀번호가 모두 무효). 안전한 곳에 따로 보관.

## 9. 정하지 못한 점

- 페퍼 비밀값을 `SESSION_SECRET`과 나눌지(`PASSWORD_PEPPER` 따로 두기). 지금은 지시대로 `SESSION_SECRET`.
- 20,000회가 실제 무료 요금제에서 통과하는지(측정 7ms). 넘으면 10,000으로 내릴지, 처음부터 Paid로 갈지.
- 요청 수 제한을 D1 밖(Rate Limiting 바인딩·KV)으로 옮길지 — 304로 읽기를 줄여도 제한 카운터 쓰기가 남는다.
- 백업 처리량(하루 180개 모임)이 모자랄 때 크론 시간대를 넓힐지, 한 번에 처리할 수를 늘릴지(CPU 한도와 맞바꿈).
- 지운 모임의 자동 백업 보관(최대 30일)을 처리방침에 적을지.
- 나머지 운영자 쓰기(`unlinkByOperator`, `resolveMemberRequest`)와 `exportBackup` batch화는 다음 차례로 남겼다.
