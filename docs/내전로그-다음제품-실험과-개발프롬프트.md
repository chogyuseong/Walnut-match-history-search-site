# 내전로그의 다음 제품 실험

## 제품 판단

운영자는 팀을 짜고 결과를 저장할 이유가 명확하다. 참가자는 자리와 승패를 확인한 뒤 다시 방문할 이유가 있는가? 저장소만으로 재방문 수요를 알 수는 없다. 다만 현재 자료에는 순위표가 쓰지 않는 관계 정보가 있다. 한 사람이 같은 저녁에 누구와 같은 팀이었고, 다음 경기에는 누구와 맞붙었는지 복원할 수 있다. 별도 입력 없이 참가자에게 그 기록을 돌려주는 실험을 먼저 제안한다.

| 제품 가설 | 사용자가 얻는 것 | 가장 싼 실험 | 투자하지 않을 조건 |
|---|---|---|---|
| **그날의 내 경기** | 내 이름을 누르면 한 회차에 내가 뛴 경기와 함께 뛴 사람들이 연결된다. 경기 번호를 몰라도 기억나는 판을 찾는다. | 예시 모임에서 한 사람의 회차 기록을 제공하고 기존 개인 통계로 같은 과제를 수행해 비교한다. | 기존 최근 경기 목록과 탐색 비용이 같고 참가자가 새로 발견한 정보도 없다. |
| **조건 하나만 바꾸면** | 운영자가 “둘을 같은 팀으로 두면 균형이 얼마나 달라져?”에 즉석에서 답한다. | 기존 추천 후보의 같은 편 조건 하나만 바꿔 기존안과 가능한 최선안을 나란히 놓는다. | 이미 있는 후보 세 개와 변화 요약만으로 운영자가 같은 답을 쉽게 얻는다. |
| **백업 복구 리허설** | 오래된 백업을 가진 운영자가 적용 전에 어떤 경기·사람·시즌까지 돌아올지 확인한다. | 합성 백업을 격리된 로컬 모임에 복구하고 기존 미리보기와 실제 집계 차이를 비교한다. | 기존 복원 검증이 같은 불확실성을 이미 없애거나, 추가 단계 때문에 긴급 복구가 느려진다. |
| **내전 기억 퀴즈** | 경기 사이 대기 시간에 “지난번 우리 둘이 상대였던 판은?”을 실제 기록으로 맞혀 본다. | 별도 게임을 만들기 전에 공개 가능한 예시 경기 세 건으로 수동 진행해 반응을 본다. | 몇 사람이 반복해서 놀림의 대상이 되거나, 운영자가 매번 진행해야만 성립한다. |

**추천 순서.** 결과 저장의 신뢰성 같은 운영 결함은 별도 트랙으로 관리한다. 신규 제품 실험은 ‘그날의 내 경기’부터 시작한다. 기록이 있는 모임에서 즉시 시험할 수 있고, 예상 승률이나 선수 평가의 정확도를 전제하지 않는다. 한 판만 진행한 모임에서는 기존 기록 상세가 충분할 수 있다.

## 코드로 검토한 실현 가능성

- 현재 `sessionSummary`는 회차의 확정 경기 수, 선수별 승패, 서포터 횟수, 연승을 제공한다. `MatchView`에는 회차 ID, 경기 시각, 팀·라인별 명단, 승리 팀이 있다. 기존 요약은 그대로 유용하다. 새 실험의 고유한 질문은 **“내가 누구와 어떤 순서로 같은 편 또는 상대가 됐나?”**다.
- 프로젝트의 `buildDemoSnapshot({seed: 20261106, matches: 120})`, `isCounted`, `byPlayedAt`로 계산했다. 합성 확정 경기 120개가 38개 회차에 있었고, 37개 회차가 두 경기 이상이었다. 같은 회차의 인접 경기 82쌍 중 74쌍에서 직전 경기의 팀원 둘 이상이 다음 판에 서로 상대가 됐다. **언급할 수 있는 사실이 존재한다**는 근거다. 특정 참가자에게 매번 그런 변화가 생긴다는 뜻도, 운영 모임의 90%가 이 기능을 원한다는 뜻도 아니다.
- 오히려 관계 변화가 흔하다는 결과는 모든 변화를 기사처럼 자동 노출하는 설계에 불리하다. 기본 화면은 자기 출전 경기 순서만 보여 주고, **상대 한 명을 골랐을 때** 관계를 좁혀 보는 편이 유용한지 시험한다.

## 개발자에게 전달할 실행 프롬프트

내전로그에서 **‘그날의 내 경기’** 실험을 구현하고 검증해 주세요. 목표 사용자는 경기 번호나 날짜를 정확히 기억하지 못하지만 함께 플레이한 닉네임은 기억하는 참가자입니다. 성공 과제는 “오늘 지수와 같은 팀이었다가 상대가 된 경기를 찾아 그 경기 상세를 여는 것”입니다. 아래 이름은 설명용 가명입니다.

### 1. 기존 기능으로 먼저 풀어 보기

1. 현재 브랜치와 작업 트리, `CLAUDE.md`, 기존 화면 구현과 E2E를 읽으세요. `src/shared/sessionSummary.ts`, `stats.ts`, `headToHead.ts`, `src/web/screens/Person.tsx`, `Compare.tsx`, `Demo.tsx`, `Viewer.tsx`부터 확인하세요.
2. 같은 합성 모임으로 개인 통계의 최근 경기, 두 사람 비교, 기록 필터 세 경로를 따라가세요. 이미 어떤 질문에 답하는지, 어디서 명단 둘을 사람이 직접 대조해야 하는지 기록하세요. 기존 화면 한 곳에 회차 필터와 상세 연결만 더하면 목적을 달성할 수 있다면 그 방법을 택하세요.
3. 실험용 자료는 최소 네 경기입니다. 1경기에서 나와 지수는 같은 팀, 2경기에서 나는 휴식, 3경기에서 둘은 상대, 4경기에서는 지수만 휴식입니다. 이 자료에서 “내 직전 출전 경기”와 “모임 직전 경기”를 구분하세요.

### 2. 첫 버전의 경험

- 예시 모임의 개인 통계나 기존 최근 경기 영역에서 시작하세요. 이미 고른 사람과 회차를 이어받고, 출전 경기들을 시간순으로 보여 주세요. 각 줄에는 기존 경기 식별자, 내 라인, 내 승패, 상세 진입만 둡니다. 기존 상세 페이지와 뒤로 가기를 재사용하세요.
- 같은 회차에서 함께 출전한 사람 한 명을 선택하면 각 경기에서 **같은 팀 / 상대 팀 / 함께 출전하지 않음**을 알 수 있어야 합니다. 팀 A·B 식별자로 비교하세요. 진영 정보가 없어도 성립하며, 블루·레드를 추정할 필요가 없습니다.
- 예시 결과는 “지수와 1경기에서는 같은 팀, 3경기에서는 상대 팀”입니다. 2경기를 건너뛰었으므로 ‘바로 다음 경기’라는 표현은 틀립니다. 4경기에서 다른 사람이 빠졌다고 해서 상대 관계가 새로 생겼다고 세지 마세요.
- 차트, 배지, 메뉴를 먼저 추가하지 마세요. 390px 모바일에서 참가자 이름과 관계, 상세 진입이 읽히는 짧은 목록부터 구현하세요. 한 판뿐인 회차는 그 경기만 보여 주고, 둘이 함께 뛴 적이 없다면 그 사실을 짧게 표시하세요.
- 이번 실험의 정상 진입점과 적용 경로를 명시하세요. 예시 모임에서 가치를 검증하는 첫 버전이라면 운영자·공개 링크 전체 배포로 확대하지 마세요.

### 3. 데이터 계약과 경계 사례

- 회차는 유효한 `sessionId`로 묶고 정렬은 앱의 기존 경기 순서를 따르세요. 자정을 넘겨도 같은 회차는 유지합니다. 회차가 없는 과거 가져오기 자료를 한 묶음으로 합치지 마세요. 해당 자료는 원래 기록 상세에서 계속 접근할 수 있어야 합니다.
- 기본 결과 범위는 프로젝트의 확정 경기 집계 규칙을 따릅니다. 취소·제외·결과 대기를 섞어 개인 승률을 다시 만들지 마세요. 닉네임이 같은 두 사람은 참가자 ID로 구별하고, 합쳐진 참가자에 대해서는 기존 조회 화면과 동일한 기준을 적용하세요.
- 참가하지 않은 경기만 보고 ‘귀가’, ‘늦참’, ‘벤치’를 추론하지 마세요. 한 사람이 잘해서 이겼다거나 특정 팀원 때문에 졌다는 인과 설명도 데이터가 뒷받침하지 않습니다.
- 첫 버전은 현재 경로가 이미 읽을 수 있는 스냅숏에서 계산하세요. 운영자 전용 티어, 기피 라인, 링크 토큰을 새 UI나 내보내기에 넣을 이유가 없습니다. 계산은 해당 회차와 두 사람의 명단 대조로 충분합니다. 전 모임의 모든 선수 쌍에 대한 영구 테이블이나 새 통계 모델은 필요하지 않습니다.
- 동명이인, 진영 미상, 단 한 경기, 중간 결장, 자정 통과, 같은 회차의 경기 정정 후 새 스냅숏을 대표 경계 사례로 삼으세요. 기록 정정이 있으면 새 사실을 반영하고 이전 관계 문장을 남기지 마세요.

### 4. 검증과 출시 판단

1. 순수 계산 검증에서는 위 네 경기의 출력 순서와 관계를 기대값으로 고정하세요. 선택한 선수 관점에서 승패가 뒤집히는 사례와 회차 ID가 없는 두 경기가 섞이지 않는 사례를 포함하세요.
2. 브라우저에서는 **개인 화면 → 회차 확인 → 함께 뛴 사람 선택 → 3경기 상세 → 뒤로**를 끝까지 실행하세요. 선택한 사람과 목록 맥락이 보존되는지, 키보드만으로 선택과 상세 진입이 가능한지 확인하세요. 기존 번들 예산과 디자인 감사도 지키세요.
3. 사용성 비교에서는 정답 도달 여부, 불필요하게 연 경기 상세 수, 사람이 직접 대조한 명단 수를 기록하세요. 같은 사람이 같은 정답을 외운 채 두 경로를 쓰지 않도록 난이도가 비슷한 다른 경기 쌍을 사용하세요. 개발자 자동화로 확인한 결과와 실제 참가자 관찰은 구분하세요.
4. **확대 조건**은 참가자가 기존 경로보다 적은 명단 대조로 정확한 경기를 찾고, 별도 설명 없이 ‘내 직전 출전’의 뜻을 이해하는 것입니다. 이미 기존 비교 화면으로 충분하거나, 과거 동료를 고르는 일이 더 번거롭거나, 한 판짜리 모임이 주 사용처라면 기존 화면 개선으로 마무리하세요.
5. 최종 제출물은 기존 경로의 기준 결과, 변경 파일과 선택 이유, 네 경기 예시의 실제 출력, 실행한 검사, 확인하지 못한 사용자 가설, 확대 또는 중단 권고입니다. 실제 사용자를 만나지 못했다면 수요와 재방문 효과는 미검증으로 남기세요.

## 실행 결과 (2026-11-19)

### 기존 경로로 먼저 풀어 본 결과

- **개인 통계 "최근 경기"**: 날짜·경기 번호·승패·라인을 한 줄씩 보여 준다. 함께 뛴 사람은 없어서 지수와의 관계는 경기 상세를 하나씩 열어 명단을 봐야 안다. 네 경기 예시라면 상세 세 개를 열고 명단 세 개를 대조한다.
- **두 사람 비교 "함께 뛴 경기"**: 같은 팀·상대 팀은 이미 판정한다(`headToHead.ts pairOutcome`). 다만 "맞대결"과 "같은 팀" 두 탭으로 나뉘어 있어서, 같은 팀이던 판과 상대이던 판의 순서를 보려면 두 탭의 날짜·경기 번호를 사람이 맞춰 봐야 한다. 기간은 "오늘"까지만 좁힐 수 있어 지난 모임 하루를 고를 수 없다. 개인 통계에서 그날 함께 뛴 사람을 고르는 길도 없다.
- **기록 화면 거르기**: 사람 하나와 라인으로만 거른다. 두 사람을 함께 거를 수 없다.

그래서 문서 1-2단계의 결론대로 **새 화면을 만들지 않고 두 사람 비교 화면에 회차 목록을 더했다.** 판정은 기존 `pairOutcome`과 같은 기준(확정 경기, 팀 A/B 글자 비교)이다.

### 네 경기 예시의 실제 출력

1경기 가람·지수 같은 팀(승) → 2경기 가람 쉼 → 3경기 둘이 상대(B 승) → 4경기 지수 쉼(자정을 넘긴 0시 10분 경기)일 때:

```
그날 경기 (가람 기준)
그날 모임 4경기 중 가람 출전 3경기, 앞 경기부터예요.
지수: 같은 팀 1 · 상대 팀 1 · 함께 안 뜀 1
1경기 · 탑   승 · 같은 팀
3경기 · 탑   패 · 상대 팀
4경기 · 탑   승 · 함께 안 뜀
```

- 2경기는 줄이 없어 번호가 1 → 3으로 건너뛴다. "바로 다음 경기"라는 말은 쓰지 않는다.
- 4경기는 지수가 없었다는 사실만 적는다. 늦게 왔는지 쉬었는지는 말하지 않고, 상대 관계로도 세지 않는다.
- 지수 쪽에서 보면 3경기는 이긴 경기다(단위 테스트로 확인).
- 결과 대기·취소 경기는 순서에 넣지 않는다. 결과를 정정하면 새 스냅숏대로 바뀐다(이전 판정을 남기지 않는다).
- 회차가 없는 가져온 경기는 같은 날이어도 회차로 묶지 않는다. 원래 경기 목록과 상세에서 그대로 본다.
- 이름이 같은 두 사람은 참가자 ID로 구별한다. 합쳐진 사람의 주소로 들어오면 비교 화면의 기존 규칙대로 남은 사람으로 연다.

### 확인하지 못한 것

- **실제 참가자 관찰은 하지 않았다.** 명단 대조가 줄었는지, "앞 경기부터"와 번호 건너뜀을 설명 없이 이해하는지, 재방문이 늘었는지는 모두 미검증이다. 위 결과는 개발자 자동 확인뿐이다.
- 같은 날 회차가 둘이면 회차 고르기에 같은 날짜가 두 번 나왔다. 같은 날짜일 때만 첫 경기 시각을 붙이게 고쳤다(2026-11-19, "11월 18일 오후 8:10").

### 권고

확대하지 말고 이 상태로 다음 실제 내전에서 관찰한다(README "바로 다음" 5번). 참가자가 기존 맞대결·같은 팀 탭보다 적은 명단 대조로 정답 경기를 찾으면 개인 통계 쪽 입구를 더 눈에 띄게 하는 것을 검토한다. 기존 탭으로 충분하다고 하거나 한 판짜리 모임이 대부분이면 이 구역은 그대로 두고 더 넓히지 않는다.
