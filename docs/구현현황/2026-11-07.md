### 준비 화면 추가 기능 6가지 (2026-11-07)

준비 화면(`Prep.tsx`)에 편성 균형·라인 맞대결·되돌리기 여러 단계·대기자 교체·편성 이미지·같은 편성 경고를 더했다. 순수 로직은 새 파일 `src/shared/prepTools.ts`에 모으고, 되돌리기 이력은 `src/shared/draft.ts`에 넣었다. 서버·DB 스키마·서버 프로토콜은 바꾸지 않았다. 초안에 더한 필드(`history`·`redoSlots`·`bench`)는 모두 선택 필드라 `DRAFT_FORMAT_VERSION`은 1 그대로이고, 기기에만 보관하며 서버로 보내지 않는다. 섞기·서포터 규칙·시드 결정성은 바꾸지 않았다.

#### 규칙

- 시작 1000. 팀 MMR = 팀원 MMR 평균. 기대 승률 `E = 1/(1+10^((R상대 − R내)/400))`. 변화 `Δ = K × (S − E)`(S: 승 1·패 0).
- K는 **사람마다** 이 경기 전 확정 경기 수로 정한다: 10 미만(배치 중) 40, 그 뒤 20. 같은 팀원은 (S − E)가 같으므로 K가 같은 사람끼리 변화가 같다.
- 한 경기의 열 명이 모두 같은 K 단계면 두 팀 변화의 합은 0이다. **배치 중인 사람과 끝난 사람이 섞인 경기는 합이 0이 아니다**(지시의 "팀원에게 똑같이"·"합 0"과 "사람별 K"가 함께 성립하지 않아 사람별 K를 따랐다. 배치 중인 사람이 빨리 제자리를 찾게 하는 흔한 Elo 방식). 그래서 모임 전체 평균은 1000에서 조금씩 벗어날 수 있다.
- 소수는 그대로 쌓고 화면·CSV에는 반올림한 정수. 비공개 정보(티어)는 쓰지 않는다. 조회 링크·예시 모임·멤버 화면도 같은 화면 컴포넌트라 그대로 보인다(공개 응답의 경기 결과로 계산).

같은 날짜에 세션 경기와 세션 없는 기록이 같이 있으면 모임 날이 둘로 센다. 드물어서 합치지 않았는데 실제 데이터에서 걸리면 날짜 기준으로 바꾸면 된다. 테스트는 876개로 늘었고 season-awards의 상 목록 기대값에 upsetMaker를 추가했다.

### 준비 화면 예상 승률 판 (2026-11-09 추가)

### MMR 랭킹 탭 (2026-11-09)

MMR 순위가 기록 화면의 소환사 랭킹에서 정렬을 "MMR 순"으로 바꿔야만 보여서 눈에 안 띈다는 말이 나와, 주 메뉴에 "랭킹" 탭을 기록과 분석 사이에 넣었다(`#/ranking`, `screens/Ranking.tsx`). 조회 링크·예시 모임·참가 중인 모임 메뉴에도 "랭킹"을 달았고, 참가자 편성 화면(`/live`)에는 "기록 보기" 옆에 링크만 하나 두었다. 서버는 건드리지 않았다.

범위 고르기는 일부러 뺐다. MMR이 원래 누적값이라 시즌을 고르게 하면 "시즌 MMR"처럼 읽힐 것 같아서 "누적 기준" 한 줄만 적었다. 순서와 묶음은 새로 만들지 않고 기록 화면 MMR 순과 같은 `rankAndSearch`를 썼다. 두 화면의 순위 숫자가 어긋나면 설명할 길이 없어서다. 그래서 같은 MMR일 때 승률 다음에 경기 수가 한 번 더 들어간다.

요약 타일 셋(1위·최근 10경기 최고 상승·최고 MMR 기록)은 `src/shared/ranking.ts`에서 뽑는데 배치 진행 중인 사람은 후보에서 뺐다. 배치 중에는 K가 40이라 몇 판만 이겨도 최고 상승을 차지해 버린다. 반올림해 +1이 안 되면 최고 상승은 "—"로 둔다. 배치 진행 중 줄도 MMR 숫자 대신 "배치 n/10" 미터로 보여 준다.

이름은 개인 통계로 가는 링크라서 줄 전체를 누르게 할 수 없었다. 오른쪽 끝에 ▾ 버튼(44px)을 따로 두고 한 번에 한 사람의 MMR 추이만 펼친다. 2·3위 은·동 색은 토큰이 없어 `--ih-accent-silver`·`--ih-accent-bronze`를 다크·라이트에 새로 넣었다. 탭이 여섯 개가 되면서 720~1023px에서는 탭 칸 최소 폭을 60px에서 52px로 줄였다. 720px에서 오른쪽 테마 고르기와 거의 맞닿는데 겹치지는 않는다.

찜찜한 점: 홈 요약의 "랭킹 상위"와 기록 화면의 소환사 랭킹은 여전히 승률이 기본이라 "랭킹"이라는 말이 두 가지 뜻으로 쓰인다. 주 메뉴 테스트는 탭 5개에서 6개로 고쳤다. 테스트 905개, 가장 큰 JS 218.8KB 그대로이고 랭킹 화면은 따로 조각으로 받는다.

목록만으로는 1위나 30위나 같은 모양이라 화려하게 해 달라는 요청이 와서, 누적 50경기 이상 1~3위를 시상대로 세우고 10위까지 색 띠와 순위 색을 단계로 줬다. 시상대를 배치 완료자까지 넓히면 몇 판 안 한 사람이 금메달을 달 수 있어서 50경기 묶음으로 한정했고, 그래서 새 모임에서는 시상대가 비어 있다. MMR 막대는 1000 근처끼리라 최고 대비 비율로는 다 똑같아 보여 묶음 최저~최고를 늘려 그렸는데, 격차가 실제보다 커 보이는 게 찜찜하다.

### MMR 연속성 가중 (2026-11-09)

"그냥 이긴 것과 연승으로 이긴 것, 그냥 진 것과 연패한 것이 달라야 한다"는 요구가 들어왔다. 먼저 확인한 사실은 체스·바둑의 Elo에는 연승 가산이 없다는 점이다. 그래서 Elo를 그대로 두지 않고, Glicko-2가 결과가 한쪽으로 몰리는 사람의 변동성을 키워 점수를 더 크게 움직이는 생각만 단순하게 빌려 왔다.

규칙은 `src/shared/rating.ts`에 있다. 사람마다 직전까지 같은 방향으로 이어진 결과 수를 세고, 이번 결과가 같은 방향이면 하나 더한 값이 run이다. run 1·2는 1배, 3은 1.25배, 4는 1.375배, 5 이상은 1.5배에서 멈추고, 이 배수를 K에 곱한다(`STREAK_K_START`·`STREAK_K_STEP`·`STREAK_K_MAX`). 방향이 바뀌면 다음 경기는 다시 1배다. 세는 경기는 MMR 계산과 같은 유효 확정 경기뿐이라 결과 대기·제외 경기는 연속을 끊지도 잇지도 않는다.

K에 곱하는 방식을 고른 이유는 기대 승률(S − E)을 그대로 두기 때문이다. 강팀을 이긴 연승은 크게, 약팀만 이긴 연승은 여전히 작게 오른다. 상한 1.5는 배치 중 K 40에 곱해도 한 판 변화가 60을 넘지 않게 잡은 값이다. `STREAK_K_MAX`를 1로 두면 예전 계산과 같아진다. 경기마다 `run`·`multiplier`를 history에 남겨 화면이 "×1.25" 같은 꼬리표를 달 수 있게 했지만, 지금은 경기 상세에 MMR 변화 표시가 없어 꼬리표는 붙이지 않았다. 랭킹 탭·소환사 랭킹 MMR 순·개인 통계 도움말에는 "3연승·3연패부터 변화 폭이 커져요(최대 1.5배)"를 넣었다.

팀원 열 명이 각자 자기 run으로 가중치를 받으니 한 경기 두 팀 변화의 합이 0이 아닐 수 있다. 배치 K가 섞일 때도 이미 그랬으니 새 성질은 아니다. 테스트는 `rating.test.ts`에 8개를 더했고, 기존 기대값 중 바뀐 것은 history 점에 새 필드 두 개가 붙은 것뿐이다.

찜찜한 점: 연승 가중이 예상 승률을 더 출렁이게 해서 경기 전 예상·이변 판정의 정확도에 영향을 줄 수 있다. 경기가 쌓이면 그래프 분석 섞기 공정성의 "예상 우세 팀 승률"로 적중률이 오르는지 내리는지 보고 상한을 다시 정하면 된다. 검증은 `npm test` 929개, typecheck, lint(오류 0), build, check:bundle을 돌렸다.

### 그래프 분석 코멘트 (2026-11-09)

그래프 분석이 숫자와 그림만 늘어놓아 "그래서 뭐가 좋은데"를 읽는 사람이 해석해야 했다. AI가 평가해 준 것 같은 문장을 달아 달라는 요청이었지만 외부 AI API는 쓰지 않았다. 무료 요금제 설계라 호출 비용과 키 관리를 들일 수 없고, 화면을 열 때마다 응답을 기다리게 되며, 같은 기록에 매번 다른 말이 나오면 믿기 어렵다. 그래서 이미 계산하던 수치(라인별 승률, 최근 10경기, MMR delta10·최고점, 이변, 시너지, 진영, 참석, 순위 변동, 날짜별 경기 수)를 규칙으로 읽어 문장을 만드는 `src/shared/commentary.ts`를 새로 두고, 카드 아래에 "기록 수치를 규칙으로 읽어 쓴 평가예요"라고 그대로 밝혔다.

임계값은 거의 "작은 표본의 운을 걸러낼 만큼"으로 잡았다. 승률 차는 15%p(라인·흐름·진영 공통), 라인 비교는 색을 칠하는 기준과 같은 5경기, 단정형 말투는 15경기부터이고 그보다 적으면 "~로 보여요"로 바꾼다. MMR은 한 판 변화가 보통 10~20이라 최근 10경기 ±30을 "빠르게", 최고점 대비 60을 "회복 구간"으로 봤다. 범위 안 경기가 10개 미만이면 첫 문장을 "아직 판단하기 일러요"로 하고 두 문장만 남긴다. 모든 값은 이름 붙인 상수에 바꾸면 무엇이 달라지는지 한 줄씩 적었다.

처음 안에서 그대로 따르지 않은 것이 둘 있다. "같은 팀이 전체 경기의 40% 이상이면 뭉침"은 열 명 고정 모임에서 무작위로 섞어도 한 쌍이 같은 팀일 확률이 4/9(약 44%)라 거의 늘 걸린다. 그래서 두 사람이 함께 나온 경기를 분모로 바꾸고 60%(함께 나온 10경기 이상)로 올렸다. 개인 최근 흐름은 `trends`가 모임 단위 목록이라 쓰지 않고 `personDetail`의 recent10과 범위 누적을 비교했다. 또 잘 맞는 동료가 혼자 승률보다 낮은 19%로 "가장 강해요"가 나오는 걸 보고, 시너지 +5%p 이상·상대 승률이 내 승률보다 10%p 이상 낮을 때만 말하게 했다. 같은 사람이 동료이자 상대로 뽑히면 "같은 팀이면 83%, 상대 팀이면 41%"처럼 한 문장으로 묶는다. 이름 끝이 숫자인 사람(사람01)도 조사가 맞도록 영·일·삼·육·칠·팔을 받침으로 친다.

이야기 띠의 같은 팀 쌍 세기는 `teammatePairs`로 꺼내 둘이 같이 쓴다. 모임 코멘트는 순위 변동 계산이 들어 있어 고른 사람이 없을 때만 구한다.

찜찜한 점: 총평의 "상위권·중위권·성장 중"은 승률과 MMR 순위만 보는 단순한 표라, 승률은 높은데 배치 중인 사람은 상위권이 될 수 없다. 데모 모임은 금요일에만 모여 요일 문장이 "모임은 늘 금요일이에요"로 나오는데, 정보가 거의 없는 문장이라 빼는 편이 나을 수도 있다. 검증은 `test/commentary.test.ts` 13개를 더해 `npm test`, typecheck, lint(오류 0), build, check:bundle을 돌렸고, 데모 화면을 390px·1100px로 찍어 가로 넘침이 없는지 봤다.

### 작은 글자 한 단계 올림 (2026-11-09)

사이트 전체 글자가 작아 안 보인다는 말을 들었다. 본문(1rem)과 제목은 두고 13px 이하만 한 단계씩 올렸다. 안내문·캡션·라벨·칩 0.75~0.8125rem은 0.875rem으로, 10~11px짜리(달력·순위 변동 축, 분포 띠 숫자, 티어 알약)는 12px로. 약 95군데라 값을 파일 전체에서 한꺼번에 바꿨고, 그래서 같은 시간에 다른 작업으로 파일 끝에 들어간 0.75rem 규칙(추이 눈금 등)도 같이 올라갔다. 눈금은 0.875rem이면 조금 큰 느낌이 있지만 읽히는 게 먼저라 그대로 뒀다.

칸 안에 들어가는 글자는 칸을 같이 키워야 넘치지 않는다(승·패 점 1.25→1.375rem). 320·390·1100px에서 요약·기록·랭킹·그래프 화면 가로 넘침은 없었다. 좁은 폰의 경기 카드 이름만 열 명이 한 줄에 들어가야 해서 한 단계 덜 올렸다. TSX 안 SVG 글자 크기 속성은 손대지 않았다.

하나 걸린 게 있었다. 기록 화면 e2e(시나리오 13, 맨 아래로 내린 채 갱신)가 입력 칸이 6px 밀린다고 실패했다. 추적해 보니 419px 이하 랭킹 행에서 오른쪽 전적 칸 글자가 커지며 왼쪽이 118px로 줄었고, 승·패 점이 셋이 되는 순간 연승 글과 함께 두 줄로 접혀 행 높이가 바뀐 것이었다. 페이지가 맨 아래에 붙어 있으면 아래쪽 높이 변화는 보정할 수 없다. 그 행에서만 점과 보조 글자를 한 단계 작게 두고 좌우를 58:42로 나눴고, 전적 글은 낱말 단위로만 줄을 바꾸게 했다. 남는 1~2px는 소수점 줄 높이의 반올림이라 테스트 허용치를 2px로 올렸다.

### 배치 경기 수 설정 (2026-11-09)

배치 경기 수를 운영자가 모임 안에서 바꾸게 해 달라는 요청이었다. 값은 `Settings.placementGames`(없으면 기본 10)에 두었다. 설정은 JSON 한 덩어리로 저장되니 마이그레이션은 없고, 옛 백업·저장한 적 없는 모임은 그대로 10으로 읽힌다. 조회 링크 응답에도 내보낸다. 이 값으로 배치를 판정하는 조회 화면도 운영자와 같은 숫자를 봐야 해서다.

계산 함수(`computeRatings`·`standings`·`matchExpectations`·`draftForecast`·`rankRace`·`ratingRank`·`suggestPriorities`·코멘트)는 설정을 직접 읽지 않고 `placementGames` 인자를 받는다. 기본값이 10이라 기존 호출과 테스트가 그대로 돌고, 함수가 스냅숏 전체를 몰라도 되는 순수 함수로 남는다. 화면은 `placementGamesOf(snapshot.group.settings)`로 한 번 읽어 넘긴다. 전역 상수를 런타임에 바꾸는 방식은 모임을 오갈 때 값이 섞일 수 있어 버렸다.

범위 1~30은, 0이면 모두가 첫 경기 전부터 배치 완료라 뜻이 없고, 30을 넘기면 주 1회 모임에서 반년 넘게 칭호가 안 붙어 실제로 쓸 일이 없다고 봤다. 서버 `parseSettings`가 정수·범위를 검사하고(400 `INVALID_FIELD`), 복원도 같은 함수를 지나니 백업 쪽 검사가 따로 필요 없다.

찜찜한 점: 인자에 기본값이 있어 새 호출부가 값을 빠뜨려도 타입 검사가 잡지 못하고 조용히 10으로 계산된다. 또 `FAIRNESS_MIN_GAMES`·`RACE_MIN_GAMES`·`SUGGEST_PRIOR_GAMES`는 "배치 판수와 같게" 10으로 잡은 표본 기준이라 설정과 묶지 않고 10으로 두었다. 배치 경기 수를 3으로 줄여도 공정성 판정은 여전히 10경기가 있어야 나온다.

### MMR 시작값·K 설정과 시즌 2 티어 이름표 (2026-11-09)

MMR 시작 점수와 변화 폭을 모임이 정하게 하고, 기본값을 1000·40/20에서 1200·50/30으로 바꿨다. 1200은 LoL 시즌 2에서 새 계정이 받던 시작 Elo와 같아서, 아래 티어 이름표를 붙였을 때 "처음엔 브론즈 끝자락에서 시작"이라는 감각이 그대로 살아난다. K를 50/30으로 올린 건 열 명 고정 모임에서 점수 차가 너무 좁게 모여(예전 기본으로 수십 판 뒤에도 대부분 ±100 안) 순위가 승률과 다를 게 없어 보였기 때문이다.

설정은 `Settings.ratingStart`·`ratingKPlacement`·`ratingK`(배치 경기 수와 같이 없으면 기본값)이고, 범위와 화면 이름은 `rating.ts`의 `RATING_SETTING_RANGES` 한 곳에 두어 서버 `parseSettings`와 모임 탭의 "MMR 설정" 칸 넷이 같이 쓴다. 계산 함수는 `computeRatings(matches, options)`처럼 빠진 값은 기본값으로 채우는 옵션 객체를 받고, 화면은 `ratingOptionsOf(snapshot.group.settings)`로 읽어 넘긴다. MMR 추이 그림의 가운데 선, 연결 안 된 사람의 예상 승률 값, 두 사람 비교의 단계 글자도 시작값을 따라간다.

티어 이름표는 시즌 2 종료 기준 Elo 구간(1250·1520·1900·2200)을 숫자 그대로 쓴다. 사용자가 "동일하게"를 원했고, 구간을 시작값에 맞춰 옮기면 같은 "골드"가 모임마다 다른 뜻이 되어 버린다. 그래서 시작값을 바꾸면 처음 놓이는 티어가 달라진다. 배치 중에는 이름표를 붙이지 않는다. 칭호(테두리형 알약)와 헷갈리지 않게 이름표는 채움형 네모로 그렸다. 티어 이름은 Riot의 상표가 들어간 말이라 도움말과 README에 "LoL 시즌 2 Elo 구간을 따랐다"고만 밝히고 공식 등급처럼 보이는 엠블럼은 쓰지 않았다.

기존 단위 테스트 중 손으로 계산한 값(시작 1000·K 40/20)은 옵션을 직접 넘겨 계산 규칙만 보게 했고, 새 기본값은 따로 검산했다(첫 경기 ±25, 같은 팀이 또 이기면 50 × (1 − E(1225, 1175)) ≈ +21.43). e2e `rating.spec.ts`의 숫자는 1041·959에서 1252·1148로 바뀌었다.

찜찜한 점: 예시 모임은 60경기 남짓 쌓여도 1위가 1504라 모두 실버·브론즈다. 열 명이 돌아가며 붙는 내전에서는 Elo 점수가 시즌 2 래더처럼 넓게 퍼지지 않아서, 골드 위 구간은 사실상 비어 있을 것이다. K를 더 키우면 퍼지지만 한 판 운에 크게 흔들린다. 쓰다 보면 구간을 모임에 맞게 옮겨 달라는 말이 나올 수 있다. 그래프 코멘트의 "최근 10경기 ±30이면 빠르게" 같은 MMR 임계값도 K 20 시절 기준이라 K 30에서는 조금 더 자주 걸린다.

### 개인 통계 맞라인 상대 (2026-11-09)

개인 통계에 "맞라인 상대" 묶음을 더했다. 같은 라인에서 상대 팀으로 맞붙은 사람별 전적을 내 기준으로 보여 준다. 계산은 `headToHead.ts`의 `laneRivals`로, 두 사람 비교의 `laneDuels`와 같은 규칙(확정 경기만, 포지션 기록 없는 경기 제외)을 모든 상대로 펼친 것이다. 한 사람과 여러 라인에서 만났으면 라인마다 따로 센다.

라인마다 3경기(`LANE_RIVAL_MIN`) 이상 만난 상대 중 승률이 가장 낮은 사람을 "가장 어려운"(빨강), 가장 높은 사람을 "가장 쉬운"(초록) 칩으로 둔다. 승률이 같으면 경기 수가 많은 쪽이다. 후보가 한 명이면 둘이 같은 사람이라 승률 50% 미만이면 어려운 칩, 이상이면 쉬운 칩 하나만 보인다. 아래 "전체 보기"(기본 접힘)는 상대별 행이고, 누르면 두 사람 비교로 간다.

자리는 처음 생각한 라인별 바로 아래가 아니라 "다른 플레이어와 비교" 다음, 참여 경기 위다. 720px부터 2단 격자에서 라인별이 두 줄을 차지하는데, 그 아래에 새 구역을 끼우면 진영별이 밀려 오른쪽 칸이 비었다. 지금 자리는 비교 구역 옆 칸에 짝지어 놓인다.

찜찜한 점: 예시 모임처럼 경기가 적으면 "가장 어려운" 상대가 67%처럼 내가 이긴 쪽인 경우도 나온다. 라인별 상대가 고르게 흩어져 3경기 넘는 상대 자체가 드물다.

처음 구현은 라인마다 승률 최저·최고를 그대로 "가장 어려운"·"가장 쉬운"으로 불러서, 예시 모임에서 67% 이기는 상대가 어려운 상대로 떴다. 어려운 쪽은 50% 미만에서만, 쉬운 쪽은 50% 이상에서만 고르게 바꿨다. 한쪽이 없으면 칩도 하나만 나온다.

### 두 사람 비교: 같은 라인으로 맞붙었을 때 (2026-11-09)

비교 화면의 "라인별 승률"은 각자 전체 경기 기준이라, 사용자는 "상대와 똑같은 라인에 섰을 때 승률"을 기대했다. 그 값은 원래 "상대일 때" 안에 "미드 3승 1패" 칩으로 작게 있었는데 눈에 안 들어왔다. 독립 구역으로 떼서 라인마다 왼쪽에 A 승률, 가운데 라인과 경기 수, 오른쪽에 B 승률을 두고 아래에 A:B 막대를 깔았다. 두 사람이 같은 경기에서 마주 선 것이라 경기 수는 양쪽이 같고 승률은 서로 거울이다(60% ↔ 40%). 계산은 기존 `laneDuels` 그대로다.

### 요약 전광판과 시작값 기준 막대 순위표 (2026-11-10)

디자인 시안 일곱 개 중 사용자가 고른 둘을 실제 화면에 옮겼다. 요약 탭(조회 링크·예시 모임)은 가장 최근 확정 경기를 전광판(`matchCard.tsx`의 `MatchScoreboard`)으로 크게 올린다. 위에 블루·레드 띠, 진영 이름과 승리·패배 라벨, 가운데 시리즈 점수(시리즈가 아니면 숫자 없이 "vs"), 그 아래 라인끼리 마주 세운 이름 줄이다. 블루가 늘 왼쪽이고 진영을 모르면 팀 A가 왼쪽에 ●A/■B로 선다. 포지션이 없는 경기는 라인 칸 없이 두 줄로만 나뉜다. 두 팀은 따로 group으로 묶어 경기 카드와 같은 "블루팀 승리" 이름을 갖고, 라인 칸은 그 사이에 읽지 않는 칸으로 둔다. 줄 높이를 고정해 DOM이 나뉘어 있어도 라인이 같은 줄에 선다. 시리즈 점수는 기준 판 팀 A 쪽이 앞이라 `seriesScoreOfMatch`가 이 경기의 팀 쪽으로 옮겨 준다. 나머지는 "이전 경기" 카드 4개로 그대로 두어 전광판까지 다섯 경기다. 운영자 홈은 위에 오늘의 결과가 있어 전광판을 두지 않는다(`Dashboard`의 `headline`). 영어 BLUE/RED와 Barlow 글꼴은 쓰지 않고 "블루"/"레드"를 굵은 기본 글꼴로 썼다.

KPI 띠의 블루 : 레드 승률은 두 숫자 사이에 비율 막대를 넣었다. 같은 `KpiStrip`이라 기록·오늘 화면의 띠에도 막대가 생긴다.

MMR 랭킹은 시상대 세 칸을 포인트 색으로 채운 1위 칸 하나로 바꿨다(누적 50경기 이상 묶음의 1위만, 규칙은 `podiumOf` 그대로). 채운 색은 테마의 `--ih-brand-fill`이라 다크는 골드, 바이올렛은 보라, 라이트는 잉크색이다. 그 위 글자는 `--ih-on-brand-fill` 하나로 쓰고 칭호·티어·변동·승패 칸의 원래 색은 바탕 위 대비가 깨져 같은 글자 색으로 바꿨다. 순위표 줄에는 묶음 안 최저~최고를 견주던 막대 대신 시작 MMR 기준선에서 오른쪽(올랐다)·왼쪽(내렸다, 패배 색)으로 뻗는 막대를 두었다. 눈금은 배치 완료자 전체의 최저·최고 MMR에 시작값을 넣어 넓힌 범위(`ranking.ts`의 `mmrScale`·`divergingBar`)라 검색해도 흔들리지 않는다. 막대마다 "시작 1200보다 +304" 같은 읽기용 글자가 있고, 맨 위에 눈금 줄(최저 · 시작 · 최고)을 둔다. 줄마다 따로 grid라 넓은 화면에서는 막대 양옆 칸을 고정 폭으로 두어 막대가 세로로 맞는다. 폰에서는 막대가 이름 아래 한 줄을 따로 쓴다.

좁은 화면(719px 이하)에서는 조회·예시 메뉴의 화면 링크를 CSS만으로 운영자 하단 탭과 같은 자리·모양으로 내렸다. 모임 이름은 위에 남고, 본문 아래 여백은 원래 하단 탭 높이만큼이라 가리는 곳이 없다. 화면 키보드가 열리면 하단 탭처럼 숨긴다.

### 챔피언 기록 (2026-11-10)

경기마다 각자 쓴 챔피언을 원하면 골라 남길 수 있게 했다. 2026-11-06에 한 번 만들다가 "손으로 넣어야 해서 안 쓰일 것"이라며 되돌린 기능인데, 이번에는 사용자가 "넣고 싶은 사람만, 검색으로 빨리"라는 조건으로 다시 요청했다. 그래서 안 쓰는 모임의 흐름은 그대로 두는 것을 첫 기준으로 잡았다. 결과 입력 창에는 "챔피언도 기록하기(선택)" 접힌 영역 하나만 늘었고, 펼치지 않으면 요청 본문이 예전과 한 글자도 다르지 않다(e2e로 본문 키를 확인한다).

저장은 `match_roster.champion` 열 하나다(migrations/0025, 칸 추가만). 값은 Riot 데이터의 고정 키(`Ahri`, 오공은 `MonkeyKing`)이고 목록은 `src/shared/champions.ts`에 171개를 글자로만 넣었다. 새 챔피언은 그 파일에 한 줄 더하면 된다. 유나라(2025년 여름) 뒤에 나온 챔피언은 키와 한글 이름을 확실히 알지 못해 넣지 않았으니, 운영 전에 실제 게임 목록과 맞춰 보고 빠진 것을 더해야 한다. 서버는 목록에 있는 키만 받는다. 같은 챔피언을 두 사람이 골라도 막지 않는다.

결과 입력 때 고른 값은 기존 결과 요청에 선택 항목 `champions`({ 참가자 ID: 키 })로 얹었다. 메모와 같은 방식이라 보내지 않은 요청은 예전과 같은 내용으로 해시돼 요청 ID 재시도가 깨지지 않는다. 나중에 고치는 것은 따로 `POST …/matches/:id/champions`(requestId, baseMatchVersion, champions)를 두었다. 메모는 경기 버전을 올리지 않고 "직전 메모 비교"로 충돌을 막지만, 챔피언은 경기 버전을 올린다. 명단 표에는 data_version 트리거가 없어서(0021) matches 행을 건드리지 않으면 조회 링크의 ETag가 그대로라 고친 챔피언이 304 뒤에 숨는다. 그 대신 다른 기기에서 열어 둔 정정 창이 한 번 충돌로 막힌다. 보낸 값이 그 경기 챔피언 전체가 되고(빠진 사람은 지움), 변경 이력에는 남기지 않는다. 확정 경기만 고칠 수 있다.

고르기 칸(`src/web/championPicker.tsx`)은 combobox 패턴이다. 한글 이름·초성(ㅇㄹ → 아리)·영문 키·별칭(미포, 트페 등)으로 찾고 띄어쓰기는 무시한다. 한글 입력기는 "아리"를 치는 도중 "알"을 보여 주므로, 마지막 글자의 받침을 다음 글자 초성으로 본 검색어도 함께 찾아 목록이 깜빡이지 않게 했다. 순서는 앞부분 일치 → 중간 일치 → 그 사람이 예전에 자주 쓴 순 → 가나다이고, 칸이 비어 있으면 자주 쓴 챔피언이 맨 앞에 "3판"처럼 붙어 나온다. 같은 경기에서 다른 사람이 고른 챔피언은 보조 글자색과 "다른 사람이 고름"으로 맨 뒤에 둔다. 고르면 다음 사람 칸으로 초점이 넘어가 키보드를 닫지 않고 이어서 고른다. 목록은 떠 있는 상자 대신 칸 바로 밑에 끼워 넣었고, 폰에서는 칸을 창 위쪽으로 올려 키보드에 가리지 않게 했다(390px 다크·라이트 캡처로 확인). Esc는 목록만 닫고 결과 창은 남긴다.

챔피언 목록은 결과 입력 창에서 영역을 펼칠 때 따로 받는다(`lazyScreens.ts`의 `ChampionFields`). 첫 화면·오늘 화면 묶음에는 들어가지 않는다. 경기 상세(`Records.tsx`의 `MatchDetail`)는 팀 판의 이름 밑에 챔피언 이름을 적고, 운영자에게 "챔피언: 10명 중 N명 [기록/수정]" 줄을 둔다. 조회 링크 응답·백업에는 메모처럼 공개 정보로 들어간다. 백업 형식 번호는 올리지 않았고 챔피언 항목이 없는 예전 백업도 복원된다. 사람 합치기·되돌리기는 명단 행의 참가자 ID만 바꾸므로 챔피언이 따라간다. 결과 뒤 참가자 교체(정정)도 같은 이유로 챔피언이 그 자리의 새 사람에게 넘어간다.

CSV 내보내기에는 넣지 않았다. 경기 열이 테스트(`csv.test.ts`, `e2e/search-csv.spec.ts`)로 고정돼 있어 열을 늘리면 이미 받은 파일과 모양이 달라진다. 챔피언별 승률·랭킹 반영도 하지 않았다.

검증: `npm run typecheck`·`npm run lint`(오류 0) 통과, `npm test` 68개 파일 998개 통과(새 `champions.test.ts` 17: 검색 6, 결과 입력 2, 상세 수정 7, 백업·합치기 2), `npm run build`·`npm run check:bundle` 통과(첫 화면 325.6KB, 챔피언 목록은 `championPicker` 조각에만). e2e는 새 `champions.spec.ts` 2개와 `records`·`site`·`restore-privacy`·`merge-delete`·`memo-series-season` 22개를 돌려 모두 통과. 운영 배포 때는 0025를 먼저 적용해야 한다(새 코드가 이 열을 읽는다, 배포안내 7절).

찜찜한 점: 챔피언 목록이 코드에 박혀 있어 새 챔피언이 나오면 배포해야 고를 수 있다. 결과 입력 창에서 영역을 처음 펼칠 때 목록 조각을 받느라 "불러오는 중…"이 잠깐 보일 수 있다.

### 차콜 테마 (2026-11-10)

사용자가 한 전적 사이트의 분위기를 기준으로 삼되 저작권·상표 문제가 없게 다크 테마를 바꿔 달라고 했다. 그 사이트는 열어 보지 않았고, 디자인 시안(CharcoalHome·CharcoalRank)의 값만 썼다. 따른 것은 이 장르에서 흔한 관습(무채색 어두운 바탕, 한 단계 밝은 상단 바, 채운 활성 탭, 머리 줄이 있는 표)뿐이고, 그 사이트의 로고·아이콘·문구·코드와 대표 색 조합(차콜 + 민트)은 가져오지 않았다. 포인트는 원래 골드(#e3b04b)를 그대로 둬 우리 사이트 쪽 정체성으로 남겼고, 화면 배치도 바꾸지 않았다.

다크 토큰은 바탕 #16171a, 카드 #1e1f23, 올린 면 #26272c, 상단 바 #202125(새 토큰 `--ih-bg-bar`), 글자 #eceef1 · 보조 #a4a8b0, 테두리는 흰색 8%·18%로 바꿨다. 이전 "기록지"의 따뜻한 미색이 들어 있던 값(은메달 색, 승률 0·낮은 쪽 글자)만 같은 밝기의 무채색으로 옮겼고, 승패·라인·승률 단계·칭호 색은 대비 검사가 그대로 통과해 손대지 않았다. 모서리는 `--ih-radius-md`·`lg`를 8·10px → 6px로 맞췄다.

구조는 공통 규칙에서만 바꿨다. 상단 바·하단 탭·조회 메뉴 줄은 `--ih-bg-bar`로 채우고, 지금 화면 탭은 운영자 탭·조회 메뉴, 좁은 화면 하단·넓은 화면 상단 모두 채운 버튼 색(`--ih-brand-fill`)으로 채운 칸이 됐다. 그래서 다크는 골드, 바이올렛은 보라, 라이트는 잉크색 칸이다. 좁은 화면 하단 탭은 위아래 6px를 띄워 칸이 44px다. 조회 메뉴 링크는 금색 밑줄 링크 대신 탭 모양이다. 표 머리(`.matrix`·`.cmp-table`·`.privacy-table`·`.restore-diff`), 요약 전광판 머리 줄, MMR 순위표의 눈금 줄과 묶음 소제목은 올린 면으로 채웠다.

바이올렛 테마는 dark를 물려받는 구조 그대로이고, 상단 바 색 하나만 더했다. 글자가 무채색이 된 것 말고는 대비가 깨진 곳이 없었다. 코드 안 식별자 `deeplol`은 남의 서비스 이름이라 `violet`으로 바꿨다. 이미 `naejeon.theme`에 옛 값을 저장한 기기는 `theme.ts`의 `readTheme`가 읽을 때 `violet`으로 옮겨 적는다.

찜찜한 점: 라이트 테마는 상단 바가 흰 면이 됐을 뿐 바탕 색은 그대로다. 표 머리를 칠하지 않은 다른 작은 표(`.sheet-table`은 원래 칠해져 있음)가 남아 있을 수 있다.

### 화면 틀 통일 (2026-11-10)

차콜 테마로 색만 바꾼 뒤 "바뀐 게 없다"는 반응이 와서, 이번에는 뼈대를 맞췄다. 기준으로 삼은 것은 전적 사이트들이 공통으로 쓰는 구조 관습뿐이다: 화면마다 같은 가운데 폭, 큰 제목과 한 줄 설명, 그 아래 한 줄 필터, 요약 카드 줄, 머리 줄이 있는 정렬 표. 특정 사이트의 로고·아이콘·문구·색 값과 화면 배치는 가져오지 않았고, 우리 정보 구성(블루/레드, 시작값 기준 MMR, 배치 묶음)에 맞춰 짰다.

폭은 토큰 두 개로 정리했다. 읽는 화면(요약·검색·기록·랭킹·그래프 분석·개인 통계·비교·시즌 요약·운영자 오늘)은 `.screen.page-wide` 또는 `.screen.cols`로 `--page-wide`(1120px, 메뉴 줄과 같은 폭)를 쓰고, 나머지 양식 화면은 `--page-narrow`(760px)다. 전에는 요약·랭킹이 760px, 기록이 1120px, 오늘이 1040px이라 탭을 오가면 본문이 출렁였다. 준비·티어 배정은 손으로 조작하는 입력 흐름이라 1040px 그대로 두었다.

공용 부품은 `ui.tsx` 끝에 모았다. `ScreenHead`는 제목·한 줄 설명·오른쪽 동작 자리(운영자의 "지난 경기 입력" 같은 지금 할 입력이 여기 온다. 조회 화면은 비워 둔다), `FilterBar`는 붙은 구간 탭(`ScopePicker` 같은 `.segmented`)·고르기 상자·검색 칸을 한 줄에 둔다. `StatCard`는 제목·큰 수치·"라벨 … 값" 줄이고 `tone="lead"`면 포인트 색으로 채운다. 표는 두 가지다. 줄이 목록 항목이어야 하는 순위표(묶음 소제목·펼친 추이가 줄 사이에 끼고, e2e가 "줄 = listitem"에 기댄다)는 `SortHead` 머리 줄 + `.list-card` 줄을 같은 grid 칸 배치로 그리고 정렬 상태를 `aria-pressed`로 알린다. 새 화면은 진짜 `<table>`인 `DataTable`(머리 `aria-sort`, 정렬 버튼, 숫자 오른쪽 정렬, 좁은 화면에서 `wideOnly` 열 숨김)을 쓴다. `Glue`는 넓은 화면에서 크기 0으로 숨는 칸 사이 이음 글자라, 칸으로 나뉜 줄도 글자 내용·버튼 이름은 "70% · 7승 3패 (10경기)"처럼 예전 한 줄 그대로 읽힌다.

랭킹은 머리 → 이름 검색 필터 줄 → 요약 카드 줄(1위 · 최근 10경기 최고 상승 · 최고 MMR · 티어 분포) → 표(순위 · 이름·칭호 · 시작값 기준 막대 · MMR · 티어 · 최근 변동 · 경기 · 승률 · 최근 10경기 · 펼치기)가 됐다. 막대 눈금은 머리 줄 막대 칸에 들어갔다. MMR·최근 변동·경기·승률 머리를 누르면 정렬하는데, 묶음(누적 50경기 이상 → 배치 완료 → 배치 진행 중)은 그대로 두고 묶음 안에서만 다시 세운다. 몇 판 안 한 사람이 승률 100%로 맨 위에 오지 않게 하려는 것이고, 큰 값부터 하나만 둔 것도 같은 이유다. 누적 50경기 이상인 사람이 없는 새 모임은 1위 칸에 "배치 완료자 중" 1위를 경기 수와 함께 보여 준다. 확정 경기가 없으면 안내 칸에 운영자만 "이름 넣고 팀 짜기" 버튼이 있다. 태블릿(720~1023px)은 티어·최근 10경기 열을 빼고, 폰은 세 줄짜리 줄로 접는다.

기록은 머리(운영자는 오른쪽에 "지난 경기 입력", 설명 줄에 시즌 기간과 시즌 요약 링크) → 필터 줄 하나(범위·사람·이긴 진영) → 누적 띠 → PC 2단(왼쪽 5 경기 카드, 오른쪽 7 소환사 랭킹 표)이다. 고른 사람 칩과 그 사람의 라인·승패는 사람을 고른 뒤에만 생기므로 경기 목록 위에 남겼다. 소환사 랭킹은 정렬 탭 대신 승률·승수·경기 수·MMR 열 머리를 누른다. 순서 규칙(배치 완료 먼저 등)은 `rankAndSearch` 그대로다. 줄은 이름·최근 승패·연승 한 줄, 칭호(누적 기준) 한 줄로 두 줄이고, 폰에서는 셋째 줄에 "70% · 7승 3패 (10경기)"와 MMR이 온다.

요약(조회 링크·예시의 요약 탭, 운영자 오늘 아래쪽)은 PC에서 2단이다. 왼쪽 넓은 단에 전광판과 이전 경기, 오른쪽 좁은 단에 랭킹 상위 5명과 요즘 흐름. 이전 경기는 PC에서 한 경기 한 줄 표(경기 · 일시와 시리즈·이변 표시 · 결과 · 블루 다섯 · 레드 다섯)로 바꿨다. 줄을 누르면 경기 상세, 이름은 개인 통계다. 메모 열은 비어 있는 경기가 많아 두지 않았다. 폰은 표 대신 기존 경기 카드다(`useMediaQuery`로 둘 중 하나만 그린다).

나머지 화면(검색·그래프 분석·개인 통계·비교·시즌 요약·오늘)은 폭과 머리만 맞췄다. 개인 통계는 범위 고르기를 필터 줄에 넣었고, 그래프 분석의 도구 띠는 카드 테두리를 빼 다른 화면의 필터 줄과 같은 모양이 됐다. 오늘 화면의 "지금 할 일"(경기 시작·결과 입력 버튼)은 머리 바로 아래 그대로이고, 준비·진행·결과 입력 흐름은 손대지 않았다.

e2e는 네 곳을 고쳤다. 랭킹 요약 타일 수(`.ps-tiles > div` 3개 → `.stat-card` 4개와 "배치 완료자 중"), 랭킹 이름 검색 칸 위치(순위표 구역 → 위 필터 줄 "순위표 찾기"), 소환사 랭킹 MMR 정렬 버튼 이름("MMR 순" → 열 머리 "MMR"), 기록 거르기의 사람·이긴 진영 고르기를 경기 목록 구역이 아니라 화면에서 찾기(필터 줄로 옮겼다). 검사하는 내용은 그대로다.

찜찜한 점: 순위표 두 개는 진짜 표가 아니라 목록이라 화면 읽기 프로그램이 열 머리를 읽어 주지 않는다(정렬 상태는 버튼의 눌림으로 알린다). 경기 상세·모임 설정·가져오기 같은 좁은 화면은 머리 부품으로 옮기지 않았다.

## 챔피언 티어 · 챔피언 초상화 (2026-11-10)

운영자가 결과 입력·경기 상세에서 손으로 남기는 챔피언 기록(0025)을 모아 보는 "챔피언 티어" 화면을 더했다. 주소는 운영자 `#/champions`, 조회 링크 `#/v/토큰/champions`, 예시 모임 `#/demo/champions`이고 참가 중인 모임(`#/mine/모임/champions`)도 같은 화면을 쓴다. 전적 사이트의 챔피언 티어 화면에서 구조만 가져왔다. 왼쪽 좁은 패널은 초성 줄과 초성별로 묶은 초상화 격자(기록이 있는 챔피언만, 누르면 오른쪽 표에서 그 줄을 펼치고 그리로 내려간다), 오른쪽은 순위·챔피언·티어·승률·픽률·판·주로 쓴 사람 표다. 티어·승률·픽률·판 머리를 누르면 정렬하고, 같은 머리를 다시 누르면 방향이 바뀐다. 줄을 펼치면 사람별 전적(누르면 개인 통계), 라인 분포, 그 챔피언이 나온 최근 5경기(누르면 경기 상세)가 나온다. 표 위에는 범위(오늘·시즌·연도·전체), 라인(전체·탑·정글·미드·원딜·서폿), 챔피언 검색(고르기 창과 같은 초성·영문·별칭 검색)이 있다. 폰에서는 한 단이고 격자는 "챔피언 모아 보기"로 접어 두며, 주로 쓴 사람 열을 빼서 가로로 넘치지 않는다.

API 전적이 아니라 손 입력이라는 점을 두 군데에서 드러냈다. 화면 머리 오른쪽에 늘 "챔피언 기록 34 / 111경기"(범위 안 확정 경기 중 챔피언이 하나라도 있는 경기)를 두고, 운영자에게는 챔피언이 빠진 가장 최근 확정 경기로 가는 "빠진 경기 채우기 · N경기" 버튼을 준다(경기 상세가 열리고 거기서 "챔피언 기록"). 조회자에게는 숫자만 보인다. 기록이 하나도 없으면 표 대신 어떻게 채우는지 안내하고, 운영자에게만 "N경기 챔피언 기록하기"(경기도 없으면 "이름 넣고 팀 짜기") 버튼이 있다. 밴율·카운터는 기록하지 않는 값이라 넣지 않았고 그 자리에 "주로 쓴 사람"을 뒀다.

계산은 `src/shared/championTier.ts`의 순수 함수다(스냅숏으로 화면에서 계산, 새 API·DB 없음). 확정 경기 중 챔피언이 기록된 명단 칸만 센다. 픽률의 분모는 챔피언이 하나라도 기록된 경기 수이고, 라인을 고르면 그 라인에 챔피언이 기록된 경기 수다. 같은 경기 양 팀에 같은 챔피언이 적혔으면(손 입력이라 생길 수 있다) 판 수는 둘, 픽률의 경기 수는 하나로 센다. 라인 분포는 라인 필터와 상관없이 범위 안 전체를 보여 준다. 티어는 날것의 승률로 매기지 않는다. 승률에 50% 승률의 가상 경기 12판을 더해 50% 쪽으로 당긴 보정 승률(`TIER_PRIOR_GAMES`)에 픽률 × 0.1(`TIER_PICK_WEIGHT`)을 더한 점수를 쓰고, 점수 57%·53.5%·50%·45% 이상이 1~4티어, 그 아래가 5티어다(`TIER_CUTS`). 이 값이면 2판 2승(보정 57.1%)은 20판 13승(59.4%)보다 아래이고, 3판 3승은 1티어, 10판 5승은 3티어, 10판 3승은 5티어다. 3판 미만(`TIER_MIN_GAMES`)은 티어 없이 표 아래 "기록 부족" 묶음에 따로 둔다. 상수는 모두 이 파일 한곳에 근거와 함께 적었다. 줄 순서는 점수 → 판 수 → 한글 이름 순이라 기록 순서가 바뀌어도 같다. 티어 표시는 숫자가 든 24px 각진 칸이고 1티어만 포인트 색으로 채운다(기존 토큰만, 세 테마 공통).

챔피언 초상화는 라이엇이 공개하는 Data Dragon의 정사각형 그림(`https://ddragon.leagueoflegends.com/cdn/16.22.1/img/champion/<키>.png`)을 주소로 불러온다. 저장소에 그림 파일을 넣지 않았고 다른 사이트의 그림은 쓰지 않는다. 개발 때 `api/versions.json`(최신 16.22.1)과 그 버전의 `ko_KR/champion.json`으로 우리 목록 171개를 대조했더니 키가 모두 Data Dragon id와 같고(오공 MonkeyKing, 누누와 윌럼프 Nunu처럼 이름과 다른 것도 이미 id로 적혀 있었다) 한글 이름도 같아서 대응표는 두지 않았다. 빠져 있던 로크(Locke)·자헨(Zaahen)을 더해 173개가 됐다. 실행 중에는 이 JSON을 받지 않는다. 초상화는 챔피언 티어 화면(격자 44px, 표 32px), 챔피언 고르기 목록(28px), 경기 상세 명단(이름 옆 32px)에 나온다. `loading="lazy"`, `decoding="async"`, 가로세로를 적어 자리가 밀리지 않고 `alt=""`다(이름 글자가 늘 옆에 있다). 못 불러오면(오프라인, 새 챔피언) 그림 요소를 지워 글자만 남는다. 결과 이미지·명단 이미지 캔버스에는 넣지 않았다(다른 출처 그림을 그리면 내보내기가 막힌다).

라이엇 "Legal Jibber Jabber" 정책 조건에 맞췄다. 모든 화면 아래 고지에 정책이 요구하는 영어 문구("내전 운영 was created under Riot Games' "Legal Jibber Jabber" policy using assets owned by Riot Games. Riot Games does not endorse or sponsor this project.")를 원문 그대로 더했고, 한국어 문구는 "로고·상표는 쓰지 않고 챔피언 초상화는 라이엇 자산이며 위 정책에 따라 불러온다"로 사실에 맞게 고쳤다. 라이엇 로고·상표 그림은 쓰지 않는다. 끄는 곳은 `src/web/portraits.ts`의 `CHAMPION_PORTRAITS` 하나다. `false`로 바꾸면 사이트 전체가 예전처럼 글자만 보이고 고지문도 예전 문구로, 처리방침의 라이엇 줄도 빠진다. 허가가 철회되거나 유료화·광고·법인 운영으로 바뀌면 끈다(배포안내 10절에도 적었다). CSP `img-src`에 `https://ddragon.leagueoflegends.com`만 더했고(`public/_headers`·`src/server/http.ts`, 두 값이 같은지 `security.test.ts`가 본다), 개인정보 처리방침의 "다른 회사에 전달되는 것"에 방문자 브라우저가 라이엇 이미지 서버에 직접 접속한다는 줄을 더했다.

메뉴: 운영자 주 메뉴는 오늘 · 검색 · 기록 · 랭킹 · **챔피언** · 분석 · 모임이 됐다. 폰 하단 탭은 이미 6칸이라 7칸이면 글자가 칸을 넘쳐서, 720px 미만에서는 "챔피언"을 숨기고(`.nav-wide-only`) 랭킹 화면 머리 오른쪽의 "챔피언 티어 →" 링크로 가게 했다. 조회 링크 메뉴(현재 경기·요약·검색·기록·랭킹·챔피언, 6칸)와 예시 모임 메뉴(5칸)는 폰 하단에도 그대로 있고, 참가 중인 모임 메뉴는 "내 정보"까지 7칸이라 운영자와 같이 폰에서만 숨겼다. 메뉴 글자는 다른 탭과 길이를 맞춰 "챔피언"이고 화면 제목은 "챔피언 티어"다.

예시 모임(`src/shared/demo.ts`)에 챔피언을 채웠다. 승패를 만든 난수와 따로 굴려서 기존 예시 기록(순위·시즌 시상)은 바뀌지 않는다. 앞 25% 경기는 비우고(기록을 중간부터 시작한 모임) 그 뒤도 10%는 통째로, 칸마다 5%는 비워 입력률이 100%가 아니다(지금 75 / 111경기). 사람마다 라인별 즐겨 쓰는 챔피언 셋이 있다.

번들: 챔피언 티어 화면은 따로 조각(`ChampionTier-*.js`)이고 조회 링크·예시 모임도 이 조각을 지연 로딩한다. 첫 화면 JS가 상한 330KB를 넘지 않도록, 표 부품 `DataTable`을 `ui.tsx`에서 `src/web/dataTable.tsx`로 옮겼고(쓰는 화면이 요약·챔피언 티어뿐이라 첫 화면 묶음에 있을 이유가 없었다) 경기 상세의 초상화는 `MatchTeams`가 직접 부르지 않고 `championPortrait` prop으로 받는다. `DataTable`에는 펼친 줄(`expanded`)을 더했다.

## 경험 개선 첫 실험: 참가자 편성 화면 개인화(B-1) · 직전 편성 대비 한 줄(A 축소형) · 결함 수정 (2026-11-10)

설계는 `docs/개선-경험-설계-2026-11-10.md`다. 두 기능 모두 관찰로 가릴 실험으로 넣었고, 폐기 조건을 먼저 정해 두었다(설계 5절). 서버·API·DB는 바꾸지 않았다.

참가자 편성 화면(`#/v/토큰/live`)에서 이름을 바로 고를 수 있게 했다. 이름을 안 골랐으면 명단 줄이 버튼(높이 44px 이상)이 되고, 맨 위 "내 자리" 칸에 "아래 명단에서 내 이름을 누르면 내 자리를 먼저 보여드려요. 이 기기에서만 쓰는 표시이고 로그인이 아니에요."를 둔다. 고르면 그 칸이 팀·라인·이름(글자 "나")·같은 팀 네 명(라인 순)·맞라인으로 바뀌고, 명단의 내 줄에도 색 띠와 함께 글자 "나"가 붙는다. 저장은 지금까지 쓰던 `naejeon.me.<토큰>` 하나뿐이고 어떤 요청에도 싣지 않는다. 합치기로 사라진 이름을 골라 두었으면 남은 이름으로 본다(F3). 열어 둔 동안 같은 경기에서 사람이 바뀌면 "바뀐 자리: 레드 정글 밤송이 → 호두알" 한 줄과 들어온 사람 줄에 "바뀜" 꼬리표를, 새 경기가 시작되면 "3경기 편성이 올라왔어요."를 쓴다. 경기가 없을 때는 기존 문구 "지금 진행 중인 경기가 없어요."를 두고, 열린 내전이면 "다음 경기는 운영자가 시작하면 여기에 떠요."를 덧붙이며, 내 자리 칸에는 최근 경기의 내 결과("2경기 블루팀 승 · 내 팀 승리")와 그 내전 성적("11월 10일 내전 2승 1패(확정 3경기, 결과 안 들어온 1경기 제외)")을 쓴다.

자동 확인은 고정 30초를 버리고 상태별 간격으로 바꿨다(`src/shared/liveView.ts`의 `nextPollDelay`). 대기 15초(10분 조용하면 30초, 60분이면 멈춤), 경기 중 60초, 열린 내전 없음 120초(30분이면 멈춤), 실패하면 두 배씩 최대 5분이고 연속 5번이면 멈춘다. 429는 응답의 `retryAfter`보다 일찍 보내지 않는다. 모든 간격에 ±20% 흩뜨림을 준다. 화면이 숨으면 타이머를 지우고, 다시 보이거나 온라인이 되면 한 번 확인한다. 끊기면 머리 표시가 "진행 중 · 시작"에서 "21:42 기준"으로 바뀌고 아래 줄이 "연결이 끊겼어요. 21:40 내용이에요." → "자동 확인을 멈췄어요."로 바뀐다. "지금 확인"이 언제나 있다(F2). 링크가 폐기돼 404가 오면 명단을 지우고 폐기 안내만 남긴 채 다시 요청하지 않는다(F1). 모임 화면 조회 링크 구역에 "참가자 편성 링크 복사"를 두어 경기 전에 미리 보낼 수 있고(F4), 진행 중 화면의 보내기 창에 "한 번 보내 두면 다음 경기도 같은 링크예요."를 더했다. 명단은 `ui.tsx`의 `MatchTeams`를 키우지 않으려고 같은 모양의 작은 부품을 `ViewerLive.tsx` 안에 따로 두었다. B-1의 폐기 조건은 참가자 다섯 명 중 둘 이상이 10초 안에 자기 팀·라인을 말하지 못하거나 남의 이름을 고르고도 모르는 경우(요약을 빼고 이름 고르기만 남김), 내전 두 번 뒤에도 운영자가 매 경기 명단 글을 다시 붙이는 경우(전체를 되돌림), 내전한 날 `#/admin`의 `view-ip` 한도 걸림이 0이 아닌 경우(자동 확인을 끔)다. 되돌릴 때는 `ViewerLive.tsx`와 `liveView.ts`만 이전으로 돌리면 된다.

준비 화면 편성 판 바로 아래에 "직전 편성 대비" 한 줄을 넣었다(`src/shared/prepDelta.ts`, `prep/DeltaNote.tsx`). 되돌리기 이력의 직전 자리와 지금 자리를 같은 입력으로 평가해 달라진 것만 쓴다. 순서는 어긴 팀 조건 → 기피 라인에 선 사람 → 시작 때 확인할 서포터 → 옮겨져 풀린 고정 → 최근 N경기 같은 팀 반복 → 예상 블루 %(MMR 추정)이고, 앞의 넷 중 늘어난 것이 있으면 줄 전체가 경고 톤이고 그 항목이 맨 앞이다. "좋아졌어요" 같은 평가 낱말은 쓰지 않는다. 직전 편성이 없거나(처음, 사람 교체 뒤), 되돌린 직후이거나, 달라진 값이 없으면 줄을 그리지 않는다. 예상은 양쪽 다 신뢰할 수 있을 때만, 반복은 센 경기가 있을 때만 나온다. 옆의 "방금 변경 되돌리기"는 "직전 편성으로"와 같은 동작인데, e2e가 "직전 편성으로" 버튼 개수로 단계를 세서 이름을 달리 두었다. 티어 점수 차는 이 줄에 넣지 않고 예상 승률 판의 접힌 "티어 점수 보기" 안에 "직전 편성 대비 티어 점수 차(블루 − 레드) 2 → 0"으로만 쓴다. 같은 식을 쓰도록 `forecast.ts`에서 팀 평균·예상을 `teamExpectation`으로, `recommend.ts`에서 반복 쌍 합을 `repeatPairsOf`로 떼어 냈다(숫자는 그대로). 폐기 조건은 운영자 세 명 관찰에서 아무도 그 줄을 읽지 않거나, 한 명이라도 예상 숫자를 실제 효과로 말하거나(예상 항목부터 뺀다), 줄 때문에 섞기 버튼을 못 찾거나 스크롤이 늘었다는 반응이다.

결함 수정. 그래프 분석 코멘트의 과장 문구를 사실 서술로 바꿨다(F5). "섞기가 공정해요"·"MMR이 실력을 잘 반영하고 있어요"는 "판정 12경기 중 8경기가 예상 45~55%였어요(균형 경기 67%). 예상 우세 팀이 12경기 중 7경기 이겼어요(58%)."로, "강팀일 때 방심하는 편이에요"는 "예상 승률 60% 넘는 강팀으로 진 경기가 4회로, 약팀으로 이긴 1회보다 많아요."로, "이변이 많은 편이에요 … 실력 차가 좁다는 뜻이에요"는 "판정 20경기 중 5경기가 이변이었어요(25%)."로, 총평 "공정한 섞기 + 안정된 MMR"은 "균형 경기 67% · 예상 우세 팀 승률 58%"로 바꿨다. 섞기 공정성 머리의 판정 글도 "섞기가 공정했어요" 대신 "균형 경기 60% 이상"처럼 구간 숫자로 쓴다. 문장마다의 근거(`Remark.basis`)는 title 풍선 대신 문장 아래 작은 글씨("기준: …")로 보인다. 경기 상세의 "경기 전 예상" 줄 끝에 "지금 기록과 설정으로 다시 계산한 값"을 붙였다(F6). title에만 있던 판단 기준 넷을 터치 화면에서도 읽을 수 있게 했다(X2): 코멘트 근거(위), 준비 화면 라인 우위의 줄별 계산(예상 승률 판의 접힌 "라인별 계산 보기"), 이변 배지 기준(경기 상세의 접힌 "이변 기준"), 섞기 버튼 설명 열한 개(섞기 구역 맨 아래 접힌 "버튼 설명" 하나에 모음, 버튼 title과 같은 상수를 쓴다). "앞부분 경기만 넣어 계산한 경기 전 예상이 전체 기록으로 계산한 값과 같다"는 속성 테스트를 `test/upset.test.ts`에 더했다(시드 셋 × 40경기, 결과 대기·제외·취소 섞음).

챔피언 티어 보정을 고쳤다. 가상 12판으로 당겨도 3판 3승(0.60)이 1티어 경계(0.57)를 넘었다. 가상 판 수를 늘리면 점수가 모두 50% 쪽으로 몰려 경계를 다시 잡아야 해서, 대신 1티어에 최소 판 수 10(`TIER_TOP_MIN_GAMES`)을 두어 그보다 적으면 점수가 높아도 2티어로 둔다. 기본 정렬은 티어 → 점수 순이 되어 2티어로 내린 챔피언이 1티어 사이에 끼지 않는다. 2판 2승 < 20판 13승, 10판 5승 3티어, 10판 3승 5티어는 그대로다. 예시 모임의 티어 분포는 1~5티어 12·16·6·13·12개에서 8·20·6·13·12개로 바뀌었다(9판 7승, 4판 4승, 3판 3승, 9판 6승이 2티어로).

검증: `npm run typecheck`·`npm run lint`(오류 0)·`npm run build`·`npm run check:bundle` 통과, `npm test` 71개 파일 1048개 중 1047개 통과(새 `test/live-view.test.ts` 17·`test/prep-delta.test.ts` 15, `champion-tier.test.ts`·`commentary.test.ts`·`upset.test.ts` 추가분 포함. 남은 1개는 손대지 않은 `draft-fuzz.test.ts`의 큰 무작위 점검이 병렬 실행 중 30초 제한을 넘긴 것으로, 혼자 돌리면 21초에 통과한다). e2e는 113개에 새 `e2e/live-roster.spec.ts` 8개와 `e2e/prep-walkthrough.spec.ts`의 직전 편성 대비 1개를 더해 122개다. 전체 실행에서 시계를 앞당기는 두 개가 한 번 실패했는데, 간격보다 멀리 앞당기면 그 사이 나간 요청의 15초 제한 시간까지 가짜 시계로 지나가 끊긴 것으로 잡혔기 때문이라 테스트에서 흩뜨림을 없애고 간격만큼만 앞당기게 고쳤다(그 뒤 그 파일을 세 번 반복해 24/24 통과). 첫 화면 JS는 328.9KB로 그대로이고(새 코드는 ViewerLive·Prep·Graphs 조각 안), 참가자 편성 화면이 받는 양은 332.0KB에서 339.6KB가 됐다. 찜찜한 점: 설계 7절의 "오늘 기록 보기" 링크는 메뉴의 "기록 보기"와 이름이 겹쳐 넣지 않았다. 카카오톡·디스코드 인앱 브라우저에서 "내 이름"이 남는지와 타이머가 도는지는 실기기로 보지 못했다.

## 오늘 명단 이어가기 · 팀 조건 이어받기 · 참가자 상한 결함 수정 (2026-11-10)

설계는 `docs/개선-오늘명단-설계-2026-11-10.md`다. 서버 API·스키마는 바꾸지 않았고(참가자 상한 검사만 고침) 마이그레이션도 없다.

11명 이상 온 밤에 "그날 온 사람과 그 순서"를 기기에 남기는 것을 실험으로 넣었다. 고르기 화면에서 대기자가 생기게 팀을 짜면 `naejeon.night.v1.<모임>`에 명단을 쓰고, 첫 경기 시작에 성공하면 그 경기의 세션에 묶는다(`src/web/nightPoolStore.ts`). 판 수·연속 기록은 저장하지 않고 그 세션의 서버 경기에서 그때그때 센다(`src/shared/nightPool.ts`). 미진행 취소는 빼고 결과 대기·진행 중·전적 제외는 뛴 판으로 센다. 결과 저장 창에 "다음 판 쉬는 사람(제안): 도토리 · 밤송이" 한 줄이 나오고, "다음 경기 준비"는 쉬던 사람이 나간 사람의 팀·포지션을 물려받은 초안을 만든다. 규칙은 하나다: 쉬던 사람은 모두 들어오고, 빠지는 사람은 연속으로 가장 오래 뛴 사람 → 오늘 경기가 많은 사람 → 명단 앞쪽 순. 무작위가 없어 어느 기기에서나 같은 제안이다. 준비 화면 안내 줄이 "2경기 · 오늘 온 12명 중 10명이에요. 쉬던 꿀떡·모래알이 도토리(레드 서폿)·밤송이(블루 미드) 자리에 들어갔어요."로 바뀌고 "같은 10명으로"·"팀 다시 짜기"가 붙는다(사람이 바뀐 초안에는 "포지션 유지"가 없다). 예전 대기자 구역은 "쉬는 사람"이 되어 오른쪽 도구 단에서 편성 판·직전 대비 줄 바로 아래로 옮겼다. 줄마다 오늘 판 수·연속 판 수와 [빼기](바로 아래 되돌리기), [+ 늦게 온 사람], 접힌 "쉬는 순서 정하는 법" 안에 규칙 설명과 "오늘 명단 글 복사"가 있다. 시리즈로 이어갈 때는 사람을 바꾸지 않고 쉬는 사람만 붙이고, 정확히 10명인 밤은 명단을 남기지 않아 화면과 초안이 예전과 같다. 쉬는 사람은 명단 글·편성 이미지·조회 링크·참가자 화면에 나가지 않는다.

같이 넣은 작은 개선: 시작에 성공하면 그 편성의 팀 조건을 `naejeon.constraints.v1.<모임>`에 남기고(새 이름의 조건 키는 생긴 참가자 키로 바꿔서), "다음 경기 준비"가 12시간 안의 값 중 두 사람이 모두 새 초안에 있는 조건만 넣는다. 안내 줄 끝에 "지난 경기의 팀 조건 1개를 이어 왔어요."가 붙고 조건 구역에서 지울 수 있다. 쉬러 빠진 사람의 조건은 지워진다.

설계와 다르게 한 것. 세션에 묶인 명단도 세션의 마지막 활동에서 12시간이 지나면 지난 밤으로 본다. "오늘 내전 마치기"를 안 누르면 세션이 다음 주까지 열려 있어서, 이 조건이 없으면 지난주 명단이 고르기 화면을 채운다. 빼기로 뺀 사람은 명단에 `left`로 남긴다. 그날 뛴 사람이라 서버 경기에서 다른 기기의 사람을 찾아 더하는 동기화가 곧바로 되살렸기 때문이다. "오늘 온 사람이 9명이에요" 경고는 넣지 않았다. 빼기는 쉬는 사람에게만 있어 명단이 편성 10명보다 작아지는 경로가 없다. 초안 형식 파일(`src/shared/draft.ts`)은 첫 화면 묶음이라 고치지 않고, 안내 줄에 쓸 값(들어간 사람과 자리, 명단 수, 다른 기기에서 더한 이름, 이어 온 조건 수)을 초안의 선택 필드 `night`로 얹었다(`NightDraft`). 로그인 전(모임이 없을 때) 짠 팀은 명단을 남기지 않는다.

중단 조건(설계 ⑦). 11명 이상 모이는 밤 두 번을 관찰해 제안을 절반 넘게 손으로 뒤집으면 규칙(`nextLineup`)을 빼고 명단 이어가기만 남긴다. 지난주 명단이 잘못 뜬 일이 한 번이라도 있으면 오래된 명단 규칙을 더 좁힌다. 두 밤 모두 10명이면 더 손대지 않는다. 이어 온 조건을 운영자가 매번 지우면 작은 개선을 되돌린다. 되돌릴 때는 위 새 파일과 `Pick.tsx`·`Match.tsx`·`Prep.tsx`·`prep/*`만 이전으로 돌리면 된다(서버 데이터 없음).

참가자 상한 결함(R1)도 고쳤다. 이름 추가가 "지금 수 ≥ 200"만 보고 한 번에 30명을 넣어 229명까지 갈 수 있었고, 그런 모임의 백업은 복원이 200명 초과로 거절했다. 이제 지금 수에 실제로 새로 생길 행 수(이미 활성 참가자인 이름은 빼고, 보관된 같은 이름은 새 행이라 셈)를 더해 검사하고, 상한은 `src/server/groups.ts`의 `MAX_PARTICIPANTS_PER_GROUP` 하나를 복원도 쓴다. 참가자 행을 만드는 경로는 이 하나뿐이었다(참가 신청 불러오기·가져오기·시트 가져오기는 화면이 이 경로를 부르고, 합치기 되돌리기는 상태만 바꾼다).

검증: `npm run typecheck`·`npm run lint`(오류 0, 경고 34 그대로)·`npm run build`·`npm run check:bundle`(첫 화면 329.0KB) 통과. `npm test`에 `test/night-pool.test.ts` 12개(설계 ①~⑨, 뺀 사람 되살리지 않음, 조건 이어받기 3)와 `test/participant-limit.test.ts` 3개(199명 + 2명 거절, 199명 + 1명 성공·기존 이름은 200명이어도 돌려줌, 200명 모임 백업 복원 성공)를 더했다. e2e는 새 `e2e/night-pool.spec.ts` 2개(12명 흐름, 10명 밤과 조건 이어받기)를 더했고, `prep-walkthrough.spec.ts`의 대기자 구역 이름·제목을 새 이름으로 바꿨다(검사 내용은 그대로). 단위 테스트는 73개 파일 1064개, e2e는 전체 124개가 통과했다. 390px 세 테마와 1440px 다크로 저장 창의 제안 줄, 회전한 준비 화면, 빼기 뒤 되돌리기, 늦게 온 사람, 10명 밤의 조건 이어받기를 캡처해 봤다.


커밋 전 리뷰에서 다섯 건이 나와 고쳤다. 밤 중간에 다시 고르면(2명 귀가·3명 합류, 또는 12명 중 2명 귀가) 그 세션에서 이미 뛰고 간 사람을 동기화가 "다른 기기에서 넣은 사람"으로 보고 되살려 다음 판에 넣던 것은, 명단을 새로 만들 때 그 세션에서 뛰었는데 새 명단에 없는 사람을 `left`에 넣어 막았다(`goneFromSession`; 명단을 만든 뒤 다른 기기가 시작한 경기의 새 얼굴은 그대로 더한다). 이름 추가의 인원 확인이 batch 밖이라 두 기기가 동시에 넣으면 상한을 넘던 것은 같은 계산을 batch 맨 앞 보호 문장(`guard.state_conflict`, 새 마이그레이션 없음)으로 다시 해 409 `TOO_MANY_PARTICIPANTS`로 막고, 직전 경기에 뛰고 명단에서 뺀 사람이 쉬는 사람으로 뽑히지 않던 것은 쉬는 순서 맨 앞에 두었다. 기기 보관값의 `left`가 문자열 목록이 아니면 화면이 멈추던 것은 읽을 때 그 명단을 버리게 했고(`parseNightPool`), `check:bundle`은 첫 화면의 우리 코드 JS에 소스맵이 없으면 허용 목록 검사를 못 하므로 조용히 넘기지 않고 실패한다(`.map`을 잠시 옮겨 실패하는 것을 확인). 테스트는 `night-pool` 6개(재현 두 가지, 다른 기기 교체, 세션 조건, 뺀 사람 먼저 쉼, 깨진 보관값)와 `participant-limit` 1개(확인 뒤 batch 전에 다른 기기가 5명을 채운 상황)를 더했다.

## 첫 화면 JS 경계 정리 · brotli 예산 · 껍데기 허용 목록 · 주소 기반 미리 받기 (2026-11-10)

첫 화면 JS가 상한(압축 전 330KB)에 329.0KB로 붙어 있었다. 번들러는 파일 단위로 나누는데, 진입 쪽이 `ui.tsx`의 34개 내보내기 중 대화 상자·오류 문구·복사 버튼·키보드 감지 넷만 쓰면서 나머지 화면 부품과 그것들이 부르는 통계·칭호·MMR·날짜 형식 계산까지 통째로 첫 화면에 싣고 있었다. 로그인 창(`screens/Login.tsx`)도 App·상단 바·오류 문구가 정적으로 불러 첫 화면에 있었고, `useApp.ts`는 저장된 초안 하나를 읽으려고 편성 조작 전체(`draft.ts`)와 팀 추천(`recommend.ts`), 합치기 미리보기의 칭호 계산(`merge.ts` → `titles.ts`)을 끌고 왔다. 상한을 올리거나 번들러 설정으로 나누지 않고 파일 경계를 고쳤다. 기능·문구·서버 API는 그대로다.

`ui.tsx`는 껍데기 부품 다섯(Dialog·ErrorNote·CopyButton·useKeyboardOpen·useKeyboardFlag)만 남기고 나머지 서른 개를 `src/web/screenKit.tsx`로 옮겼다. 쓰던 화면 53개 파일의 import를 둘로 나눴다. `format.ts`의 `copyText`는 쓰는 곳이 복사 버튼뿐이라 `ui.tsx` 안으로 들였다. 지나온 화면 기록(`nav.ts`)은 첫 주소부터 hashchange를 지켜봐야 해서 `main.tsx`가 직접 부르게 했다. 예전에는 `ui.tsx`의 "← 뒤로"가 불러서 우연히 첫 화면에 있었는데, 화면 부품과 함께 옮겼더니 검색 → 개인 통계에서 "← 뒤로"가 사라지는 것을 e2e(`scenarios.spec.ts` 화면 이동)가 잡았다. 로그인 창과 로그인 실패 안내는 `lazyScreens.ts`의 지연 로딩(`LoginDialog`·`LoginFailed`)으로 바꾸고, 상단 바·로그인 안내·오류 문구 안에서 열 때는 `Suspense`로 감쌌다. 로그인 버튼에 포인터가 올라가거나 초점이 가면 운영 묶음 미리 받기와 같은 방식(`preload(...).catch`)으로 조각을 미리 받는다(`prefetchLogin`). 오류 문구 안의 "다시 로그인"은 작은 파일 `sessionExpiredNote.tsx`로, 모임 탭의 비밀번호 바꾸기·복구 코드는 `localAccountSettings.tsx`로 떼어 냈다. 역할 이름 `ROLE_LABEL`은 상단 바가 쓰므로 `groupSwitcher.tsx`에서 `account.tsx`로 옮겼다. 공용 계산은 서버와 함께 쓰는 구조를 그대로 두고, 저장값 읽기(`parseStoredDraft`와 그것이 쓰는 형식 번호·이력 길이·예전 진영 맞추기)를 `src/shared/storedDraft.ts`로, 합치기 전후 칭호 비교(`mergeStandings`·`mergedMatches`)를 `src/shared/mergeStandings.ts`로 떼어 냈다. 서버 `merge.ts`와 테스트 일곱 파일의 import를 함께 고쳤다.

결과: 첫 화면 우리 코드(React·런타임 제외)는 압축 전 110.0KB → 46.9KB, brotli 30.8KB → 15.1KB(주소 미리 받기 파일 1.9KB/0.8KB 포함). 첫 화면 전체(JS + CSS) brotli는 108.9KB → 93.2KB다. 빠진 코드는 화면 조각 쪽으로 갔다: 운영자 묶음(`operator-*.js`)이 183.8KB → 196.8KB, 화면 부품 조각 `screenKit-*.js` 26.4KB, 로그인 조각 `Login-*.js` 12.1KB가 새로 생겼다. 화면마다 받는 JS 총량(첫 화면 + 그 화면)은 `#/` 397.5 → 388.5KB, 조회 링크 556.8 → 535.9KB, 예시 모임 558.9 → 538.0KB로 조금씩 줄었다.

`check:bundle`은 예산을 brotli 기준 둘로 바꿨다. 첫 화면 우리 코드 17KB(정리 뒤 15.1KB, 화면 부품 하나를 잘못 붙이면 2~5KB씩 늘어 여유를 13%쯤만 둠), 첫 화면 전체 97KB(정리 뒤 93.2KB, 약 4%). 가장 큰 JS 한 파일 250KB(압축 전)는 그대로 두었다. 압축 전 크기는 참고로, 화면별 크기는 압축 전과 brotli를 함께 출력한다. 예산이나 허용 목록에 걸리면 첫 화면 파일의 소스맵 mappings를 직접 풀어 원본 파일별 크기 상위 15개를 출력한다. 첫 화면에 들어가도 되는 원본 파일 목록은 `scripts/shell-modules.mjs`에 이유와 함께 두었고(넣는 기준을 파일 머리에 적음), 소스맵에서 뽑은 첫 화면 원본이 목록 밖이면 실패하면서 "main.tsx → App.tsx → screenKit.tsx → shared/rating.ts → shared/insights.ts"처럼 들어온 import 경로를 이름과 크기와 함께 보여 준다. 일부러 깨 봤다: `App.tsx`의 없는 주소 화면에 `screenKit`의 `RatingTierBadge`를 하나 넣으니 우리 코드 26.8KB·전체 104.9KB로 두 예산과 허용 목록이 함께 실패했고, 밖에서 들어온 11개 모듈(screenKit 14.7KB, insights 5.9KB, stats 5.5KB …)과 경로, 상위 15개 목록이 나왔다. 되돌린 뒤 통과한다.

주소 기반 미리 받기를 넣었다(`scripts/route-preload-plugin.mjs`, vite 설정의 `routePreload()`). 빌드의 generateBundle에서 조회 링크(`#/v/토큰`, `#/v/토큰/live`)·참가 신청(`#/join/…`)·예시 모임(`#/demo…`)의 화면 조각과 그 정적 import 중 첫 화면에 없는 것을 모아 대응표를 만들고, `/assets/route-preload-<해시>.js`로 내보내 index.html의 진입 스크립트 바로 앞에 `<script type="module" src>`로 단다. 보안 정책 `script-src 'self'`는 그대로이고 인라인 스크립트는 없다. 그 파일이 `location.hash`를 App.tsx와 같은 규칙으로 읽어 `<link rel="modulepreload" crossorigin>`을 붙이므로, React를 받는 동안 화면 조각도 함께 받는다. 파일이 없거나 대응이 틀려도 화면은 지연 로딩으로 평소처럼 뜬다. 화면 모듈을 못 찾으면 빌드를 멈추고, 대응표의 파일이 빌드 결과에 있는지는 `check:bundle`이 다시 본다. 이 파일도 첫 화면 예산에 센다. `#/`(오늘 화면)도 넣어 봤는데 측정에서 화면 조각 표시가 2.3초에서 2.8초로 오히려 늦어져(여러 번 같은 경향) 뺐다. 왜 늦어지는지는 끝까지 밝히지 못했다. 파일은 1.6초 안에 다 받았는데 그리는 시점이 늦었으므로 4배 감속한 CPU에서 미리 받은 13개 모듈의 처리와 React 시작이 겹친 것으로 짐작한다.

확인: 새 빌드를 따로 띄운 로컬 서버(wrangler dev, `_headers`를 적용해 CSP 헤더가 붙는 것을 응답에서 확인)에서 `#/v/토큰`·`#/v/토큰/live`·`#/demo`·`#/join/…`로 들어가면 각각 Viewer·ViewerLive·Demo·Join 조각에 modulepreload가 붙고 콘솔에 CSP 위반이 없었다(참가 신청은 없는 토큰이라 API 404 한 줄만). `#/`에서 로그인 버튼에 포인터를 올리면 Login 조각을 받고, 누르면 로그인 창이 열린다.

## 배포 전 보안 감사 후속 (2026-11-10)

배포 전 보안 감사에서 나온 지적 여섯 가지를 고쳤다. 마이그레이션·새 의존성은 없다.

요청 수 제한(`src/server/ratelimit.ts`)은 한도에 걸린 요청까지 카운터를 올리고 걸린 횟수를 더해, 로그인 없는 사람 하나가 한 IP에서 계속 보내기만 해도 D1 하루 쓰기 한도를 다 쓸 수 있었다. UPSERT의 `DO UPDATE`에 `WHERE rate_limits.count <= limit`을 걸어 카운트가 limit + 1에서 멈추게 했다. 처음 넘는 요청만 쓰고 걸린 횟수를 한 번 더하며, 그 뒤 같은 창의 요청은 쓰기 없이 429다. 그래서 사이트 현황의 "한도 걸림"은 걸린 요청 수가 아니라 (버킷 키, 창)마다 1이 됐고, 화면에 그렇게 적었다. 다른 Worker가 fetch로 보낸 요청은 같은 zone이면 CF-Connecting-IP를 Worker 코드가 바꿀 수 있어서, `CF-Worker` 헤더가 있으면 IP 대신 `worker:<zone>` 하나로 센다. 이 헤더를 Worker 코드가 뺄 수 없다는 것은 문서에 없어 staging에서 확인한다(`docs/배포안내.md` 8-1절 3번).

오류 기록(`src/server/errorLog.ts`)의 1000건 한도를 출처마다 따로 세게 했다. 합쳐 세면 로그인 없이 보내는 화면 오류로 서버 오류 기록을 밀어낼 수 있었다. 운영(`wrangler.jsonc` env.production)은 실행 기록(invocation logs)을 껐다. 요청 주소가 그대로 남아 조회·신청 링크 토큰이 대시보드에 쌓이기 때문이다. staging은 CPU 시간을 보려고 켜 두었고, staging의 D1 ID와 주소도 실제 값으로 채웠다.

자체 계정 비밀번호는 새로 정할 때(가입·비밀번호 바꾸기·복구 코드로 다시 정하기) 흔한 비밀번호 94개(유출 목록 상위권과 1q2w3e4r·qwer1234 같은 한국 키보드 배열, 8자 이상만), 아이디가 들어간 비밀번호, 한 글자만 되풀이한 비밀번호를 거절한다. 규칙은 `src/shared/account.ts`의 `passwordProblem` 하나를 서버와 화면이 함께 쓰고, 비교는 NFKC·소문자로 해서 Password1·전각 글자도 걸린다. 이미 정한 비밀번호로 로그인하는 것은 막지 않는다. 비밀번호 바꾸기 화면은 아이디를 모르므로 아이디 검사는 서버만 한다. 칸 아래 조건 줄은 "8자 이상, 아이디가 들어가거나 흔한 비밀번호는 안 돼요"로 바꿨다.

공동 운영자를 내보내도 그 사람은 조회 링크와 참가 신청 링크 주소를 그대로 안다. 링크를 자동으로 바꾸면 참가자들이 가진 링크까지 끊기므로 운영자가 정하게 두고, 내보낸 직후 공동 운영자 칸에 "두 링크를 다시 만들어 참가자에게 새로 보내 주세요" 안내를 띄운다. 안내의 버튼은 모임 탭의 조회 링크 칸(접혀 있으면 펼쳐서)과 참가자 고르기 화면(참가 신청 링크 관리)으로 데려가고, 닫을 때까지 남는다.

문서: `docs/배포안내.md` 8-1절 3번에 CF-Worker 헤더, 비밀번호 확인 CPU 시간, 소스맵 비공개, 운영 실행 기록 꺼짐 확인을 더했고, 오류 기록 보관 한도를 출처별로 고쳐 적었다. `docs/개선-서버-2026-11-08.md` 4절의 "429도 D1 쓰기를 쓰지만 Worker 요청 한도가 먼저 닿는다"는 틀린 서술이었다(그때 429 한 번이 쓰기 2행이라 D1 쓰기 한도가 먼저 닿았다). 이번 수정으로 사실이 됐다고 바로잡았다.

검증: `npm run typecheck`·`npm run lint`(오류 0, 경고 34 그대로)·`npm run build`·`npm run check:bundle`(첫 화면 우리 코드 brotli 15.1KB, 전체 93.2KB로 그대로. 흔한 비밀번호 목록은 첫 화면 밖 조각에 들어간다) 통과. `npm test` 73개 파일 1079개 통과(1072 + 7: `ratelimit` 2개 — 카운트가 limit + 1에서 멈추고 걸린 횟수는 창마다 1, CF-Worker 요청은 IP가 달라도 한 버킷 / `error-log` 1개 — 화면 오류가 넘쳐도 서버 오류 기록이 남음 / `local-accounts` 4개 — 공용 규칙, 가입 거절, 비밀번호 바꾸기·복구 거절, 예전 흔한 비밀번호로 로그인). 기존 `local-accounts`의 경계 사례 두 줄은 새 규칙에 걸려 값만 바꿨다(8자 경계 `12345678` → 흔하지 않은 8자, 128자 `가` 반복 → `가나` 반복). e2e는 `signup.spec.ts`의 조건 줄 문구를 바꾸고 흔한 비밀번호 안내 확인을 더했으며, `co-operators.spec.ts`에 내보낸 뒤 안내·조회 링크 칸 이동·닫기를 더했다(e2e 개수는 124개 그대로).
