## 4. 요청 수 제한의 D1 쓰기 줄이기 — (a)를 택함

**택한 것**: (a) 조회 링크 `GET /api/view/:token`과 참가 신청 공개 조회 `GET /api/join/:token`에서 **ETag가 맞아 304로 답할 때는 `view-ip` 카운터를 올리지 않는다**. 공통 앞단에서 이 두 GET을 빼고 경로 안에서 센다: ETag 비교 → 304면 끝, 아니면 세기 → 본문 만들기. 없는 토큰·링크(404)는 센다(토큰 맞히기 방지). 인수·공동 운영 초대·연결 링크 GET은 예전처럼 앞단에서 센다.

**왜 (a)인가**
- 304 한 번의 비용은 모임 행 1행 읽기뿐이다. 제한을 세는 비용(`rate_limits` UPSERT + 지난 창 DELETE)이 오히려 그보다 크고, D1 쓰기는 하루 10만 행으로 읽기(500만)보다 50배 좁다.
- 304를 세어도 막을 수 있는 것이 거의 없다: 한도에 걸린 429 응답도 Worker 요청 1건이고 D1 쓰기를 쓴다. 무료 요금제의 하루 Worker 요청 한도가 먼저 닿는 쪽이고, 304 남발로 D1 읽기 한도(500만)에 닿으려면 그보다 훨씬 많은 요청이 필요하다.
- 비싼 일(스냅숏 batch, 신청 명단 batch)은 여전히 한도 뒤에 있다. 304는 같은 ETag(곧 이미 받은 본문)를 가진 사람만 받을 수 있다.
- (b) Rate Limiting 바인딩은 이번에 넣지 않았다. 공식 문서(https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/, 2026-11-08 확인): 설정은 최상위 `ratelimits` 배열(`name`, `namespace_id`, `simple: { limit, period }`), period는 **10 또는 60초만**, "Each location applies an approximate limit"(위치별 대략적 제한). **무료 요금제에서 쓸 수 있는지는 그 문서에 적혀 있지 않다 [미확인]**. 지시의 `unsafe.bindings` 꼴은 문서에 없었다.

**세부**
- 세기를 ETag 헤더보다 먼저 한다: 429 응답에 `ETag`·`Cache-Control: private`가 붙어 브라우저가 저장하면 다음 304가 그 429 본문을 되살릴 수 있어서다. 429에는 `no-store`가 붙는다.
- 한도에 걸린 뒤에도 같은 ETag의 304는 계속 받는다(본문을 다시 만들지 않으므로 부담이 없다).

**파일**: `src/server/index.ts`(앞단, `/api/view/:token`, `/api/join/:token`), `src/server/join.ts`(`joinInfoConditional`의 `count` 인자).

**테스트**(`test/server-followup.test.ts`, 한도 2·고정 시계) [확인]: 조회 링크 200 → 304 다섯 번 → 200(두 번째로 셈) → 429(ETag 없음, `no-store`) → 같은 ETag는 304 / 없는 토큰 404·404·429 / 참가 신청도 같음. 기존 ETag·요청 수 제한 테스트 통과.

**한계**: 304가 아닌 조회(200)와 모든 쓰기는 여전히 요청마다 D1 쓰기 1행 이상이다. 조회가 아주 많아지면 바인딩(위 [미확인] 확인 뒤)이나 KV를 다시 검토한다.

## 2026-11-08 리뷰 후속

심층 리뷰에서 나온 지적을 고쳤다. 방침: **무료 요금제(요청당 CPU 10ms, D1 하루 읽기 500만 행)에 맞게 지금 고치고, 나중에 확장할 때 끼울 자리만 구조로 남긴다.** 고치기 전에 각 지점을 코드·`EXPLAIN QUERY PLAN`(node:sqlite에 마이그레이션 전부를 적용해 확인)으로 확인했다.

### A. 스냅숏 ETag와 질의(`src/server/snapshot.ts`, `migrations/0022_snapshot_indexes.sql`)

- **운영자 ETag에서 1분 단위 시각을 뺐다.** 시각을 넣은 이유는 연결 링크(`participant_claims`) 만료 하나뿐이었다(스냅숏의 `memberClaims`는 "지금 만료되지 않은 링크"만 싣는다). 대신 `loadEtagHead`가 같은 행 읽기에서 `claims_next_expiry` = 쓰지 않은 링크 중 **아직 지나지 않은** 가장 이른 만료 시각을 함께 읽어 재료에 넣는다.
  - 왜 "아직 안 지난" 최솟값인가: 링크 행이 바뀌면 `data_version`이 오른다(0021 트리거). 행이 그대로일 때 목록이 바뀌는 순간은 어떤 링크의 만료가 지나는 순간뿐이고, 그때 이 값은 반드시 다음 값(또는 null)으로 바뀐다. 그냥 `MIN(expires_at)`이면 지난 만료가 계속 최솟값으로 남아 ETag는 그대로인데 목록만 달라진다(만료된 링크가 304로 계속 보임).
  - 효과: 운영자 화면을 열어 둔 채 다시 읽기만 하면, 남은 연결 링크가 없을 때 시간이 지나도 계속 304다(예전에는 1분마다 200 + 스냅숏 batch 전체).
  - 테스트(`test/server-hardening.test.ts`): 이미 만료된 링크 + 1.5초 뒤 만료될 링크 → 304 → 만료 뒤 200(`memberClaims` 빈 목록, 새 ETag) → 그 ETag로 다시 304.
- **시리즈 질의**: `match_series_members` JOIN `matches`를 통계 없는 계획기가 `matches`(모임의 경기 전부)에서 출발해 시리즈가 0개여도 다 훑었다 [확인: `SEARCH m USING INDEX sqlite_autoindex_matches_3 (group_id=?)` + 정렬용 임시 B-트리]. `CROSS JOIN`으로 `match_series_members`(`idx_series_members`)에서 출발하게 고정하고, 경기 행은 기본 키로 찾는다. 정렬(경기 시각 → 경기 번호)은 `parseSeries`가 JS에서 한다. 결과 순서는 예전 SQL과 같다(무작위 자료 5회 비교 같음, `played_at`은 ASCII라 JS 문자열 비교 = SQLite BINARY, `match_no`는 모임 안에서 UNIQUE).
- **변경 이력 질의 두 개**:
  - "변경 내역"(정정·제외·복구 200줄): `idx_revisions_group (group_id, id)`를 거꾸로 걸으며 종류를 하나씩 걸렀다. 정정은 드물어 사실상 이력 전부를 읽었다.
  - 합치기 묶음(`kind = 'correction'`): 이력 전부를 읽고 줄마다 합치기 판별 하위 질의를 돌렸다.
  - 0022에 `idx_revisions_group_kind ON match_revisions (group_id, kind, id)`를 더했다. 합치기 묶음 질의는 바로 이 색인을 쓴다(`SEARCH r USING INDEX idx_revisions_group_kind (group_id=? AND kind=?)`). "변경 내역" 질의는 색인만 더해서는 계획기가 정렬을 아끼려고 예전 색인을 계속 골라, `ORDER BY +r.id DESC`("+"로 id 순서를 색인에 맞추지 않게)로 새 색인을 쓰게 했다. 세 종류의 줄만 읽고 그것만 정렬한다(id는 겹치지 않아 결과 같음).
  - "최근 이력"(종류 무관 200줄) 질의는 예전 색인을 거꾸로 걸으며 200줄을 채우면 멈추므로 그대로 뒀다.
- **확장 자리**: ETag 경로(운영자 스냅숏·조회 링크)의 200 본문을 만드는 단일 함수 `snapshotBody(env, groupId, role, etag)`를 두고 `index.ts`의 두 경로가 이것을 부른다. 위에 "나중에 gzip 본문을 ETag 열쇠로 D1 한 행에 캐시할 자리. 도입 기준: 가장 큰 모임이 약 1000경기(서버 JS 시간이 10ms에 닿는 지점. **522경기에서 4~5ms 실측**)" 주석을 달았다. 캐시는 구현하지 않았다(캐시하면 본문의 `serverTime`이 굳는 점도 주석에 적음).

### B. 쓰기 공통 경로의 점검 보호(`src/server/mutation.ts`)

- **batch 안 점검 재확인**: `runMutation`은 점검 상태(`groups.maintenance`)를 batch 밖에서 읽기만 해서, 확인 뒤 batch 실행 전에 복원(1단계가 점검을 켜고 기존 행을 지움)이나 모임 삭제가 끼면 그 쓰기가 점검 중인 모임에 저장될 수 있었다 [확인: 아래 테스트가 고치기 전 코드에서 실패]. `allowMaintenance`가 없는 요청은 첫 batch(단계가 있으면 첫 단계) 맨 앞에 `maintenanceGuard`(`INSERT INTO guard (maintenance) SELECT 1 FROM groups WHERE id = ?1 AND maintenance = 1`, 0022의 `guard.maintenance` CHECK)를 넣고, `classifyBatchError`가 `guard_maintenance`를 기존 `maintenanceError()`(503 `MAINTENANCE`)로 바꾼다. 복원(allowMaintenance 있음)은 넣지 않는다: 스스로 점검을 켜고 이어 가며, 겹치는 실행은 작업 잠금(claimJob·jobOwnerGuard)이 막는다(예전처럼 `RESTORE_IN_PROGRESS`).
  - 비용: 쓰기마다 D1 읽기 1행.
  - 테스트(`test/restore.test.ts` "점검 확인을 통과한 다른 운영자의 쓰기라도…"): 쓰기가 점검 확인을 마친 뒤 build 안에서 멈춤 → 여러 단계 복원 시작 → `restoreHooks.afterStage(0)`에서 쓰기를 풀어 줌 → 쓰기는 `MAINTENANCE`, 요청 기록 없음, 복원 결과는 백업과 같음(끼어든 시즌 없음).
- **요청 해시를 원문으로**: 큰 본문은 `JSON.stringify`로 다시 직렬화해 SHA-256 하던 것을, 호출자가 원문을 넘기면(`payloadText`) 원문으로 해시한다(`op\nraw:원문`). 복원 두 경로(`applyRestore`, `importAsNewGroup`)만 적용했다(`http.ts`의 새 `readJsonBodyWithText`). 복원 8MB 본문에서 약 2ms(리뷰 측정값)를 아낀다. 멱등 의미는 같다: 원문에는 요청 ID·확인 문구·baseGeneration·백업이 모두 들어 있어 "같은 요청 ID + 같은 본문"이면 같은 요청이다. 바이트만 다르고 내용이 같은 JSON은 다른 요청으로 보지만, 재시도는 같은 본문을 그대로 보내므로 문제가 없다. 나머지 쓰기는 본문이 작아 그대로 뒀다.

### C. 모임 삭제 때 R2 자동 백업도 지우기(`src/server/deletion.ts`)

- `deleteStoredBackups`: D1 삭제가 끝난 뒤(한 batch·여러 단계 모두) `backups/{모임 ID}/`(접두어는 `backupCron.ts`의 `BACKUP_PREFIX`)를 `list`(1000개씩, `truncated`/`cursor`) → `delete`(최대 1000개씩).
- **D1 삭제 뒤, best-effort**로 한 이유: 먼저 지우면 D1 삭제가 실패·중단됐을 때 모임은 남고 백업만 사라진다. D1에서 모임 행이 사라진 뒤에는 자동 백업이 그 모임을 고르지 않아 다시 생기지 않는다. R2 실패는 `{"backup":"delete-failed","group":…}` 한 줄(Workers Logs, `backupCron.ts`와 같은 꼴)만 남기고 삭제 응답은 성공이다. 남은 파일과 "삭제 직전에 시작된 자동 백업이 넣은 파일"은 R2 수명 주기 규칙(backups/ 30일)이 지운다. `BACKUPS` 바인딩이 없으면 건너뛴다.
- 테스트(`test/deletion.test.ts`, Miniflare R2): 한 batch 삭제가 그 모임 백업만 지움 / 여러 단계 삭제가 끊기면 백업이 남고 다시 실행해 끝나면 지움 / 1005개(목록 2쪽) 모두 지움 / R2가 실패해도 200·모든 행 삭제·오류 기록, 바인딩이 없어도 200.
- 처리방침(`src/web/screens/Privacy.tsx`): 모임 삭제 항목에 "서버의 자동 백업(하루 한 번, 최대 30일)도 함께 지움(오류로 남으면 30일 안에 자동 삭제)", 익명 처리 항목에 "서버 자동 백업(최대 30일 보관 뒤 자동 삭제)에도 옛 이름이 남을 수 있음". `docs/배포안내.md` 13-4절 메모도 갱신.

### D. 배포 안내(`docs/배포안내.md`)

- 7절: 0022 설명(색인 1개 + 보호 열 1개, 0022를 먼저 적용하고 배포).
- 9절 4번: staging에서는 로컬 522경기 백업 파일로 복원을 실제로 실행하고 Workers Logs의 `cpuTime`을 본다. 10ms를 넘으면 13절에 "복원은 Workers Paid로 바꾼 날에만 실행"을 적는다.
- 8-1절 5번: 운영 D1에 기존 기록을 처음 옮길 때는 복원이 아니라 '기존 사이트 기록 가져오기'(50경기씩).
- 13절(13-1 아래): 무료 요금제에서는 복원이 CPU 초과(1102)로 끊길 수 있음, 그때는 Paid 전환 후 같은 파일로 다시 실행.

### 측정값(이번에 새로 잰 것은 없음, 리뷰·이전 측정 인용)

- 스냅숏 서버 JS 시간: 522경기 모임에서 4~5ms → 약 1000경기에서 10ms에 닿을 것으로 봄(캐시 도입 기준).
- 복원 요청 해시: 8MB 본문 재직렬화 + SHA-256 약 2ms → 원문 해시로 재직렬화 몫이 빠짐.
- [미확인] 실제 D1에서의 계획(통계가 생기면 계획기가 달리 고를 수 있다), staging 복원의 `cpuTime`.

### 남긴 확장 자리

- `snapshotBody`: gzip 본문 캐시(ETag 열쇠, D1 한 행). 도입 기준 약 1000경기.
- `runMutation`의 `payloadText`: 다른 큰 본문 경로(가져오기 등)도 원문을 넘기면 바로 쓴다.
- `snapshotEtag` 주석: 스냅숏에 시각에 따라 바뀌는 값을 새로 넣으면 그 "다음 바뀌는 시각"을 `claims_next_expiry`처럼 재료에 넣는다.

### 하지 않기로 한 것

- **통계 계산을 서버로 옮기기**: 지금은 화면이 스냅숏으로 계산한다. 서버로 옮기면 무료 요금제 CPU 10ms에 먼저 닿는다.
- **스냅숏 폴링(실시간 갱신)**: 304가 싸졌어도 요청 수·D1 읽기가 늘어난다. 지금처럼 새로 고침 기준.
- **복원 장치 확장**(단계 재개 지점 저장, 큐·Durable Object 등): 무료 요금제에서 큰 복원이 끊기면 Paid로 바꿔 다시 실행하는 것으로 충분하다(13절).
