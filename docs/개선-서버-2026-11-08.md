## 4. 요청 수 제한의 D1 쓰기 줄이기 — (a)를 택함

**택한 것**: (a) 조회 링크 `GET /api/view/:token`과 참가 신청 공개 조회 `GET /api/join/:token`에서 **ETag가 맞아 304로 답할 때는 `view-ip` 카운터를 올리지 않는다**. 공통 앞단에서 이 두 GET을 빼고 경로 안에서 센다: ETag 비교 → 304면 끝, 아니면 세기 → 본문 만들기. 없는 토큰·링크(404)는 센다(토큰 맞히기 방지). 인수·공동 운영 초대·연결 링크 GET은 예전처럼 앞단에서 센다.

**왜 (a)인가**
- 304 한 번의 비용은 모임 행 1행 읽기뿐이다. 제한을 세는 비용(`rate_limits` UPSERT + 지난 창 DELETE)이 오히려 그보다 크고, D1 쓰기는 하루 10만 행으로 읽기(500만)보다 50배 좁다.
- 304를 세어도 막을 수 있는 것이 거의 없다: 한도에 걸린 429 응답도 Worker 요청 1건이다. 304 남발로 D1 읽기 한도(500만)에 닿으려면 하루 Worker 요청 한도보다 훨씬 많은 요청이 필요하다.
  - (2026-11-10 보안 감사로 바로잡음) 이 절을 쓸 때는 "429도 D1 쓰기를 쓰지만 Worker 요청 한도가 먼저 닿는다"고 적었는데 틀렸다. 그때 429 한 번은 카운터 UPSERT 1행 + 한도 걸림 합계 1행으로 쓰기 2행을 써서, 한 IP가 계속 보내기만 해도 D1 쓰기 한도(하루 10만 행)가 Worker 요청 한도(하루 10만 건)보다 먼저, 절반쯤에서 닿았다. 지금은 `hit()`이 카운트를 limit + 1에서 멈춰 창마다 처음 넘는 요청만 쓰고 그 뒤 429는 쓰기가 없다(`src/server/ratelimit.ts`).
  - (같은 날 두 번째 감사로 다시 바로잡음) 위 수정 뒤에 "그래서 이제는 Worker 요청 한도가 먼저 닿는다"고 적었는데 그것도 틀렸다. 429가 쓰기를 쓰지 않을 뿐, **한도 안의 요청**은 여전히 요청마다 1행 이상을 쓴다(카운터 1행. 틀린 로그인은 실패 기록까지 3~4행, 화면 오류 보고는 기록 넣기·한도 지우기까지 약 5행). 한 IP가 각 한도 바로 아래로만 보내면 분당 약 250행, 6~7시간이면 하루 10만 행이라 Worker 요청 한도(10만 건)보다 D1 쓰기 한도가 먼저 닿았다. 그 뒤의 수정과 남은 양은 [개선-서버-2026-11-10](개선-서버-2026-11-10.md) H2에 있다.
- 비싼 일(스냅숏 batch, 신청 명단 batch)은 여전히 한도 뒤에 있다. 304는 같은 ETag(곧 이미 받은 본문)를 가진 사람만 받을 수 있다.
- (b) Rate Limiting 바인딩은 이번에 넣지 않았다. 공식 문서(https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/, 2026-11-08 확인): 설정은 최상위 `ratelimits` 배열(`name`, `namespace_id`, `simple: { limit, period }`), period는 **10 또는 60초만**, "Each location applies an approximate limit"(위치별 대략적 제한). **무료 요금제에서 쓸 수 있는지는 그 문서에 적혀 있지 않다 [미확인]**. 지시의 `unsafe.bindings` 꼴은 문서에 없었다.

**세부**
- 세기를 ETag 헤더보다 먼저 한다: 429 응답에 `ETag`·`Cache-Control: private`가 붙어 브라우저가 저장하면 다음 304가 그 429 본문을 되살릴 수 있어서다. 429에는 `no-store`가 붙는다.
- 한도에 걸린 뒤에도 같은 ETag의 304는 계속 받는다(본문을 다시 만들지 않으므로 부담이 없다).

**파일**: `src/server/index.ts`(앞단, `/api/view/:token`, `/api/join/:token`), `src/server/join.ts`(`joinInfoConditional`의 `count` 인자).

**테스트**(`test/server-followup.test.ts`, 한도 2·고정 시계) [확인]: 조회 링크 200 → 304 다섯 번 → 200(두 번째로 셈) → 429(ETag 없음, `no-store`) → 같은 ETag는 304 / 없는 토큰 404·404·429 / 참가 신청도 같음. 기존 ETag·요청 수 제한 테스트 통과.

**한계**: 304가 아닌 조회(200)와 모든 쓰기는 여전히 요청마다 D1 쓰기 1행 이상이다. 조회가 아주 많아지면 바인딩(위 [미확인] 확인 뒤)이나 KV를 다시 검토한다.

## 2026-11-08 리뷰 후속

심층 리뷰에서 나온 지적을 고쳤다. 방침: **무료 요금제(요청당 CPU 10ms, D1 하루 읽기 500만 행)에 맞게 지금 고치고, 나중에 확장할 때 끼울 자리만 구조로 남긴다.** 고치기 전에 각 지점을 코드·`EXPLAIN QUERY PLAN`(node:sqlite에 마이그레이션 전부를 적용해 확인)으로 확인했다.

### A. 스냅숏 ETag와 질의(`src/server/snapshot.ts`, `migrations/0022_snapshot_indexes.sql`)

- **운영자 ETag에서 1분 단위 시각을 뺐다.** 시각을 넣은 이유는 연결 링크(`participant_claims`) 만료 하나뿐이었다(스냅숏의 `memberClaims`는 "지금 만료되지 않은 링크"만 싣는다). 대신 `loadEtagHead`가 같은 행 읽기에서 `claims_next_expiry` = 쓰지 않은 링크 중 **아직 지나지 않은** 가장 이른 만료 시각을 함께 읽어 재료에 넣는다.
  - 왜 "아직 안 지난" 최솟값인가: 링크 행이 바뀌면 `data_version`이 오른다(0021 트리거). 행이 그대로일 때 목록이 바뀌는 순간은 어떤 링크의 만료가 지나는 순간뿐이고, 그때 이 값은 반드시 다음 값(또는 null)으로 바뀐다. 그냥 `MIN(expires_at)`이면 지난 만료가 계속 최솟값으로 남아 ETag는 그대로인데 목록만 달라진다(만료된 링크가 304로 계속 보임).
  - 효과: 운영자 화면을 열어 둔 채 다시 읽기만 하면, 남은 연결 링크가 없을 때 시간이 지나도 계속 304다(예전에는 1분마다 200 + 스냅숏 batch 전체).
  - 테스트(`test/server-hardening.test.ts`): 이미 만료된 링크 + 1.5초 뒤 만료될 링크 → 304 → 만료 뒤 200(`memberClaims` 빈 목록, 새 ETag) → 그 ETag로 다시 304.
- **시리즈 질의**: `match_series_members` JOIN `matches`를 통계 없는 계획기가 `matches`(모임의 경기 전부)에서 출발해 시리즈가 0개여도 다 훑었다 [확인: `SEARCH m USING INDEX sqlite_autoindex_matches_3 (group_id=?)` + 정렬용 임시 B-트리]. `CROSS JOIN`으로 `match_series_members`(`idx_series_members`)에서 출발하게 고정하고, 경기 행은 기본 키로 찾는다. 정렬(경기 시각 → 경기 번호)은 `parseSeries`가 JS에서 한다. 결과 순서는 예전 SQL과 같다(무작위 자료 5회 비교 같음, `played_at`은 ASCII라 JS 문자열 비교 = SQLite BINARY, `match_no`는 모임 안에서 UNIQUE).
- **변경 이력 질의 두 개**:
  - "변경 내역"(정정·제외·복구 200줄): `idx_revisions_group (group_id, id)`를 거꾸로 걸으며 종류를 하나씩 걸렀다. 정정은 드물어 사실상 이력 전부를 읽었다.
  - 합치기 묶음(`kind = 'correction'`): 이력 전부를 읽고 줄마다 합치기 판별 하위 질의를 돌렸다.
  - 0022에 `idx_revisions_group_kind ON match_revisions (group_id, kind, id)`를 더했다. 합치기 묶음 질의는 바로 이 색인을 쓴다(`SEARCH r USING INDEX idx_revisions_group_kind (group_id=? AND kind=?)`). "변경 내역" 질의는 색인만 더해서는 계획기가 정렬을 아끼려고 예전 색인을 계속 골라, `ORDER BY +r.id DESC`("+"로 id 순서를 색인에 맞추지 않게)로 새 색인을 쓰게 했다. 세 종류의 줄만 읽고 그것만 정렬한다(id는 겹치지 않아 결과 같음).
  - "최근 이력"(종류 무관 200줄) 질의는 예전 색인을 거꾸로 걸으며 200줄을 채우면 멈추므로 그대로 뒀다.
- **확장 자리**: ETag 경로(운영자 스냅숏·조회 링크)의 200 본문을 만드는 단일 함수 `snapshotBody(env, groupId, role, etag)`를 두고 `index.ts`의 두 경로가 이것을 부른다. 위에 "나중에 gzip 본문을 ETag 열쇠로 D1 한 행에 캐시할 자리. 도입 기준: 가장 큰 모임이 약 1000경기(서버 JS 시간이 10ms에 닿는 지점. **522경기에서 4~5ms 실측**)" 주석을 달았다. 캐시는 구현하지 않았다(캐시하면 본문의 `serverTime`이 굳는 점도 주석에 적음).

### B. 쓰기 공통 경로의 점검 보호(`src/server/mutation.ts`)

- **batch 안 점검 재확인**: `runMutation`은 점검 상태(`groups.maintenance`)를 batch 밖에서 읽기만 해서, 확인 뒤 batch 실행 전에 복원(1단계가 점검을 켜고 기존 행을 지움)이나 모임 삭제가 끼면 그 쓰기가 점검 중인 모임에 저장될 수 있었다 [확인: 아래 테스트가 고치기 전 코드에서 실패]. `allowMaintenance`가 없는 요청은 첫 batch(단계가 있으면 첫 단계) 맨 앞에 `maintenanceGuard`(`INSERT INTO guard (maintenance) SELECT 1 FROM groups WHERE id = ?1 AND maintenance = 1`, 0022의 `guard.maintenance` CHECK)를 넣고, `classifyBatchError`가 `guard_maintenance`를 기존 `maintenanceError()`(503 `MAINTENANCE`)로 바꾼다. 복원(allowMaintenance 있음)은 넣지 않는다: 스스로 점검을 켜고 이어 가며, 겹치는 실행은 작업 잠금(claimJob·jobOwnerGuard)이 막는다(예전처럼 `RESTORE_IN_PROGRESS`).
  - 비용: 쓰기마다 D1 읽기 1행.
  - 테스트(`test/restore.test.ts` "점검 확인을 통과한 다른 운영자의 쓰기라도…"): 쓰기가 점검 확인을 마친 뒤 build 안에서 멈춤 → 여러 단계 복원 시작 → `restoreHooks.afterStage(0)`에서 쓰기를 풀어 줌 → 쓰기는 `MAINTENANCE`, 요청 기록 없음, 복원 결과는 백업과 같음(끼어든 시즌 없음).
- **요청 해시를 원문으로**: 큰 본문은 `JSON.stringify`로 다시 직렬화해 SHA-256 하던 것을, 호출자가 원문을 넘기면(`payloadText`) 원문으로 해시한다(`op\nraw:원문`). 복원 두 경로(`applyRestore`, `importAsNewGroup`)만 적용했다(`http.ts`의 새 `readJsonBodyWithText`). 복원 8MB 본문에서 약 2ms(리뷰 측정값)를 아낀다. 멱등 의미는 같다: 원문에는 요청 ID·확인 문구·baseGeneration·백업이 모두 들어 있어 "같은 요청 ID + 같은 본문"이면 같은 요청이다. 바이트만 다르고 내용이 같은 JSON은 다른 요청으로 보지만, 재시도는 같은 본문을 그대로 보내므로 문제가 없다. 나머지 쓰기는 본문이 작아 그대로 뒀다.

### C. 모임 삭제 때 R2 자동 백업도 지우기(`src/server/deletion.ts`)

- `deleteStoredBackups`: D1 삭제가 끝난 뒤(한 batch·여러 단계 모두) `backups/{모임 ID}/`(접두어는 `backupCron.ts`의 `BACKUP_PREFIX`)를 `list`(1000개씩, `truncated`/`cursor`) → `delete`(최대 1000개씩).
- **D1 삭제 뒤, best-effort**로 한 이유: 먼저 지우면 D1 삭제가 실패·중단됐을 때 모임은 남고 백업만 사라진다. D1에서 모임 행이 사라진 뒤에는 자동 백업이 그 모임을 고르지 않아 다시 생기지 않는다. R2 실패는 `{"backup":"delete-failed","group":…}` 한 줄(Workers Logs, `backupCron.ts`와 같은 꼴)만 남기고 삭제 응답은 성공이다. 남은 파일과 "삭제 직전에 시작된 자동 백업이 넣은 파일"은 R2 수명 주기 규칙(backups/ 30일)이 지운다. `BACKUPS` 바인딩이 없으면 건너뛴다.
- 테스트(`test/deletion.test.ts`, Miniflare R2): 한 batch 삭제가 그 모임 백업만 지움 / 여러 단계 삭제가 끊기면 백업이 남고 다시 실행해 끝나면 지움 / 1005개(목록 2쪽) 모두 지움 / R2가 실패해도 200·모든 행 삭제·오류 기록, 바인딩이 없어도 200.
- 처리방침(`src/web/screens/Privacy.tsx`): 모임 삭제 항목에 "서버의 자동 백업(하루 한 번, 최대 30일)도 함께 지움(오류로 남으면 30일 안에 자동 삭제)", 익명 처리 항목에 "서버 자동 백업(최대 30일 보관 뒤 자동 삭제)에도 옛 이름이 남을 수 있음". `docs/배포안내.md` 13-4절 메모도 갱신.

### 측정값(이번에 새로 잰 것은 없음, 리뷰·이전 측정 인용)

- 스냅숏 서버 JS 시간: 522경기 모임에서 4~5ms → 약 1000경기에서 10ms에 닿을 것으로 봄(캐시 도입 기준).
- 복원 요청 해시: 8MB 본문 재직렬화 + SHA-256 약 2ms → 원문 해시로 재직렬화 몫이 빠짐.
- [미확인] 실제 D1에서의 계획(통계가 생기면 계획기가 달리 고를 수 있다), staging 복원의 `cpuTime`.

### 남긴 확장 자리

- `snapshotBody`: gzip 본문 캐시(ETag 열쇠, D1 한 행). 도입 기준 약 1000경기.
- `runMutation`의 `payloadText`: 다른 큰 본문 경로(가져오기 등)도 원문을 넘기면 바로 쓴다.
- `snapshotEtag` 주석: 스냅숏에 시각에 따라 바뀌는 값을 새로 넣으면 그 "다음 바뀌는 시각"을 `claims_next_expiry`처럼 재료에 넣는다.

### 하지 않기로 한 것

- **통계 계산을 서버로 옮기기**: 지금은 화면이 스냅숏으로 계산한다. 서버로 옮기면 무료 요금제 CPU 10ms에 먼저 닿는다.
- **스냅숏 폴링(실시간 갱신)**: 304가 싸졌어도 요청 수·D1 읽기가 늘어난다. 지금처럼 새로 고침 기준.
- **복원 장치 확장**(단계 재개 지점 저장, 큐·Durable Object 등): 무료 요금제에서 큰 복원이 끊기면 Paid로 바꿔 다시 실행하는 것으로 충분하다(13절).

## 보안 점검 후속(2026-11-08)

보안 리뷰에서 나온 항목을 코드로 확인한 뒤 고쳤다. 리뷰 내용이 틀린 항목은 없었다.

1. **HEAD 요청이 요청 수 제한을 건너뜀**(`src/server/index.ts`): Hono는 HEAD를 GET 경로로 보내 같은 처리(D1 읽기 포함)를 하는데, 제한 앞단은 `method === "GET"`만 보고 HEAD는 아무 버킷에도 세지 않았다. HEAD를 GET으로 보고 센다(view-ip·heavy-ip 등). 조회 링크·참가 신청은 원래대로 경로 안에서 센다.
2. **IPv6 주소 돌려쓰기**(`src/server/ratelimit.ts` `ipSubject`): 한 회선이 보통 /64를 통째로 받아 주소 끝만 바꾸면 IP별 한도를 피할 수 있었다. IPv6는 압축 표기(`::`)·앞자리 0·대소문자·영역 표시·끝의 IPv4 표기를 풀어 앞 64비트만 키로 쓴다. IPv4-mapped(`::ffff:a.b.c.d`)는 IPv4로 본다. 라이브러리 없이 직접 푼다(형식이 이상하면 그대로).
3. **권한을 잃은 운영자가 미리 만든 참가자 연결 링크**(`src/server/coOperators.ts` `removeCoOperator`, `src/server/groups.ts` `acceptTransfer`): 공동 운영자를 내보내거나(스스로 나가기 포함) 대표를 넘기면, 그 사람이 만든 쓰지 않은 연결 링크로 나중에 남의 참가자에 계정을 연결할 수 있었다. 링크 표(`participant_claims`)에 만든 사람이 없어 모임의 쓰지 않은 링크를 모두 같은 batch에서 지운다(남은 운영자는 필요하면 다시 만든다. 이미 쓴 연결은 그대로). 내보내기는 행이 있는지 먼저 확인해, 없는 공동 운영자를 내보내는 404 요청은 링크를 건드리지 않는다.
4. **자체 계정 잠금을 남이 걸 수 있음**(`src/server/local.ts`): 실패 횟수를 아이디로만 세어, 아이디만 알면 틀린 비밀번호 10번으로 주인의 로그인을 15분씩 막을 수 있었다. 로그인·복구는 (아이디 HMAC, IP 키)별로 10·5번, 아이디 전체(모든 IP 합계)는 15분 100번으로 나눴다. IP 키는 요청 수 제한과 같은 `ipKey`(IPv6 /64). 성공하면 그 아이디의 기록을 IP와 상관없이 지운다. 계정 탈퇴도 "키:IP" 꼴까지 지운다(`deletion.ts`, 범위 비교 `FAILURE_KEY_MATCH`). 로그인한 상태의 비밀번호 확인은 계정별 그대로.
5. **DEPLOY_ENV 안전장치 뒤집기**(`src/server/auth.ts` `productionConfigProblem`): 이전에는 `DEPLOY_ENV=production`일 때만 검사해, 운영 표시를 빠뜨리거나 잘못 적으면(`prod`, 빈 값) 검사가 꺼졌다. 이제 `local`만 건너뛰고 나머지는 모두 검사한다. 테스트 설정은 `wrangler.jsonc` 맨 위(`DEPLOY_ENV=local`)라 그대로다. `wrangler.spike.jsonc`(`DEPLOY_ENV=spike`, `AUTH_MODE=fake`)는 이제 모든 API가 503이지만, 스파이크 테스트는 D1만 직접 쓰므로 영향이 없다(오히려 실수로 배포해도 닫힌다). `test/auth.test.ts`의 "다른 표시면 닫힌다" 기대를 404 → 503(CONFIG_ERROR)으로 바꾸고, local이 아닌 값에서 올바른 설정이면 동작하는 사례를 더했다.
6. **대량 쓰기 하루 예산**(`src/server/ratelimit.ts` `spendBulkRows`): 분당 요청 수 제한만으로는 계정·IP 몇 개로 가져오기(50경기씩)를 하루 종일 돌려 D1 무료 쓰기 한도(하루 10만 행)를 다 쓸 수 있었다. UTC 하루 창 버킷 `bulk-rows-account`(3,000경기)·`bulk-rows-ip`(6,000경기)을 두고 가져오기·지난 경기 입력(1경기)·복원(같은 모임 복구, 새 모임으로 가져오기: 파일의 경기 수)에서 쓴다. wrangler vars `RATE_BULK_ROWS_PER_ACCOUNT`·`RATE_BULK_ROWS_PER_IP`로 바꾼다(로컬 설정은 넉넉히 1,000,000).
   - 확인과 더하기를 보호 문장(`guard_state_conflict`)과 함께 한 batch로 실행해 동시 요청도 한도를 넘지 않고, 거절된 묶음은 예산을 깎지 않는다(분당 제한과 다른 점: 큰 묶음이 거절돼도 작은 묶음은 계속 넣을 수 있다).
   - 입력 검증이 끝난 뒤 쓰기 직전에 쓴다. 같은 요청 ID의 재시도(runMutation 재생), 중간에 멈춘 같은 복원 요청을 이어서 끝내기, 새 모임 가져오기의 재전송은 다시 쓰지 않는다. 쓴 뒤 batch가 버전 충돌로 실패하면 그만큼은 돌려받지 못한다(하루 예산이라 감수).
   - `hit()`에 창 길이(초) 매개변수를 더했다(기본은 지금처럼 `RATE_WINDOW_SECONDS`). 지난 창 정리가 하루 예산 행을 지우지 않도록, 정리 문장을 `bulk-rows-` 키와 나머지로 나눴다.
   - 정상 사용(522경기를 50경기씩 11번) 테스트가 기본 한도에서 통과한다. 문구: "오늘 넣을 수 있는 경기 수를 넘었어요. 약 N시간 뒤(한국 시각 오전 9시)에 다시 시도해 주세요."(429 `RATE_LIMITED`, `retryAfter`).

## 정합성 점검 후속(2026-11-08)

데이터 정합성 리뷰에서 로컬 재현으로 확인된 항목을 코드로 다시 확인한 뒤 고쳤다. 질의 수는 무료 요금제 기준(Workers 호출 1회당 D1 질의 50회, `db.batch()`는 문장 수와 상관없이 1회)으로 잰다.

**질의 수 세는 공용 헬퍼**(`test/queryCount.ts`): `countingDb()`가 D1을 Proxy로 감싸 `first`·`all`·`run`·`raw`·`batch`·`exec`를 세고(bind가 돌려주는 새 문장도 감쌈), `directCounted()`가 `test/direct.ts`의 `direct()`에 그 DB를 넣어 서버를 불러 응답과 질의 수를 함께 준다(인증·요청 수 제한·요청 기록까지 그 호출의 모든 질의). `beforeBatch` 훅은 batch 직전에 그 batch 문장의 SQL 목록을 받아 "확인 뒤 batch 전에 상태가 바뀜"을 만든다. 리뷰어가 scratchpad에서 쓴 방식을 옮긴 것이다. 테스트: `test/integrity-followup.test.ts`.

1. **날짜 일괄 정정이 경기마다 질의 2회**(`src/server/matches.ts` `shiftMatchDates`): 경기마다 `loadMatch`(경기 + 명단)라 21경기부터 50회를 넘었다. `SELECT id, match_no, version, state, played_at, (모임 시간대) FROM matches WHERE group_id = ?1 AND id IN (SELECT value FROM json_each(?2))` 한 번으로 읽고 상태·미래 시각 검사와 옮긴 시각·정정 기록은 JS에서 만든다. batch도 경기 수와 상관없이 4문장이다(json_each로 버전·상태 보호 1 + 정정 기록 1 + 시각 갱신 1 + 진행 상태 버전). **질의 수: 1·60·500경기 모두 10회**(전에는 약 2×경기 수 + 8). 리뷰 밖에서 찾은 것: 기본 본문 상한 16KB에 경기 ID 500개(약 20KB)가 안 들어가 400개 남짓에서 413이 났다. 이 경로만 64KB(`SHIFT_DATES_BODY_BYTES`, `index.ts`)로 받는다.
   - 시간대: `shiftYears`의 timeZone에 서버는 모임 시간대(`groups.timezone`, 같은 질의에서 읽음), 화면(`DateCheck.tsx` 미리보기)은 `snapshot.group.timezone`을 넘긴다. 테스트: 모임을 America/New_York으로 두면 UTC 2024-02-29 03:00(뉴욕 2/28 22:00) +1년 → 2025-03-01T03:00Z(한국 기준이면 2025-02-28T03:00Z).
2. **합치기 전 백업으로 같은 모임을 복원하면 남길 대상에 옮겨 간 연결이 남음**(`src/server/restore.ts` `rewindMergeLinks`): 본인 연결·요청은 백업 밖이라 복원이 그대로 두는데 합치기는 연결을 남길 대상으로 옮긴다. 그래서 합치기는 사라지고 연결은 B에 남아 그 계정이 B의 기피 라인을 바꿀 수 있었다. `buildRestorePlan`(같은 모임 복구)이 지우기 전에 지금의 합치기(`id, source_id, target_id, created_at, undone_at, moved_link`)와 연결을 batch 1회로 읽고:
   - (a) 지금 유효한데 파일에는 없거나 되돌린 합치기: 되돌리기(`merge.ts undoLinkPlan`)와 같은 규칙으로 연결·요청을 원래 사람에게 돌려놓고, 원래 사람에게 다른 연결이 있으면 끊는다. 지웠던 연결(removed)은 조건이 맞을 때만 다시 만든다(계정 존재·한도는 문장 안에서 확인). 나중에 한 합치기부터 처리하며 연결 상태를 JS로 따라가 이어진 합치기(A→B→C)도 맞게 푼다. `undoLinkPlan`을 합치기마다 부르지 않은 이유: 합치기마다 질의 1~2회라 합치기가 많으면 50회에 닿고, 앞 처리의 결과를 보지 못한다. 이 문장들은 첫 batch(한 batch 복원이면 그 batch, 여러 단계면 1단계)에 넣고, 읽은 연결이 그대로인지 확인하는 보호 문장을 앞에 둔다.
   - (b) 지금도 파일에도 유효한 합치기: `moved_link`를 그대로 넣는다(예전에는 NULL이 되어 복원 뒤 되돌리면 연결을 돌려놓지 못했다).
   - 남는 한계: 파일에는 유효하지만 지금은 되돌린 합치기를 복원하면 연결은 합칠 대상(보관됨)에 남는다(그 계정은 보관된 자기 이름만 다뤄 남의 것을 바꾸지 못한다). 기록이 없는 합치기(`moved_link` NULL, 0023 전·새 모임 가져오기)는 무엇을 옮겼는지 몰라 되돌리기처럼 건드리지 않는다. 여러 단계 복원이 1단계 뒤에 끊겨 다시 실행하면 (b)의 값은 지워진 뒤라 NULL이 된다.
   - 테스트: 리뷰 재현 순서 그대로(A 연결 → 백업 → A를 B에 합침 → 그 백업으로 복원) → 연결이 A에게, 그 계정의 기피 라인 저장은 A에만 반영되고 B는 그대로. 그리고 합친 뒤 백업으로 복원 → `moved_link`가 남고 되돌리기가 `returned`.
3. **시리즈 만들기·이어가기가 판마다 질의**(`src/server/series.ts`): 경기·명단은 `loadMatchesByIds`(`snapshot.ts`, json_each로 batch 1회), 시리즈 소속은 `seriesOfMatches` 한 질의, 기준 판은 시리즈 판들을 batch 1회로 읽어 공용 함수로 고른다. **질의 수: 만들기 1판·15판 모두 11회(전 15판 55회), 14판 시리즈에 넣기 13회, 14판 시리즈에서 이어가기(경기 시작) 22회.** 지시의 "20판"은 한 시리즈 상한(`MAX_SERIES_GAMES` 15)을 넘어 만들 수 없어, 테스트는 상한 15판 만들기와 14판 시리즈에 넣기·이어가기로 고정했다.
4. **시리즈 기준 판이 "첫 판"**(`src/shared/series.ts` `seriesReferenceOf`): 첫 판만 참가자 정정되면 나머지가 모두 "구성 다름"이 됐다. 기준을 "전적 제외·취소가 아닌 판들 중 가장 많은 구성(동률이면 그 구성의 첫 판이 이른 쪽), 그 구성의 첫 판"으로 바꿨다(없으면 첫 판). `seriesScore`(점수·0쪽 팀)·`seriesReference`(화면 넣기 안내)·서버 `referenceOf`(넣기·이어가기 검사)가 모두 이 함수를 쓴다. 기존 테스트는 바꿀 것이 없었다(모두 다수 구성 = 첫 판 구성). 새 테스트: bo3 3판 중 1판 참가자 정정 → 1판 mismatch, 2·3판 counted, 원래 구성의 4판은 서버가 받아 줌.
   - [화면 문구, 이번 범위 밖] `src/web/seriesPanel.tsx`의 "팀 구성이 첫 판과 다른 판 N개는 점수에서 뺐어요"는 "기준 구성과 다른"이 맞다. 다른 작업과 겹치지 않게 손대지 않았다.
5. **멤버·참가 신청 쓰기의 점검 확인이 batch 밖에만 있음**(`src/server/members.ts`, `src/server/join.ts`): `acceptClaim`·`setOwnAvoid`·`createMemberRequest`(그리고 같은 꼴인 `createClaimLink`)의 batch 맨 앞에 `maintenanceGuard`를 넣고 `guard_maintenance`를 `maintenanceError`(503 `MAINTENANCE`)로 바꾼다. `join.ts`는 `createJoinLink`(한 문장 `.run()` → batch)와 공개 신청·취소가 함께 쓰는 `runGuarded`에 넣었다. 테스트: `beforeBatch` 훅으로 기피 라인 저장 batch 직전에 점검을 켬 → 503, 기피 라인 그대로. 손대지 않은 것: `unlinkSelf`(멤버 본인 연결 끊기)는 점검 확인 자체가 없다. 점검 중에 끊어도 권한이 줄어드는 쪽이라 두었다.
6. **포지션·참가자 정정 때 새 서포터 차례 종류**(`matches.ts` 정정): `already ? "repeat" : event.kind` → 진행 중 교체와 같은 `already ? "repeat" : "used"`. 반복이던 서포터 자리를 아직 차례를 안 쓴 사람으로 고치면 그 사람의 차례가 소비되지 않았다. 테스트: 같은 서포터 2연속(반복) → 2판을 원딜과 맞바꿈 → 원딜의 기록이 `used`.
7. **시리즈 요청의 같은 요청 ID 재전송이 지금 상태를 다시 읽음**(`series.ts` 만들기·넣기·빼기·고치기): 처음 응답의 시리즈(`SeriesView`, 판 순서는 `loadSeries`와 같은 비교)를 요청 기록(`stored.series`)에 남기고 재전송에는 그것을 그대로 준다(`storedSeries`, runMutation 재생 원칙과 같다). 이 변경 전에 남은 요청 기록에는 없으므로 예전처럼 다시 읽는다. 테스트: 네 요청 뒤 시리즈를 지우고 같은 요청 ID로 다시 보내면 모두 200·처음과 같은 본문.
8. **날짜 정정이 같은 묶음의 전적 제외 경기를 틀린 연도로 남김**: 서버는 확정·제외 경기를 모두 받아 옮기고(제외 상태 그대로, 정정 기록은 남김), 진행 중·결과 대기·취소 경기는 여전히 409 `STATE_CONFLICT`. 화면(`DateCheck.tsx`)은 찾기는 지금처럼 확정 경기로만 하고, 옮길 때 같은 묶음(+1 묶음: 경기 번호가 묶음 안이고 날짜가 기준보다 앞인 것, −1 묶음: 미래 시각인 것)·같은 범위의 제외 경기를 더한다(미리보기에 "(전적 제외)", 묶음 안내에 "전적 제외 경기 N개도 함께 옮겨요"). 테스트: 3경기 중 가운데 제외 → 셋 다 +1년 → 제외 경기도 옮겨지고 제외 그대로, 정정 기록 있음, 복구하면 옮긴 날짜로 돌아옴.
