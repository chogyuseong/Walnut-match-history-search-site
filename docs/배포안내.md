# 배포 안내 — 내전 운영 서비스 v2

작성일: 2026-11-05 · 독자: 이 저장소의 주인(개발은 해 봤지만 Cloudflare 배포는 처음일 수 있음)

이 문서는 **사용자가 직접 해야 하는 일**을 순서대로 적는다. 저장소에는 운영 설정의 자리만 있고 실제 값(DB ID, 비밀값, 로그인 키)은 없다. 아직 아무것도 배포하지 않았고 원격 리소스도 만들지 않았다.

표기: [확인] = 공식 문서에서 2026-11-05에 확인한 사실, [미확인] = 확인하지 못했거나 실제로 해 보지 않은 것.

## 0. 준비물

- Cloudflare 계정(무료 요금제로 시작 가능).
- 선택: 카카오 계정(카카오 디벨로퍼스), Google 계정(Google Cloud 콘솔). **카카오·Google 키 없이도 자체 계정(아이디 + 비밀번호)으로 운영할 수 있다**(4-1절). 키를 넣으면 그 로그인 버튼이 함께 보인다.
- 서비스 주소. 처음에는 Cloudflare가 주는 `https://naejeon-v2-production.<계정 하위 도메인>.workers.dev`를 써도 된다. 나중에 도메인을 연결하면 **로그인 리디렉션 URI도 바꿔야 한다**(4·5절).
- 이 저장소에서 `npm install`, `npm test`가 통과하는 상태.

명령은 모두 저장소 폴더에서 실행한다. `npx wrangler ...`의 `--env production`은 `wrangler.jsonc`의 `env.production` 구역을 쓰라는 뜻이다. 빠뜨리면 로컬 설정(가짜 로그인)이 올라가므로 **항상 붙인다**.

## 1. Cloudflare 로그인

```
npx wrangler login
```

브라우저가 열리고 계정 권한을 묻는다. 끝나면 `npx wrangler whoami`로 계정을 확인한다.

## 2. 운영 D1 만들기

```
npx wrangler d1 create naejeon-prod
```

출력에 나오는 `database_id`를 `wrangler.jsonc`의 `env.production.d1_databases[0].database_id`(지금 `REPLACE-WITH-PRODUCTION-D1-ID`)에 넣는다. 이 ID는 비밀값이 아니라 저장소에 넣어도 된다.

## 3. 서비스 주소 정하기

`wrangler.jsonc`의 `env.production.vars.PUBLIC_ORIGIN`(지금 `https://REPLACE-WITH-YOUR-DOMAIN`)을 실제 주소로 바꾼다. 끝에 `/`를 붙이지 않는다.

- workers.dev 주소를 쓰면 첫 배포(8절) 뒤에 주소가 정해진다. 그 경우 순서: 임시로 예상 주소를 넣고 배포 → 출력된 주소와 다르면 고쳐서 다시 배포.
- 이 값이 비었거나 `https://`가 아니거나 자리 표시값 그대로면 운영 서버가 **모든 API를 거절**한다(안전장치, 9절).
- **주소는 하나만 연다.** workers.dev 주소와 맞춤 도메인을 같이 열어 두면 `PUBLIC_ORIGIN`이 아닌 쪽에서는 로그인이 실패하고(리디렉션 URI가 `PUBLIC_ORIGIN`으로 고정), 쓰기 요청도 다른 사이트 요청으로 거절된다(Origin 확인). 맞춤 도메인을 쓰면 `PUBLIC_ORIGIN`을 그 도메인으로 두고 workers.dev 경로를 끈다(`wrangler.jsonc`의 `env.production`에 `"workers_dev": false`, 또는 Cloudflare 대시보드 Worker 설정 → Domains & Routes에서 workers.dev 끄기).

로그인 리디렉션 URI는 이 주소에서 정해진다:

| 제공자 | 리디렉션 URI |
|---|---|
| 카카오 | `{PUBLIC_ORIGIN}/api/auth/kakao/callback` |
| Google | `{PUBLIC_ORIGIN}/api/auth/google/callback` |

## 4-1. 자체 계정(아이디 + 비밀번호) — 기본 켜짐

외부 서비스 없이 바로 쓰는 로그인이다. 따로 등록할 것은 없고, 0009 마이그레이션(`local_credentials`, `auth_failures` 표)만 적용하면 된다(7절의 마이그레이션 명령에 포함).

- 가입 조건: 아이디 3~20자(영문 소문자·숫자·밑줄, 대문자는 소문자로 저장), 비밀번호 8~128자(조합 규칙 없음, 아이디와 같으면 거절). 값은 `src/shared/account.ts` 한곳에 있다.
- 저장: 비밀번호는 PBKDF2-HMAC-SHA-256(계정마다 무작위 솔트, 반복 100,000회 — Workers 런타임이 받는 최대값), 복구 코드는 SHA-256 해시만. 원문은 저장하지 않는다.
- 비밀번호를 잊으면: 이메일이 없으므로 가입할 때 한 번 보여 주는 **복구 코드**로만 다시 정할 수 있다. 코드를 잃은 운영자는 로그인한 상태에서 모임 탭 → 계정 관리 → "복구 코드 새로 받기"로 미리 바꿔 둔다.
- 끄기: `wrangler.jsonc`의 `env.production.vars`에 `"LOCAL_ACCOUNTS": "off"`를 넣고 다시 배포하면 가입·로그인·복구·비밀번호 바꾸기 경로가 404가 되고 화면에서 사라진다. 이미 로그인한 자체 계정의 세션은 만료·로그아웃 전까지 유지된다.
- [주의] Workers **무료 요금제의 요청당 CPU 시간은 10ms**다([확인] https://developers.cloudflare.com/workers/platform/limits/). PBKDF2 100,000회는 로컬 측정으로 한 번에 약 30ms가 걸려(아래 실측) 무료 요금제에서는 가입·로그인 요청이 CPU 한도에 걸릴 수 있다. [미확인] 실제 Cloudflare 설비에서의 시간과 무료 요금제에서의 동작은 배포해 보지 않아 확인하지 못했다. 걸리면 유료 요금제(요청당 기본 30초)로 올리거나 `PASSWORD_PBKDF2_ITERATIONS`를 낮춘다(최소 10,000. 낮추면 비밀번호 추측에 약해진다. 저장한 해시에 횟수가 적혀 있어 나중에 올리면 다음 로그인 때 새 횟수로 다시 저장된다).
- [확인] Workers의 WebCrypto는 PBKDF2(deriveBits)를 지원한다(https://developers.cloudflare.com/workers/runtime-apis/web-crypto/). 반복 횟수 상한(100,000)은 공식 문서에 적혀 있지 않고, workerd 소스의 "최대 반복 횟수를 제한한다(의도적인 비표준)"는 주석과 운영 Workers에서 100,000 초과가 거절됐다는 외부 보고로 정했다. [미확인] 로컬 개발 서버(workerd)는 100,000을 넘는 값도 계산했다 — 운영과 다를 수 있으므로 100,000을 넘기지 않는다.
- `node:crypto`의 scrypt는 `nodejs_compat` 호환 플래그가 필요한데 이 프로젝트는 켜지 않았다(`wrangler.jsonc`). 켜면 다른 모듈의 동작도 바뀔 수 있어 쓰지 않았다.

## 4. 카카오 앱 등록(선택)

카카오 디벨로퍼스(https://developers.kakao.com)에서:

1. 내 애플리케이션 → 애플리케이션 추가.
2. 앱 키에서 **REST API 키**를 확인한다 → `KAKAO_CLIENT_ID`.
3. 카카오 로그인 → 활성화 설정 ON. **Redirect URI**에 3절의 카카오 주소를 정확히 등록한다(한 글자라도 다르면 로그인 실패).
4. 플랫폼(Web)에 사이트 도메인(`PUBLIC_ORIGIN`)을 등록한다.
5. 보안 → **Client Secret** 코드 생성 → `KAKAO_CLIENT_SECRET`. [확인] 클라이언트 시크릿 기능은 기본으로 켜져 있고, 켜져 있으면 토큰 요청에 반드시 넣어야 한다.
6. 동의 항목: **아무것도 켜지 않는다.** 이 서비스는 회원번호만 쓴다(닉네임·이메일·프로필 사진 요청 안 함).

[미확인] 동의 항목 없이 회원번호만 쓰는 개인 개발자 앱이 비즈 앱 전환이나 검수 없이 운영 가능한지는 공식 가이드에서 확인하지 못했다(docs/P4 51행). 막히면 Google 로그인만 켜도 된다(카카오 키를 넣지 않으면 카카오 버튼이 사라진다).

메뉴 이름은 콘솔 개편으로 바뀔 수 있다.

## 5. Google 로그인 등록(선택, 대체 수단)

Google Cloud 콘솔(https://console.cloud.google.com)에서:

1. 프로젝트 만들기.
2. OAuth 동의 화면(Google Auth Platform → 브랜딩/대상): 외부(External), 앱 이름·지원 이메일 입력. 범위(scope)는 추가하지 않는다(서비스는 `openid`만 요청).
3. 사용자 인증 정보 → OAuth 클라이언트 ID 만들기 → 웹 애플리케이션.
4. 승인된 리디렉션 URI에 3절의 Google 주소를 등록한다.
5. 클라이언트 ID → `GOOGLE_CLIENT_ID`, 클라이언트 보안 비밀 → `GOOGLE_CLIENT_SECRET`.
6. 앱을 "프로덕션"으로 게시한다(테스트 상태면 등록한 테스트 사용자만 로그인된다).

[미확인] `openid`만 요청하는 경우 Google 검수가 필요 없는지는 공식 문서에서 직접 확인하지 못했다(민감 범위가 아니라 필요 없을 것으로 추정).

## 6. 비밀값 넣기

비밀값은 저장소에 넣지 않고 Cloudflare에만 저장한다. 명령마다 값을 물어보면 붙여 넣는다.

```
npx wrangler secret put SESSION_SECRET --env production
npx wrangler secret put KAKAO_CLIENT_ID --env production
npx wrangler secret put KAKAO_CLIENT_SECRET --env production
npx wrangler secret put GOOGLE_CLIENT_ID --env production
npx wrangler secret put GOOGLE_CLIENT_SECRET --env production
```

- `SESSION_SECRET`: 세션 쿠키 서명 키. **32자 이상**의 무작위 값(짧으면 서버가 거절). 만들기 예: `node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"`. 로컬 `.dev.vars`의 값과 다른 값을 쓴다. 바꾸면 모든 사람이 다시 로그인해야 한다.
- 쓰지 않는 제공자는 넣지 않는다. 넣지 않은 제공자의 버튼은 화면에 나오지 않는다.
- 확인: `npx wrangler secret list --env production`.

## 7. 운영 D1에 표 만들기(마이그레이션)

```
npx wrangler d1 migrations apply naejeon-prod --remote --env production
```

`migrations/` 폴더의 번호 순서대로 적용된다(0008은 복원·삭제 작업 잠금 열 추가). 이미 적용된 번호는 건너뛴다. 마이그레이션은 앞으로만 간다(되돌리기 없음, docs/P4 P4-2).

0020(티어 5단계)은 `participants.skill_group` 열을 새 열로 바꿔 끼운다(새 열 추가 → 값 복사 → 옛 열 삭제 → 이름 바꾸기). 표 전체를 다시 쓰므로 참가자가 많으면 잠깐 걸릴 수 있고, 운영 D1에서는 아직 돌려 보지 않았다 [미확인]. 적용 직전 시각을 적어 두면 문제가 생겼을 때 Time Travel로 그 시점에 돌릴 수 있다(13절). 적용 뒤 `SELECT skill_group, COUNT(*) FROM participants GROUP BY skill_group`이 적용 전과 같은지 본다. 이 마이그레이션과 새 코드는 함께 배포한다: 옛 코드는 5티어를 거절할 뿐 동작은 하지만, 새 코드를 0020 없이 띄우면 5티어 저장이 DB에서 거절된다.

### 7-1. 실제 D1에서 원자성 스파이크 다시 돌리기

로컬에서는 "batch 안의 보호 문장이 실패하면 batch 전체가 되돌려진다"를 확인했지만(docs/구현현황.md), 실제 D1에서는 확인하지 않았다. 첫 배포 전에 **운영 DB가 아닌 버릴 DB**에서 같은 테스트를 돌린다.

```
npx wrangler d1 create naejeon-spike
```

1. 출력된 `database_id`를 `wrangler.spike.jsonc`의 `REPLACE-WITH-SPIKE-D1-ID`에 넣는다. 이 설정은 DB 바인딩에 `"remote": true`가 있어 워커는 로컬에서, DB는 실제 Cloudflare D1에서 돈다.
2. `npx vitest run --config vitest.spike.config.ts`
3. 6개 사례가 모두 통과하면 docs/구현현황.md의 스파이크 [미확인] 항목을 갱신한다.
4. 끝나면 지운다: `npx wrangler d1 delete naejeon-spike`.

[미확인] 이 절차는 저장소에서 실제로 돌려 보지 않았다. [확인] Cloudflare 문서는 원격 바인딩(`remote: true`)을 `wrangler dev`와 `@cloudflare/vitest-plugin`이 지원한다고 적었으나 D1 예시는 없다(https://developers.cloudflare.com/workers/development-testing/). 안 되면 대안: `npx wrangler dev -c wrangler.spike.jsonc`로 띄운 뒤 같은 사례를 손으로 요청해 확인한다.

## 8. 배포

```
npm run build
npx wrangler deploy --env production
```

`npm run build`가 화면을 `dist/web`에 만들고, `wrangler deploy`가 서버와 화면을 함께 올린다. 출력에 서비스 주소가 나온다.

## 9. 배포 뒤 확인(순서대로)

1. `AUTH_MODE` 확인: `https://{주소}/api/me`를 열어 `"authMode":"oauth"`인지 본다. `"fake"`가 보이면 즉시 `npx wrangler rollback --env production` 또는 설정을 고쳐 다시 배포한다.
   - 안전장치: 운영 설정(`DEPLOY_ENV=production`)에서 `AUTH_MODE=fake`이거나 `SESSION_SECRET`이 32자 미만이거나 `PUBLIC_ORIGIN`이 올바르지 않으면 서버가 모든 API에 `CONFIG_ERROR`(503)를 돌려준다. 가짜 로그인 경로(`/api/auth/fake-login`)와 테스트 훅(`/api/test/*`)은 허용 목록으로만 열린다: `AUTH_MODE=fake`이고 `DEPLOY_ENV=local`이고 요청 주소가 localhost·127.0.0.1·`*.test`일 때만. `--env production`을 빠뜨리거나 `wrangler.spike.jsonc`를 배포해도 공개 주소에서는 404다(그래도 그런 배포는 바로 되돌린다).
   - `https://{주소}/api/health`가 503이면 위 설정 중 하나가 빠졌다. `npx wrangler tail --env production`으로 로그의 `config` 항목을 본다.
2. `/api/me`의 `providers`에 `local`(자체 계정, 끄지 않았다면)과 넣은 제공자(`kakao`, `google`)가 보이는지.
3. 휴대폰과 PC에서 로그인(카카오 또는 아이디 가입) → 모임 만들기 → 경기 하나 시작·저장 → 로그아웃 → 다시 로그인해서 같은 모임이 보이는지. 아이디로 가입했다면 복구 코드가 한 번 보이는지, 틀린 비밀번호로 "아이디 또는 비밀번호가 맞지 않아요"가 나오는지.
4. 모임 탭에서 백업 내려받기 → "백업에서 복원"에 그 파일을 골라 요약이 나오는지(실행은 하지 않아도 된다).
5. 화면 아래 "개인정보 처리방침"이 열리는지.

## 10. 출시 전에 채울 것

- `src/web/legal.ts`의 `[채워야 함]`: 운영자 이름, 연락처, 개인정보 보호책임자, 시행일. 채우기 전에는 처리방침 화면에 "초안" 표시가 나온다.
- 처리방침 문구는 코드가 실제로 저장하는 항목을 적은 **초안**이며 법률 검토를 받지 않았다. 특히 국외 이전(Cloudflare)·처리 위탁 고지 범위를 확인한다.
- Riot 제품 등록은 하지 않는다(2026-11-06 사용자 결정: 내전은 Riot 서버에 기록이 남지 않아 Riot API를 쓰지 않는다). 푸터의 비제휴 고지 문구는 유지한다.
- 카카오 로그인 버튼의 말풍선 심볼은 가이드 모양을 따라 그린 것이다. 카카오 디벨로퍼스 "리소스 다운로드"의 공식 이미지로 바꾸는 것이 가장 정확하다(`src/web/screens/Login.tsx`).

## 11. 운영 중 바꿀 수 있는 값

`wrangler.jsonc`의 `env.production.vars`(바꾼 뒤 다시 배포):

| 값 | 기본 | 뜻 |
|---|---|---|
| `SESSION_TTL_HOURS` | 720 | 로그인 유지 시간(30일) |
| `RATE_WINDOW_SECONDS` | 60 | 요청 수를 세는 구간 |
| `RATE_WRITE_PER_ACCOUNT` | 60 | 계정당 구간마다 쓰기 요청 수 |
| `RATE_WRITE_PER_IP` | 120 | IP당 구간마다 쓰기 요청 수 |
| `RATE_AUTH_PER_IP` | 20 | IP당 구간마다 로그인 요청 수 |
| `RATE_VIEW_PER_IP` | 120 | IP당 구간마다 조회 링크·인수 링크 요청 수 |
| `RATE_SIGNUP_PER_IP` | 5 | IP당 구간마다 자체 계정 가입 요청 수(가입은 "이미 쓰는 아이디"를 알려 주므로 가장 좁게) |
| `RATE_LOGIN_PER_IP` | 10 | IP당 구간마다 아이디 로그인 요청 수 |
| `RATE_RECOVER_PER_IP` | 5 | IP당 구간마다 복구 코드 확인 요청 수 |
| `RATE_CLIENT_ERROR_PER_IP` | 10 | IP당 구간마다 화면 오류 보고 수(로그인 없음, 14절) |
| `SITE_ADMIN_ACCOUNT_IDS` | (빈 값) | 사이트 운영자 계정 ID(쉼표 구분). 비어 있으면 아무도 현황 화면을 못 본다(14절) |
| `LOCAL_ACCOUNTS` | (켜짐) | `off`면 자체 계정을 끈다(4-1절) |
| `PASSWORD_PBKDF2_ITERATIONS` | 100000 | 비밀번호 해시 반복 횟수(10,000~100,000) |

아이디별 틀린 시도 제한은 코드에 고정이다(`src/server/local.ts`): 15분마다 로그인 10번, 복구 코드 5번, 로그인한 상태의 비밀번호 확인(비밀번호 바꾸기·복구 코드 새로 받기·탈퇴) 10번. 넘으면 그 15분이 끝날 때까지 맞는 비밀번호도 거절한다. 없는 아이디도 같은 방식으로 세어 아이디가 있는지 드러나지 않는다(가입만 예외: "이미 쓰는 아이디"를 알려 준다).
| `RESTORE_BATCH_BYTES` | 1048576 | 복원을 한 번에 넣는 데이터 크기 상한. 넘으면 점검 상태에서 나눠 넣는다 |
| `GROUP_DELETE_BATCH_ROWS` | 20000 | 모임 삭제를 한 번에 지우는 행 수 상한. 넘으면 점검 상태에서 나눠 지운다(지운 행도 D1 쓰기 한도에 들어간다) |

요청 수 제한은 D1 표(`rate_limits`)로 센다. 제한 대상 요청마다 D1 쓰기가 1~2행 늘어난다(무료 한도: 하루 10만 행 쓰기). 주 1회 Cloudflare 대시보드에서 D1 쓰기 수를 확인한다(docs/P4 P4-1).

## 12. 되돌리기

- 앱: `npx wrangler deployments list --env production` → `npx wrangler rollback --env production`.
- DB 전체: D1 Time Travel(무료 7일). **모든 모임이 함께 되돌아가므로** 서비스 전체 사고에만 쓴다. 한 모임은 모임 탭의 "백업에서 복원"으로 되돌린다. 자세한 절차는 13절.

## 13. 사고가 났을 때 되돌리는 법

확인한 날: 2026-11-06. 출처(Cloudflare 공식 문서):
- D1 Time Travel: https://developers.cloudflare.com/d1/reference/time-travel/
- wrangler d1 명령: https://developers.cloudflare.com/workers/wrangler/commands/d1/
- 내보내기·가져오기: https://developers.cloudflare.com/d1/best-practices/import-export-data/

### 13-1. 두 가지 되돌리기의 차이

| | D1 Time Travel(시점 복구) | 모임별 백업 내려받기·복원(이미 있음) |
|---|---|---|
| 범위 | **DB 전체**(모든 모임·계정·세션·오류 기록) | 모임 하나 |
| 누가 | 사이트 운영자(Cloudflare 계정 주인), 명령줄 | 그 모임의 대표 운영자, 화면(모임 탭) |
| 언제 쓰나 | 잘못된 배포·마이그레이션, 서비스 전체 데이터 손상 | 한 모임의 실수(잘못 지움·잘못 가져옴) |
| 파일 | 없음(Cloudflare가 보관) | JSON 파일(사용자 기기에 보관, 기간 제한 없음) |
| 부작용 | 그 시점 뒤의 **모든 모임의 기록이 사라진다** | 그 모임만 파일 시점으로 바뀐다 |

모임 하나의 문제에 Time Travel을 쓰지 않는다(다른 모임의 그 뒤 기록이 함께 사라진다).

### 13-2. D1 Time Travel에 대해 문서에서 확인한 것

- [확인] **따로 켤 필요 없이 늘 켜져 있다**("You do not need to enable Time Travel. It is always on."). 다만 DB가 production 저장 방식이어야 한다(`npx wrangler d1 info naejeon-prod --env production`에서 version이 production인지 확인). Wrangler 3.4.0 이상(이 저장소는 4.x).
- [확인] 보관 기간: **Workers Free 7일, Workers Paid 30일**("up to 30 days in the past (Workers Paid plan) or 7 days (Workers Free plan)").
- [확인] 비용 없음("Database history and restoring a database incur no additional costs.").
- [확인] 복구는 **그 자리에서 덮어쓴다**("is a destructive operation, and overwrites the database in place"). 진행 중이던 쿼리는 취소되고 오류가 난다("Queries in flight will be cancelled").
- [확인] 복구 명령은 **되돌리기용 북마크를 돌려준다**("will return a bookmark that allows you to undo and revert the database"). 이 북마크를 꼭 적어 둔다.
- [미확인] 복구에 걸리는 시간, 복구 중에 새로 들어오는 요청의 처리 방식. 문서에 없다.

### 13-3. 절차

1. **피해를 멈춘다.** 원인이 배포라면 먼저 앱을 되돌린다(12절 `wrangler rollback`). 사람들이 계속 쓰는 동안 복구하면 그 사이의 기록도 사라진다.
2. **되돌릴 시각을 정한다.** 사고 직전 시각(UTC 또는 한국 시각 +09:00을 붙인 RFC3339). 사이트 현황(`#/admin`)의 오류 기록 시각, Cloudflare 대시보드의 Workers Logs가 단서가 된다.
3. **지금 상태를 먼저 내보낸다(권장).** 복구가 틀렸을 때 손으로 살릴 자료다.
   ```
   npx wrangler d1 export naejeon-prod --remote --env production --output=./before-restore.sql
   ```
   [확인] 내보내는 동안 다른 DB 요청이 막힌다("A running export will block other database requests"). 사람이 적은 때 하거나 1번에서 서비스를 멈춘 뒤 한다. 이 파일에는 **모든 모임의 자료와 계정 정보가 들어 있으므로** 저장소·공유 폴더에 두지 않고, 다 쓰면 지운다.
4. **그 시각의 북마크를 확인한다.**
   ```
   npx wrangler d1 time-travel info naejeon-prod --env production --timestamp=2026-11-06T21:30:00+09:00
   ```
5. **복구한다.**
   ```
   npx wrangler d1 time-travel restore naejeon-prod --env production --timestamp=2026-11-06T21:30:00+09:00
   ```
   출력의 **되돌리기용 북마크를 적어 둔다.** 잘못 골랐으면 그 북마크로 다시 복구한다(`--bookmark=…`).
6. **확인한다.** 9절의 배포 뒤 확인 순서대로 로그인·모임 열기·조회 링크를 본다. 복구 시점 뒤에 가입한 계정, 만든 모임, 기록한 경기는 없어진다. 해당 모임 운영자에게 알리고, 그 사이 백업 파일을 받아 둔 모임은 "백업에서 복원"으로 채울 수 있다.
7. **마이그레이션 번호를 확인한다.** 복구 시점 뒤에 적용한 마이그레이션은 표가 되돌아가므로 `npx wrangler d1 migrations list naejeon-prod --remote --env production`으로 확인하고 필요하면 다시 적용한다. [미확인] 이 경우를 실제로 해 보지 않았다.

### 13-4. 자동 백업을 만들지 않은 이유

Time Travel이 늘 켜져 있고(무료 7일) 비용이 없어서, 따로 정기 백업(예정 작업으로 `d1 export`)을 만들지 않았다. 7일보다 오래 보관하려면 유료 요금제(30일)로 바꾸거나, 사이트 운영자가 주기적으로 3번의 `d1 export`를 손으로 받아 안전한 곳에 둔다. 예정 작업(Cron Trigger)으로 Workers 안에서 내보내는 방법은 문서에서 확인하지 않아 만들지 않았다([미확인]).

## 14. 사이트 운영자 · 오류 기록

### 14-1. 사이트 운영자 정하기

사이트 운영자는 이 서비스의 주인이다(모임의 대표·공동 운영자와 다르다). 사이트 현황 화면(`#/admin`, 상단 [로그인됨] 메뉴의 "사이트 현황")에서 전체 계정·모임·경기·참가자 수, 최근 7일·30일 활동, 오류 기록, 요청 수 제한에 걸린 횟수를 본다. **모임 이름·참가자 이름·경기 내용은 보이지 않는다**(수치만).

1. 운영 사이트에 로그인한 뒤 같은 브라우저로 `https://<서비스 주소>/api/me`를 연다. 나오는 `accountId`가 내 계정 ID다.
2. `wrangler.jsonc`의 `env.production.vars.SITE_ADMIN_ACCOUNT_IDS`에 넣는다(여러 명이면 쉼표로). 계정 ID는 비밀값이 아니라 저장소에 넣어도 된다(이 ID만으로는 로그인할 수 없다).
3. 다시 배포한다. 비어 있으면 아무도 현황 화면을 못 본다(주소로 들어와도 없는 화면처럼 첫 화면이 나오고, API는 404).

로컬에서 시험하기: 로컬 설정(`wrangler.jsonc` 맨 위 vars)에 `"SITE_ADMIN_ACCOUNT_IDS": "fake:e2e-site-admin"`이 들어 있어 개발용 로그인 이름 `e2e-site-admin`이 사이트 운영자다. 다른 이름을 쓰려면 `.dev.vars`(git 제외 파일)에 한 줄을 더한다(맨 위 vars보다 우선한다):
```
SITE_ADMIN_ACCOUNT_IDS=fake:내로그인이름
```
`fake:` 꼴은 가짜 로그인이 열린 로컬(`AUTH_MODE=fake`, `DEPLOY_ENV=local`, 로컬 주소)에서만 받는다. 운영에서는 무시된다. `.dev.vars`에 이 줄을 넣으면 브라우저 테스트(`e2e/error-admin.spec.ts`)는 실패하니 테스트 전에는 빼 둔다.

### 14-2. 오류 기록

- 화면 오류(전역 오류·처리 안 된 Promise 거절·화면 그리기 오류)는 화면이 `POST /api/client-errors`로 보내고, 서버의 예상하지 못한 오류(500)는 서버가 직접 같은 표(`error_logs`, migrations/0018)에 넣는다. 사용자 실수(4xx)는 넣지 않는다.
- **저장하지 않는 것**: 계정 ID, IP, 쿠키, 요청 본문, 참가자 이름. 경로의 토큰·ID, 메시지·스택 속 주소의 쿼리와 토큰처럼 보이는 값은 가린다(`src/shared/errorScrub.ts`). 브라우저는 종류만(예: "Chrome 모바일") 남긴다. 다만 오류 메시지 자체에 사람이 입력한 글이 섞여 있으면(드문 경우) 그대로 남을 수 있다.
- 보관 한도: **최근 1000건, 30일**(`src/server/errorLog.ts`의 `ERROR_LOG_MAX_ROWS`, `ERROR_LOG_MAX_DAYS`). 넣을 때마다 넘친 것을 지운다. 요청 수 제한에 걸린 횟수(날짜·종류별 합계만)는 30일.
- 화면은 같은 오류를 1분에 한 번, 모두 합쳐 1분에 5건까지만 보낸다(탭 기준). 서버는 IP당 구간마다 `RATE_CLIENT_ERROR_PER_IP`(기본 10)건까지 받는다. 본문은 JSON만 16KB까지, Origin 확인은 다른 쓰기와 같다.
- 현황 화면의 "오류 기록 비우기"는 표를 모두 지운다.

### 14-3. Workers Logs

`wrangler.jsonc`의 `env.production`에 `"observability": { "enabled": true, "head_sampling_rate": 1 }`을 넣었다. 서버의 `console.error` 기록(설정 오류·로그인 실패 종류·예상하지 못한 오류)을 Cloudflare 대시보드(Workers → naejeon-v2-production → Logs)에서 본다.
- [확인 2026-11-06] 형식과 환경별 설정: https://developers.cloudflare.com/workers/observability/logs/workers-logs/ . 무료 요금제 하루 200,000줄·3일 보관, 유료 월 2천만 줄·7일 보관.
- [확인] 문서에 "Starting December 1, 2026: Workers Logs will use Cloudflare Observability pricing"라는 안내가 있다. 바뀐 뒤의 한도는 [미확인]. 배포 전에 다시 확인한다.
- 오류 기록 표(14-2)와의 차이: Workers Logs는 모든 요청의 기록을 짧게(3일) 남기고 대시보드에서 찾는다. 오류 기록 표는 가린 오류만 30일·1000건까지 남기고 사이트 현황 화면에서 묶어서 본다.
