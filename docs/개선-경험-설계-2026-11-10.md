# 경험 개선 설계 (2026-11-10)

사용자가 쓴 개선안(후보 A~E)과 실행 프롬프트를 실제 소스를 읽어 수행한 설계 문서다. 구현 보고서가 아니다.
줄 번호는 2026-11-10 작업 트리 기준이라 이후 변경으로 밀릴 수 있다. 이 설계를 쓰는 동안 빌드·테스트·린트는 하나도 실행하지 않았다.

표기: [확인] 소스나 공식 문서를 직접 읽음 · [추정] 계산·가정 · [미확인].

결론: 첫 실험은 **B-1(참가자 편성 화면 개인화, 서버 변경 없음)** 과 **A 축소형(준비 화면 "직전 편성 대비" 한 줄)** 둘이다. C는 보류, D는 다음 실험 후보(과장 문구는 결함으로 분리), E는 제외다. 개선안의 전제 중 소스와 다른 것이 9가지 있어 설계를 그만큼 줄였다.

## 2. 기존 기능과 중복되어 제외한 제안
- 현재 편성의 예상 승률·라인 우위·맞대결·티어 점수(`prep/ForecastSection.tsx`), 기피·고정·서폿 횟수 꼬리표(`prep/TeamBoards.tsx` L95–101), 후보별 "최근 같은 팀 반복"(`prep/EditDialogs.tsx` L27–28), 되돌리기 5단계. A에서 다시 만들지 않는다. 새로 만드는 것은 "직전과의 차이" 하나다.
- 내 이름 고르기·내 자리 한 줄(now), 주기 확인·마지막 확인 시각·실패 시 마지막 내용 유지(live). B에서 새 화면을 만들지 않고 live 한 곳으로 모은다.
- 오늘 경기 목록·개인 오늘 성적·연승·서포터(`Today.tsx` L243–289, `sessionSummary.ts`), 시리즈 점수(`seriesPanel.tsx`). C의 2·4·5단계는 이미 있다. 없는 것은 "경기 사이에 누가 어디로 바뀌었나" 하나다.
- 근거 수치 괄호, 기준 문구, 자료 부족 보류(`commentary.ts`의 `FEW_GAMES`·`judged`). D에서 문장을 늘리지 않는다.
- 시즌 요약 이미지(`shareImage.tsx` L538), 활동 달력, 라인 오각형, 잘 맞는 동료. E·레이더·듀오 추천·시즌 결산 카드·AI 분석은 제안하지 않는다.

## 3. 사용자 장면과 현재 불편 (가설이다. 관찰한 것이 아니다)
- 운영자가 둘을 바꾸는 순간: 한 명을 누르고 다른 한 명을 누르면 즉시 바뀐다(`usePrepEditing.ts` L81–96). 예상 승률 판은 다시 계산되지만 폰에서는 섞기·진영·대기자 구역 아래에 있고(`Prep.tsx` L177–207), 바꾸기 전 숫자는 어디에도 남지 않는다. 견주려면 스크롤, 기억, "직전 편성으로", 다시 스크롤, "다시 앞으로"다.
- 참가자가 휴대폰으로 링크를 여는 순간: 열 줄에서 자기 이름을 찾는다. 강조를 받으려면 "기록 보기" → now 화면 → "내 이름 고르기" → 이름 → 다시 live다(조작 4번, 화면 전환 2번). 교체가 생겨도 바뀐 곳을 알려 주지 않는다.
- 내전이 끝난 순간: 오늘의 결과 카드가 최신순으로 쌓여 있고 "오늘 요약 공유"가 개인 승패를 준다. 이 시점에 사람들이 다시 보는지는 모른다.
- 분석 문장을 본 순간: 괄호 숫자는 있지만 어느 경기인지 열 수 없고, 기준은 마우스를 올려야 보인다. 일부 문장은 수치가 말해 주는 것보다 많이 말한다(F5).

## 4. 후보별 판단 (반대 의견 먼저)

### A 교환 전후 비교 → 축소 검증(작은 보완). 미리보기 창은 보류
반대 의견: ① 현재값 표시는 있고 차이 표시는 없다. ② 섞기·추천으로 끝내는 모임이면 거의 안 쓴다. 관찰 전에는 모른다. ③ 개선안의 안(선택 → 비교 → 적용)은 버튼이 이미 5개인 선택 줄(`TeamBoards.tsx` L172–211)에 모드를 하나 더 얹는다. ④ 더 적은 코드로 된다. 교환은 기기 안에서만 일어나고 되돌리기가 5단계라, "적용한 뒤 차이를 한 줄로 보여 주고 되돌리기를 옆에 둔다"가 미리보기와 같은 결과를 낸다. ⑤ "예상 58→52%"를 실제 효과로 읽을 수 있다. 화면 공유 중 티어 차가 보이면 두 사람의 티어 관계가 드러난다. ⑥ 서버 비용 0.
판단: ③④ 때문에 미리보기 창은 보류. 한 줄 표시는 조작을 막지 않고 떼어 내기 쉬워 관찰로 가린다.
- 조작: 전에는 교환 → 스크롤 → 기억으로 비교. 후에는 교환 → 편성 판 바로 아래 한 줄을 읽음(추가 조작 0) → 필요하면 "방금 변경 되돌리기".
- 한 문장: "직전 편성 대비 · 기피 라인 2명 → 0명 · 최근 8경기 같은 팀 반복 7 → 5 · 예상 블루 58% → 52%(MMR 추정)".
- 자료 없음: 직전 편성이 없거나(처음, 사람 교체 뒤 이력이 비워짐 `draft.ts` L332–344) 달라진 값이 없으면 줄을 그리지 않는다. 예상이 신뢰 불가(`forecast.ts` L134)면 예상 항목을, 최근 경기가 0이면 반복 항목을, 티어가 전원 미지정이면 티어 항목을 뺀다.
- 노출: 운영자 기기의 준비 화면뿐. 조회자·참가자·명단 텍스트·편성 이미지에는 없다. 티어 차는 기존의 접힌 "티어 점수 보기" 안에만 둔다.
- 모바일: 320px에서 최대 3줄. 새 카드·새 메뉴 없음. 서버 쓰기·조회·보관 0.

### B 참가자 중심 현재 경기 화면 → 채택(큰 확장). 1차는 화면만, 경량 응답은 조건부 2차
반대 의견: ① 절반은 있다. 없는 것은 live 안에서 이름 고르기, 내 자리 요약, 바뀐 자리 안내, 멈출 줄 아는 갱신, 폐기된 링크 처리, 결과 뒤 이어짐이다. ② 경기마다 열 명에게 생기는 장면이다. 다만 참가자가 링크를 여는지는 미확인. ③ 운영자 흐름은 그대로다. 참가자에게는 한 번 누르는 선택이 생기고, 안 눌러도 지금과 같다. ④ 이름 고르기만이라면 now의 창을 옮기면 된다. 나머지는 코드가 필요하다. ⑤ 이름 고르기를 로그인으로, 끊긴 화면을 최신으로 오해할 수 있다. 문구와 상태 표시로 막는다. ⑥ 304는 한도도 쓰기도 쓰지 않는다. 걱정은 큰 모임에서 바뀔 때마다 전체 스냅숏을 받는 읽기 행 수다.
판단: 채택. 1차에서는 서버·API·저장 구조를 건드리지 않는다.
- 조작: 전에는 열기 → 눈으로 찾기 → (강조를 원하면 4번 조작) → 손으로 새로 고침. 후에는 열기 → 명단에서 내 이름 한 번(첫 방문만) → 맨 위에 내 팀·라인·같은 팀·맞라인. 다음 경기가 시작되면 같은 화면이 바뀐다.
- 한 문장: "블루팀 · 미드 · 도토리(나) / 같은 팀 솔방울·밤송이·새벽별·구름빵 / 맞라인 물방울".
- 노출: 조회 토큰을 가진 누구나(지금과 같다). 운영자 초안·티어·기피·서폿 횟수는 없다(초안은 서버에 없고, 나머지는 조회 응답에 없다 `snapshot.ts` L481–493).
- 모바일: 내 자리 요약 3줄 + 기존 명단. 서버 쓰기 추가 0.

### C 내전 흐름 다시 보기 → 보류(후속)
반대 의견: ① 대부분 이미 있다. ② 내전당 한 번이고 다들 흩어지는 시점이다. 다시 보는 사람이 있는지 모른다. ③ 재생 조작이 새로 생긴다. ④ B의 "경기 없음" 상태에 "오늘 기록 보기"를 두면 최소형이 된다. ⑤ 매 판 팀이 새로 섞이는데 "팀의 흐름"처럼 읽힌다. 다시 계산한 예상·MMR을 당시 값으로 읽는다.
판단: ②④가 풀리지 않아 보류. 만들게 되면 지킬 계약: 순서는 경기 시각 → 경기 번호 / 각 단계는 그 경기에 저장된 명단만 사용 / 취소 경기는 빼고 제외·결과 미입력은 그렇게 표시 / 시리즈(같은 구성)일 때만 점수 흐름, 아니면 개인 단위(들어옴·빠짐·라인 바뀜·개인 연승)만 / MMR·예상에는 "지금 기록으로 계산" 표기 / 넘기기와 전체 목록만 두고 자동 재생 없음 / 새 화면이 아니라 `Today.tsx` "오늘의 결과" 목록의 보기 전환. 재개 조건: B의 종료 상태에서 "오늘 기록 보기"를 누르는 참가자가 관찰한 내전의 절반 이상일 때.

### D 분석 근거 펼치기 → 후속(다음 실험 1순위). 과장 문구 교정은 결함 수정으로 분리
반대 의견: ① 기준 문구는 이미 있다. ② 분석 탭을 누가 얼마나 읽는지 모른다. ③ 문장마다 펼침이 생긴다. ④ 과장은 문구 수정으로, "기준이 안 보임"은 basis를 문장 아래 작은 글씨로 내보내는 한 줄로 풀린다. 진짜 기능은 "근거 경기 목록" 하나만 남는다. ⑤ 근거 경기를 늘어놓으면 특정 경기·특정 사람 탓으로 읽힐 수 있다.
판단: 문구 교정과 basis 노출은 결함 수정으로 돌린다. 근거 경기 목록은 첫 실험 뒤로 미루고 설계만 정해 둔다.
- `Remark`(`commentary.ts` L18–24)에 `evidence?: { matchIds: string[]; scope: string; rule: string }`를 더하고, 문장의 표본 수를 `matchIds.length`로 만든다. 숫자와 목록이 같은 배열에서 나오므로 어긋날 수 없다.
- 첫 대상 셋: 강점·약점 라인(L185–205), 동료·상대(L272–304), 편성 균형(L375–401). `CommentaryCard`(`Graphs.tsx` L919–941)의 `<li>`를 `<details>`로 바꿔 범위·경기 수·규칙·경기 5줄을 편다. 새 페이지는 없다.
- 기록 화면 필터 재사용은 하지 않는다. `MatchFilter`는 사람·라인·승패·이긴 진영만 표현하고 필터 상태가 주소에 없다(`Records.tsx` L299).
- 순차 검증: "앞부분 경기만 넣어 계산한 예상과 전체로 계산한 예상이 같다"는 속성 테스트를 `test/upset.test.ts`에 더한다. 적중률은 표본 수와 함께 쓰고 "반영한다"는 판정은 하지 않는다.

### E 시즌 표지 → 제외(이번 범위)
시즌 요약 이미지가 이미 있다. 시즌당 한 번이다. 읽기 어려운 장식이 될 위험이 크다. 없어도 제품이 성립한다. 다시 꺼낼 조건: 시즌 이미지가 실제로 공유된다는 관찰이 생긴 뒤, `drawSeasonImage`(`shareImage.tsx` L538) 머리에 "칸 하나가 한 경기, 색은 이긴 진영, 묶음은 내전한 날" 띠 한 줄 정도.

## 5. 가장 먼저 검증할 큰 기능 한 개와 작은 보완 한 개

### 큰 기능: B-1 참가자 편성 화면 개인화
- 문제: 참가자가 링크를 열 때마다 자기 자리를 찾고, 바뀐 것과 끊긴 것을 알 수 없다.
- 기존 기능의 한계: 이름 고르기는 다른 화면에 있고, 갱신은 실패해도 같은 간격으로 끝없이 돌며, 폐기된 링크의 명단이 남는다(F1~F4).
- 제안: live 화면에 ① 명단 줄을 눌러 내 이름 고르기 ② 내 자리 요약 ③ 바뀐 자리 글 안내와 "바뀜" 꼬리표 ④ 상태에 따라 간격이 바뀌고 실패하면 멈추는 확인 ⑤ 404면 명단을 지우고 종료 ⑥ 결과 뒤 내 결과와 그날 성적 한 줄. 모임 화면에 "참가자 편성 링크 복사" 하나.

- 실패 처리: 6절 확인 규칙. 이 화면 조각이 깨져도 `#/v/토큰/now`는 다른 조각이라 그대로 열린다. 되돌릴 때는 `ViewerLive.tsx`와 새 파일만 이전으로 돌린다.

- 폐기 조건: ① 5명 중 2명 이상이 연 지 10초 안에 자기 팀·라인을 말하지 못함 ② 2명 이상이 남의 이름을 고르고 알아채지 못함 ③ 내전 2회 뒤에도 운영자가 매 경기 명단 글을 다시 붙여야 함 ④ 내전한 날 `#/admin`의 `view-ip` 한도 걸림이 0이 아님. ①②면 요약을 빼고 이름 고르기만 남긴다. ③이면 전체를 되돌린다. ④면 자동 확인을 끈다.

- 기존 기능의 한계: 예상 승률 판은 현재값만 보여 주고 폰에서는 편성 판에서 멀다.

- 실패 처리: 계산이 실패하면 줄을 그리지 않는다. 편성 조작과 시작 버튼은 이 계산에 기대지 않는다.

- 폐기 조건: 운영자 3명 관찰에서 ① 아무도 그 줄을 읽지 않음 ② 한 명이라도 예상 숫자를 실제 효과로 말함(예상 항목부터 뺀다) ③ 줄 때문에 섞기 버튼을 못 찾거나 스크롤이 늘었다는 반응.

## 6. 화면 흐름과 데이터·권한 계약

**B-1 화면(위에서 아래로)**
1. 조회 메뉴 줄과 점검 안내(기존).
2. 제목 "N경기 편성"과 상태 표시. 최신이면 "진행 중 · 21:40 시작", 확인이 끊겼으면 "21:42 기준"(경고 톤). 끊긴 내용을 진행 중으로 표시하지 않는다.
3. 변화 안내 한 줄(`role="status"`). 같은 경기의 교체는 "바뀐 자리: 레드 정글 밤송이 → 호두알", 새 경기는 "3경기 편성이 올라왔어요". 화면을 열어 둔 동안의 변화만 다룬다.
4. 내 자리(`<section aria-label="내 자리">`).
   - 이름을 안 골랐을 때: "아래 명단에서 내 이름을 누르면 내 자리를 먼저 보여드려요. 이 기기에서만 쓰는 표시이고 로그인이 아니에요." 이때만 명단 줄이 버튼이 된다(높이 44px 이상).
   - 골랐고 명단에 있을 때: 팀·라인·이름 / 같은 팀 4명(라인 순) / 맞라인 1명 / "이름 바꾸기".
   - 골랐지만 명단에 없을 때: "도토리 님은 N경기 명단에 없어요."와 "이름 바꾸기". 합쳐진 이름은 남은 이름으로 본다. 포지션 없는 경기는 라인·맞라인을 뺀다.
5. 명단(블루·레드). 내 줄에는 색 띠에 더해 글자 "나", 바뀐 줄에는 "바뀜" 꼬리표. 움직임은 넣지 않는다.
6. 확인 줄: "21:42 확인 · 자동으로 확인하고 있어요 [지금 확인]" / "연결이 끊겼어요. 21:40 내용이에요 [지금 확인]" / "자동 확인을 멈췄어요 [지금 확인]".
7. 경기 없음: "지금 진행 중인 경기가 없어요."(기존 문구 유지). 열린 내전이면 "다음 경기는 운영자가 시작하면 여기에 떠요." 내 자리 칸에는 "2경기 블루팀 승 · 내 팀 승리"와 "11월 10일 내전 2승 1패(확정 3경기, 결과 안 들어온 1경기 제외)". 그 아래 최근 경기 명단과 "오늘 기록 보기". 운영자가 다음 편성을 짜는 중인지는 서버가 모르므로 "준비 중"이라고 쓰지 않는다.
8. 404(링크 폐기): 명단을 지우고 "이 링크는 더 이상 열리지 않아요. 운영자에게 새 링크를 받아 주세요."만 남기고 확인을 끝낸다.

| 상태 | 간격 | 멈춤 |
|---|---|---|

모든 간격에 ±20% 흩뜨림을 준다(같은 IP의 여러 명이 같은 초에 몰리지 않게). 화면이 숨으면 타이머를 지우고, 다시 보이면(`visibilitychange`·`pageshow`·`online`) 한 번 확인한다. 겹친 요청은 순번으로 마지막 것만 반영한다. 오프라인이면 요청을 내지 않는다.

**B-1 데이터·권한 계약**
- 읽기는 기존 `GET /api/view/:token` 그대로다. 응답 모양·ETag·요청 수 제한을 바꾸지 않는다. 서버 쓰기 0.
- "내 이름"은 기존 키 `naejeon.me.<토큰>` 하나에만 저장하고 어떤 요청에도 싣지 않는다. 참가자 본인 연결(로그인 + 연결 링크)과 무관하다.
- 화면이 쓰는 값은 가장 최근 내전의 경기와 이름뿐이다. 전체 기록이 필요한 수치(MMR, 맞라인 전적)는 넣지 않는다. 나중에 경량 응답으로 바꿀 수 있게 `liveDataOf(snapshot)` 한 곳에서만 스냅숏을 읽는다.
- "그날 성적"은 그 내전의 확정 경기만 세고 그렇게 적는다.

**B-2(조건부) 경량 응답 계약**: 하루 D1 읽기가 무료 한도의 절반을 넘는 날이 생기거나 300경기 넘는 모임이 둘 이상이 되면 한다. `GET /api/view/:token/live` → `{ serverTime, group: { name, timezone, maintenance }, sessionOpen, matches, participants: { id, name }[], merged }`. 기존 조회 응답의 부분집합만 싣는다(티어는 공개 모임이어도 싣지 않는다). ETag는 `snapshotEtag(env, head, "viewer", ["live"])`, 세기는 지금처럼 200·404에서만 `view-ip`, 쓰기 없음.

**A 축소형 계약**
- 입력은 직전 자리, 지금 자리, 사람, 그리고 같은 스냅숏에서 만든 기피·서포터 횟수·최근 경기·MMR이다. 양쪽을 한 번의 호출에서 같은 입력으로 평가한다.
- 초안·서버·서포터 차례·MMR을 바꾸지 않는다(순수 함수).
- 항목 순서: 깨진 팀 조건 수 → 기피 라인에 선 사람 수 → 시작 때 확인을 묻게 될 서포터 수 → 자리가 옮겨져 풀린 고정 수 → 최근 N경기 같은 팀 반복(N은 실제로 센 경기 수) → 예상 블루 %(양쪽 다 신뢰 가능할 때만). 앞의 넷 중 나빠진 것이 있으면 줄 전체가 경고 톤이고 그 항목이 맨 앞이다. 뒤 항목이 좋아져도 가리지 않는다.
- 티어 점수 차는 이 줄에 넣지 않는다. `ForecastSection`의 접힌 영역 안에만, 운영자 스냅숏이 있을 때만 쓴다.
- 손 교환을 막지 않는 현재 규칙은 그대로다.

## 11. 운영 비용·미해결 문제·출시 전 확인

**공식 문서로 확인한 한도 [확인, 2026-11-10]** Workers 무료는 요청 10만/일, 요청당 CPU 10ms, 정적 자산 요청은 무료다. D1 무료는 읽기 500만 행/일(훑은 행 기준), 쓰기 10만 행/일이다. Durable Objects는 무료 요금제에서 SQLite 방식으로 쓸 수 있다. 출처는 developers.cloudflare.com의 workers/platform/limits, workers/static-assets/billing-and-limitations, d1/platform/pricing, durable-objects/platform/pricing.

**B-1 비용 [추정]** 참가자 한 명이 경기 한 판에 약 70번 요청한다(대기 10분 15초 간격 40번, 경기 30분 60초 간격 30번). 6경기·10명이면 저녁에 약 4,200요청(무료 한도의 4%)이다. 바뀐 것이 없으면 304라 D1 읽기 1행, 쓰기 0이다. 바뀔 때마다 보는 사람 수만큼 200이 나가고 그때 `view-ip` 쓰기 1행과 전체 스냅숏 읽기가 든다. 100경기 모임은 저녁에 약 40만 행, 522경기 모임은 약 200만 행(무료 한도의 약 40%)이다. 이 비용 구조는 지금도 같고, B는 보는 사람을 늘린다. 그래서 B-2의 실행 조건을 6절에 적었다.

**요청 수 제한** 운영의 `view-ip`는 IP당 분 30회다(`wrangler.jsonc` L90). 같은 IP에서 한 창 안에 30번 넘게 200이 나가면 429다. 한도를 올리자고 제안하지 않는다. 흩뜨림과 `retryAfter` 준수로 대응하고 `#/admin`의 한도 걸림 수로 본다.

### X1 "이 경기로 바뀐 것": 경기 상세에 열 명의 MMR 변화
반대 의견: ① 개인별 MMR 추이와 최근 10경기 변동은 있다. 경기 하나에서 열 명이 얼마씩 움직였는지는 어디에도 없다. ② 결과를 넣을 때마다 생긴다. ③ 결과 저장 뒤의 "다음 경기 준비" 버튼을 밀면 안 되므로 접힌 영역으로 둔다. ④ 계산은 이미 있다. `rating.ts` L82–90의 `RatingPoint`가 경기별 전·후·연속 가중을 갖고 있어 고르는 함수 하나와 목록 하나면 된다. ⑤ 진 경기의 큰 감점이 눈에 띄어 탓하기 소재가 될 수 있다. 같은 팀은 같은 방향이고 폭만 배치·연속 여부로 다르다는 설명을 붙인다. 과거 경기를 정정하면 뒤 경기의 값이 모두 바뀌므로 "지금 기록과 설정으로 계산"을 적는다. ⑥ 서버 비용 없음.
기존과의 차이: 손으로 넣은 결과 한 건이 열 명에게 낸 변화를 그 자리에서 보여 준다. 입력하는 사람에게 돌아오는 것이 생긴다. 연결: `Records.tsx` `MatchDetail`의 `ExpectationLine` 아래. 판단: C·E보다 먼저 볼 만하다. 첫 실험에는 넣지 않는다.
