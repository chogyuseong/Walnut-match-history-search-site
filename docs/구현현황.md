# 구현 현황 — 내전 운영 서비스 v2

작성일: 2026-11-05 · 범위: P4-7의 구현 0~7번과 보류했던 후속 기능 일부(아래 "기능 완성 작업" 절)

**먼저 읽을 것:** 이 문서의 앞부분("만든 것"~"반응형 배치")은 1차본 시점의 기록이다. 그 뒤에 추가된 기능과 현재 검증 상태는 맨 아래 "기능 완성 작업" 절이 기준이다. 두 곳이 다르면 아래 절이 맞다.

이 문서는 **만든 것, 확인한 것, 확인하지 않은 것**을 구분해 적는다. 검증은 모두 로컬 환경(로컬 Workers 실행 환경 + 로컬 D1, 헤드리스 Chromium)에서 했다. 운영 환경 배포, 실제 기기, 사용자 관찰은 **미수행**이다.

## 실행 방법

| 명령 | 하는 일 |
|---|---|
| `npm install` | 의존성 설치(버전 고정) |
| `npm run dev` | 화면 빌드 → 로컬 DB 마이그레이션 → 로컬 서버(`http://127.0.0.1:8787`) |
| `npm test` | 단위·통합 테스트 543개(32개 파일). 이 PC에서는 `npx vitest run --testTimeout=30000`으로 돌린다(부하로 5초 제한에 걸릴 수 있음) |
| `npm run e2e` | 브라우저 흐름 테스트 80개(로컬 서버를 자동으로 띄우거나 떠 있는 것을 씀). 마이그레이션을 추가한 뒤에는 떠 있는 서버를 끄고 실행해야 새 표가 적용된다 |
| `npm run typecheck` | 서버·화면 타입 검사 |
| `npm run seed` | 떠 있는 로컬 서버에 합성 데이터(가짜 이름 30명, 경기 120개, 시즌 2개)를 넣는다. 로컬 주소만 허용한다 |

로컬 로그인은 개발용 가짜 로그인이다(`AUTH_MODE=fake`). 로컬 비밀값은 `.dev.vars`에 있고 운영 값이 아니다.

## 만들지 않은 것 (1차본 시점 — 지금 상태는 맨 아래 "기능 완성 작업" 절의 "남은 것")

**배포를 막는 것**
- 실제 로그인. 지금은 개발용 가짜 로그인뿐이라 운영에 올릴 수 없다. 카카오(또는 Google) 앱 등록과 키가 필요하다.
- 운영 설정: 운영 D1 ID, 세션 서명 키, 운영에서 `AUTH_MODE`를 `fake`가 아닌 값으로 두는 것.
- Riot 제품 등록과 고지 문구, 개인정보 처리방침(P4-4의 [검증 필요] 항목).

**첫 범위 안인데 빠진 것**
- 한 경기만 넣는 지난 경기 입력 화면은 따로 만들지 않았다. 표 일괄 입력에 한 줄만 붙여 넣으면 같은 일을 한다.
- 요청 수 제한(배포 설정과 함께 정한다).

**다음 범위**
- 구현 6번의 나머지: 칭호(기존 칭호 이름과 승률 구간을 확인하지 못해 임의로 만들지 않았다), 연도별 보기.
- 표 일괄 입력의 열 형식: 지금은 임시 형식(날짜, A팀 5명, B팀 5명, 승리팀)이다. 기존 시트의 실제 열 구성을 받으면 읽는 부분(`parseMatchTable`)만 바꾼다.
- 일괄 입력은 모임 탭의 기록 목록에서 한 번에 전적 제외하고 복구할 수 있다. 여러 묶음 중간에 끊기면 "이어서 넣기"로 같은 요청을 다시 보내며 이미 들어간 묶음은 다시 들어가지 않는다.
- 구현 7번의 나머지: 키보드·확대 대응 확인, 넓은 화면 2단 배치.
- 복원·가져오기, 레거시 이관(시트 스냅샷이 있어야 설계 가능).

## 사용자 확인 사항 (2026-11-05)

- 개인이 여는 5:5 사용자 설정 게임은 Riot 공개 기록에 남지 않는다. 수동 입력이 기록을 남기는 기본 수단이다.
- 기존 서비스의 상단 메뉴: 이름 검색, 팀 편성, 경기 기록, 소환사 랭킹, 그래프 분석, 표 일괄 입력, 구글 시트 연결, 내전 라운지·시즌.
- "내전 라운지"는 만들지 않는다.
- "표 일괄 입력"은 구글 시트에 기록해 둔 사용자가 시트를 연결하면 기록이 채워지던 통로였다. v2에서는 시트 연결을 없앴으므로 붙여넣기 방식의 일괄 입력으로 대체한다(형식 대기 중).
- 기존 그래프 분석 화면(스크린샷): 개인별 승률(라인 선택), 라인별 승률(플레이어 선택), 진영별 누적 승률, 플레이어 × 라인. 전체 522경기이고 라인 정보가 모두 있다.
- 기존 배치 기준은 50전이었다. v2는 기준 문서대로 10경기다.
- 기존 진영 기록은 실제 진영이 아니라 자리 기준이다("왼쪽 팀은 블루… 가져온 표의 위 5명(A팀)은 블루, 아래 5명(B팀)은 레드"). 이관할 때 이 진영을 그대로 옮길지 "진영 미상"으로 옮길지는 결정이 필요하다.

**확인하지 못한 것**
- 자체 계정의 비밀번호 해시 계산은 로컬에서 한 번에 30~33ms였다. Cloudflare 무료 요금제의 요청당 CPU 10ms 한도에 걸릴 수 있다. 배포해서 확인해야 하며, 걸리면 `PASSWORD_PBKDF2_ITERATIONS`를 낮추거나 유료 요금제를 쓴다. 반복 횟수 상한 10만 회는 공식 문서가 아니라 외부 보고에 근거한 값이다.
- 실제 카카오·Google과의 연동(테스트는 제공자 응답을 가짜로 대체). 카카오에서 회원번호만 쓰는 앱이 검수 없이 운영 가능한지.
- 운영 D1에서의 동작 전부(batch 원자성, 큰 복원·삭제의 단계 실행 시간과 한도).
- 실제 휴대폰, iOS Safari, 실제 화면 키보드, 파일 공유(Web Share).
- 실제 사용 시트로 가져오기. 열 자동 추정은 실제 시트 형식을 받아야 맞출 수 있다. 공개 예제 시트로 읽기 경로만 확인했다.

**알려진 한계**
- 비공개 구글 시트는 읽지 못한다. 시트의 탭 목록을 고를 수 없어 탭마다 주소를 붙여 넣어야 한다.

- 시각 열이 없는 시트에서 오늘 날짜인 줄은 낮 12시 전에 가져오면 "아직 오지 않은 시각"으로 막힌다.
- 로그아웃하면 그 계정의 모든 기기에서 로그아웃된다.
- 자체 계정은 이메일을 받지 않으므로, 복구 코드를 적어 두지 않고 비밀번호를 잊으면 계정을 되찾을 수 없다.
- 참가자 개인이 자기 기록만 지우는 기능은 없다(운영자에게 요청).
- 글꼴 무결성 검사는 CSS만 대상이고 글꼴 파일 자체는 검사하지 않는다.

**만들지 않은 것**

- 기존 시트 데이터의 자동 이관 절차: 시트 가져오기 기능으로 대체한다. 기존 진영 기록(자리 기준)을 그대로 옮길지 "진영 미상"으로 옮길지는 가져올 때 고른다.

### 스스로 정한 것과 이유

- **한 계정 여러 모임**: 서버는 이미 계정당 모임 5개까지 다루고 `/api/me`도 목록을 준다. 그러나 화면에는 모임을 고르는 곳이 없고 기기에 기억한 모임(없으면 첫 모임)만 연다. 고르는 화면을 만드는 것은 범위가 커서, **이미 모임이 있는 계정(대표든 공동이든)의 초대 수락은 안내 문구와 함께 거절**한다(`HAS_GROUP`). `/api/me`에는 공동 운영 모임도 역할과 함께 넣어 화면이 열고, 대표 전용 버튼을 숨기는 데 쓴다.
- 대표는 "나가기"로 나갈 수 없다(넘기거나 삭제). 공동 운영자의 모임 이름 바꾸기·조회 링크 다시 만들기·백업 내려받기는 "같은 일"에 넣었다.
- 넘기기를 받은 순간 이전 대표의 쓰지 않은 공동 운영자 초대 링크를 지운다(권한을 잃은 사람이 만든 링크가 남지 않게).
- 초대·내보내기는 요청 ID 중복 방지(`runMutation`)를 쓰지 않는다: 운영자 넘기기와 같은 방식이며 다시 보내도 결과가 같다(새 링크 / 이미 없음 404).
- 서포터 고르기 규칙에서 서포터 자리에 고정된 사람은 그대로 둔다. 시작 전 공평 판단에서 비교 대상은 같은 팀의 고정 아닌 사람이다.
- 팀 상태는 `all-assigned`를 가장 먼저 본다(서포터 자리가 고정이어도 팀 5명이 모두 갔으면 초기화 안내 대상).

### 팀 섞기 점검 (2026-11-06 추가)

- **대량 무작위 점검**(`test/draft-fuzz.test.ts`): 시드 1,500개 × 조작 20~40번(올랜덤, 올랜덤 + 서포터 공평하게, 서포터만 바꾸기, 라인 다시 뽑기(`rerollPositions`), 팀 추천 적용, 좌우 바꾸기, 진영 선택·랜덤, 직전 편성으로, 포지션 고정, 같은 팀·다른 팀 조건 추가·삭제, 두 사람 맞바꾸기)을 무작위 순서로, 모두 45,519단계. 서포터 횟수 문맥도 무작위(0회가 많은 경우 ~ 대부분 1회 이상, 직접 입력 보정값으로 횟수와 'used' 사건이 어긋난 경우 포함)다. 매 단계 확인: 10명·팀당 5명·팀 안 포지션 5개, 사람이 사라지거나 겹치지 않음, 고정 포지션 유지(풀리는 것은 팀 추천 적용에서 같은 팀 고정이 겹친 뒤 사람뿐. 섞기는 고정을 풀지 않음), **섞기 전후로 각 팀의 5명이 반드시 같음**(팀원을 바꾸는 것은 좌우 바꾸기·팀 추천·자리 바꾸기·교체뿐), 섞기는 조건과 무관(어기는 조건이 전후로 같음), 서포터만 바꾸기는 팀 구성과 나머지 8명을 바꾸지 않고 새 서포터는 0회·비고정, 바꿀 수 없는 팀(모두 배정받음·고정·지금 서포터만 남음)은 그대로, 공평 섞기 뒤 0회 비고정이 있는 팀의 서포터는 0회, 좌우 바꾸기 두 번 = 원래(진영 포함), 되돌리기가 조작 직전 자리를 정확히 복원, 초기화 버튼 조건 = 모두 배정받은 팀 있음, 이번 주기 'used' 서포터는 반복 확인(묻기)이나 공평한 반복(ack) 중 정확히 한쪽에 들어감, 같은 시드·같은 조작 = 같은 결과. 이 범위에서 불변식을 깨는 경우는 나오지 않았다.
- **치우침 점검**: 올랜덤 8,000번에서 각 사람이 팀 안에서 각 포지션에 갈 비율 20%±2.5%p(팀은 바뀌지 않으므로 팀 A 비율은 보지 않는다). 이어서 누른 올랜덤 6,000번도 같다. 서포터만 바꾸기는 0회 후보 세 명이 각 1/3±3%p, 공평 섞기의 0회 후보 선택도 기대값과 2%p 안이다.
- **실제 화면**(`e2e/prep-walkthrough.spec.ts`, 로컬 테스트 모임): 10명 고르기 → 올랜덤(팀원 그대로) → 진영 고르기·좌우 바꾸기(진영이 팀을 따라감)·진영 랜덤 → 포지션 고정 + 올랜덤 3번 → 직전 편성으로 → 같은 팀 조건 + 올랜덤 5번(팀원이 바뀌지 않음) → 팀 추천 적용(조건을 지킴) → 서포터만 바꾸기 6번 연타(같은 결과 유지) → 올랜덤 + 서포터 공평하게로 경기 시작·결과 저장·다음 준비를 반복. 서포터가 겹치지 않고, 반복 확인 창 없이 시작되고, 매 단계 알림·초기화 버튼 상태가 "모두 배정받은 팀 있음"과 맞는지 본다. "이 팀으로 시작" 두 번 누르기는 경기 1개만 만든다(일회성 확인).
- 스크린샷(390·1440px × 다크·라이트, 상태별)을 눈으로 확인했다.

- 팀 추천 적용은 같은 팀에서 고정 포지션이 겹치면 뒤 사람의 고정을 말없이 푼다(문서화된 동작, 알림은 없다). 라인 섞기는 팀원이 그대로라 고정이 겹칠 일이 없다.

#### 스스로 정한 것과 이유

- **가중치 합 차 허용 폭 = 서로 다른 가중치 사이의 가장 작은 간격**(기본 [4,3,2,1]이면 1, 가중치가 모두 같으면 0. `priorityTolerance`). 순위별 인원 차 ≤ 1을 지키면 합 차는 홀수 인원 칸의 "남는 한 명"들을 어느 팀에 두느냐로만 달라지고(홀수 칸이 2개면 서로 다른 팀으로 강제, 4개면 짝짓기 3가지), 같은 칸 안에서 누가 어느 팀에 가는지는 여전히 자유라 후보가 충분하다(아래 테스트: 배치 7가지 모두 200번 누르면 팀 A 구성 8가지 이상). 예: 1·2·3·4순위 한 명씩 + 미지정 6명이면 항상 1·4순위가 한 팀, 2·3순위가 다른 팀. 기본 가중치에서는 사실상 최소값만 남고, 가중치를 바꾼 모임이나 미지정 중앙값이 .5인 경우에 한 칸 안쪽의 근소한 차이를 같은 후보로 본다.

#### 스스로 정한 것과 이유

- **보정값 k = 10**(배치 기준과 같음): 막 배치를 마친 사람(10경기)은 실제 승률과 50%의 딱 중간이 되고, 경기가 쌓일수록 실제 승률에 가까워진다. 예: 10전 10승(75%)보다 100전 80승(77%)이 위.
- 4등분은 floor(i×4/n)+1(10명이면 3·2·3·2명). 보정 승률이 완전히 같은 사람은 같은 순위(경계에서 ID 순으로 갈리지 않게). 이름 비교는 기기 언어와 무관하게 코드 단위.
- 적용은 일괄 API를 새로 만들지 않고 기존 참가자 수정 API를 한 명씩 부른다(서버 변경 금지). 중간에 실패하면 앞사람까지 저장되고 오류를 보여 준 뒤 다시 읽는다.
- 저장 형식: 쉼표 문자열(기존 표의 단순 열 관례, 정렬해 저장하므로 같은 값은 같은 글자). 응답·백업은 배열.
- 순위 점검의 "자료 적음" 기준은 합이 달랐던 경기 수 5경기(기존 `SMALL_SAMPLE`).
- 섞기 알림에서 고정한 사람은 기피 라인이어도 빼고 세고(사용자가 직접 고정), 명단의 "기피" 표시는 고정 여부와 상관없이 붙인다.
- 기피는 팀을 나누는 데는 쓰지 않는다(팀까지 올랜덤의 순위 균형·조건 규칙 그대로). 라인을 뽑을 때만 쓴다.

#### 스스로 정한 것과 이유

- **진영을 모르는 경기는 "팀 A/팀 B"와 중립 테두리 그대로**: 진영 미상으로 가져온 기록에 블루·레드를 붙이면 사실이 아닌 정보를 보여 주게 된다.
- **예전 초안 `red`는 두 팀을 맞바꿔 정규화**: 그 초안에서 블루로 정해 둔 5명이 계속 블루가 되도록(사람 기준으로 진영 유지). 화면 좌우는 바뀐다.
- **"진영 바꾸기" 버튼은 섞기 구역의 같은 자리**에 두었다(이름만 바꿈). "진영" 구역에는 안내 한 줄과 "진영 랜덤"만 남았다.
- **결과 입력 1단계의 " 승"**: 진영이 정해진 경기만 "블루팀 승"처럼 붙인다(정정 창도 같음). 진영을 "기억나지 않음"으로 고르면 저장 후 진영 미상 경기가 되므로 요약은 "팀 A 승 · 진영 미상"으로 쓴다.
- **경기 카드 줄 머리는 "블루"/"레드"**(2글자): 좁은 카드(1.6~2.5rem 칸)에 "블루팀"이 들어가지 않아서다. 전체 이름은 그룹 이름(`aria-label` "블루팀 승리")에 있다.

#### 검증하지 못한 것 · 걸리는 점

- 준비 화면 390·1440px × 다크·라이트, 팀 상자 바이올렛(deeplol)·진행 화면 스크린샷을 눈으로 확인했다(테두리 색·제목 한 줄). 명도 대비 수치 자동 점검은 하지 않았다(기존 토큰만 사용).
- 예전 경기 중 진영이 "A = 레드"인 것은 왼쪽이 레드팀으로 보인다(좌우를 바꾸지 않는 규칙). 블루가 늘 왼쪽이라고 기대하면 헷갈릴 수 있다.
- 단위 테스트의 일부 제목·코드 주석에는 "좌우 바꾸기" 같은 예전 이름이 남아 있다.

### "우선순위" → "티어" 이름 변경 (2026-11-06 추가)

사용자 결정으로 화면의 "우선순위·N순위"를 "티어·N티어"로 바꿨다(1티어가 가장 잘하는 사람). 화면 주소(`#/priority`), 파일 이름(`priority.ts`, `Priority.tsx`), 코드·DB 이름(`skillGroup` / `skill_group`)은 그대로다. 이 문서의 앞 절들은 당시 이름("우선순위", 그 전에는 "실력 그룹")으로 적혀 있다. 순위 점검의 "순위 합"은 "티어 점수 합"으로 적었다(1티어의 점수가 가장 높다는 뜻이 드러나게). 랭킹의 "순위"는 다른 말이라 그대로다.

사용자 결정(같은 날): 내전용 실력 점수(MMR)는 만들지 않는다. 내전은 잘하는 사람과 못하는 사람이 섞여 팀이 되는 구조라 의미가 없다고 판단했고, 운영자가 직접 정하는 4티어와 그 균형 편성·추천을 쓴다.
