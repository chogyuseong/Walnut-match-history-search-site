## 2. 기존 데이터 형태

[사실] 전부 미확인이다. 아래는 스냅샷을 받으면 확인할 항목과, 결과가 v2 설계에 미치는 영향이다.

| 확인 항목 | 상태 | v2에 미치는 영향 [제안] |
|---|---|---|
| 경기 레코드 필드 | 미확인 | 경기 ID가 없으면 이관 시 생성하고 원본 행 위치를 함께 보존한다 |
| 진영 기록 유무 | 미확인 | 없으면 전 경기를 "진영 미상"으로 이관한다. 개인 승패는 유지되고 진영 통계에서만 빠진다 |
| 진영이 팀 자리와 묶여 있는지 | 미확인 | "왼쪽 팀 = 블루"로 저장되어 있었다면 진영 값을 신뢰할 수 없어 미상 처리가 안전하다 |
| 포지션 기록 유무 | 미확인 | 없으면 라인별 통계는 이관 경기에서 "기록 없음"이다 |
| 경기 수 | 미확인 | 10판 배치 재계산 결과와 수작업 정리 가능 여부를 좌우한다 |
| 이름 표기 불일치 유형 | 미확인 | 참가자 레코드 ID로 묶는 매핑표가 필요하다. 예상 유형: 공백·대소문자, 닉네임 변경, 별칭, 동명이인 |
| 삭제·정정 이력 | 미확인 | 없으면 이관 시점 상태를 최초 이력으로 삼는다 |
| 서포터 순환 이력 | 미확인 | 순환은 세션 단위이므로 이관하지 않는 것이 기본이다 |

반대 의견: 진영을 일괄 미상 처리하면 실제로 정확했던 기록까지 버린다. → 답: 스냅샷에서 진영이 팀 자리와 독립적으로 입력된 사실이 확인되면 그대로 이관한다. 확인 전에는 판단하지 않는다.

## 3. 유지 / 분리 / 이전 / 폐기

기존 코드를 보지 못했으므로 "코드 단위"가 아니라 "개념 단위" 분류다. [제안]

| 분류 | 대상 | 근거 | 반대 의견과 답 |
|---|---|---|---|
| 유지 | 4그룹, 서포터 사람 기준 순환, 포지션 무작위, 승률별 칭호, 통계 항목 | §1 확정 규칙, P2-11 | 값(가중치·구간)을 모르면 유지라 할 수 없다 → 규칙의 틀만 유지하고 값은 모임 설정으로 둔다 |
| 분리 | 팀 A·B / 실제 진영 | §1 | 입력이 한 단계 늘어난다 → 승리 팀 선택 직후 한 번만 묻고 미상을 허용한다 |
| 분리 | 현재 경기 / 다음 초안 | §1 | 화면이 둘로 나뉘어 헷갈릴 수 있다 → P3에서 화면별 주요 행동을 1개로 제한한다 |
| 분리 | 기기 초안 / 서버 확정, 공용 설정 / 기기 설정 | P2-4 | 상태 표시가 늘어난다 → 사용자에게는 "서버 확인됨 / 이 기기에만 있음" 두 문구로 줄인다 |
| 분리 | 날짜 문자열 / 세션 ID, 이름 / 참가자 ID | P2-1 | 기존 데이터에 ID가 없다 → 이관 시 한 번 생성한다 |
| 이전 | 경기 기록, 참가자, 그룹 지정, 규칙 값 | P4-3 | 이름 정리 비용이 가치보다 클 수 있다 → 결정 요청 2에서 범위를 정한다 |
| 폐기 | Sheets + Apps Script 저장 계층 | F2, 불편 4·5 | 운영자가 시트로 직접 고치던 자유도가 사라진다 → 내보내기와 항목별 정정으로 대체한다 |
| 폐기 | 모임별 연결 설정 절차 | 불편 1·4 | 데이터 소유권이 서비스로 넘어간다 → 백업 파일을 운영자가 언제든 받을 수 있게 한다 |
| 폐기 | "원본 읽기·가져오기·공용 저장" 개념의 사용자 노출 | 불편 5 | 숙련 운영자는 기존 용어에 익숙하다 → 원본을 하나로 만들면 용어 자체가 필요 없다 |

## 4. 반복된 불편의 원인 계층 재분류

원인 계층 정의:
- **L1 원본** — 무엇이 기준 데이터인지
- **L2 저장 규약** — 요청·확인·재시도·버전
- **L3 인증·연결** — 누구의 어느 모임인지
- **L4 상태 모델** — 초안·진행·확정의 구분
- **L5 화면 구조**
- **L6 검증 절차**

불편 목록은 [사실](기준 문서 기재)이고, 원인 추정은 모두 [검증 필요]다. 마지막 열은 문구·배치 변경(해법 1종)만으로 풀리는지에 대한 판단이다.

| # | 불편 | 원인 계층 | 추정 원인 | 문구·배치만으로 해결 |
|---|---|---|---|---|
| 1 | 접속마다 재연결 | L3 | 연결 정보가 기기에만 있고 계정–모임 귀속이 서버에 없다 | 불가 |
| 2 | 기록이 사라진 듯 보임 | L2·L4 | 읽기 실패·빈 데이터·캐시·미저장 초안이 같은 빈 화면으로 보인다 | 불가. 상태 구분이 먼저 있어야 문구를 붙일 수 있다 |
| 3 | 저장 완료 판단 불가 | L2 | 서버 확인 응답과 화면 표시가 연결되지 않고, 요청을 식별할 ID가 없다 | 불가 |
| 4 | Sheets·Apps Script 설정 부담 | L3 | 모임마다 저장소를 직접 구성하는 호스팅 모델 | 불가. 호스팅 모델 변경으로 제거 |
| 5 | 원본 읽기·가져오기·공용 저장 혼동 | L1 | 원본이 여러 곳(시트, 브라우저, 가져온 사본)이라 저장 경로 선택이 사용자에게 넘어갔다 | 불가. 설명을 늘릴수록 불편 9가 커진다 |
| 6 | 실제 명단과 화면 불일치 우려 | L1·L4 | 확정 명단이 경기 ID에 고정되지 않고 편집 중인 편성과 같은 데이터를 쓴다 | 불가 |
| 7 | 참가자 선택 중 화면 닫힘 | L4·L5 | 데이터 갱신이 화면을 다시 그리면서 입력 중 상태를 버린다 | 불가. 초안을 화면 상태와 분리해야 한다 |
| 8 | 모바일 잘림 | L5 | 표 중심 배치와 한 화면의 정보량 | 일부 가능. 표를 카드로 바꾸는 것은 구조 변경이다 |
| 9 | 버튼·설명 과다 | L1·L4의 결과 | 저장 경로와 상태가 여럿이라 각각 버튼과 설명이 붙었다 | 불가. 원인을 줄여야 버튼이 줄어든다 |
| 10 | 검증 범위와 완료 보고 불일치 | L6 | 독립 환경 검사와 운영 환경 검사를 구분하지 않고 "완료"로 보고했다 | 불가. 보고 양식에 검증 종류와 "미수행"을 강제한다 |

[제안] 10개 중 8개가 L1~L4에 걸려 있다. 화면 개선보다 **원본 단일화, 요청 ID와 버전, 계정–모임 귀속, 초안·확정 분리**를 먼저 설계해야 하며, 이것이 P2가 핵심 단계인 이유와 일치한다.

반대 의견: 코드를 보지 않은 원인 추정으로 설계 방향을 정하는 것은 위험하다. → 답: v2는 재구축이므로 기존 코드의 정확한 결함 위치는 설계 입력이 아니다. 불편 목록 자체가 입력이고, 추정이 틀려도 P2의 불변식(초안·확정 분리, 요청 ID, 서버 권한 검사)은 기준 문서가 이미 요구한다. 다만 저장소를 받으면 이 표를 실제 근거로 다시 쓴다.

## 5. 기준 문서 안에서 발견한 확인 사항

- [사실] §1은 운영자 모델 기본값을 "활성 운영자 1명"으로 두는데, P1 결정 요청에는 "다중 운영자 전제 유지 여부"가 있다. P1에서 1명 기본값을 전제로 다시 묻겠다.
- [사실] P1 결정 요청은 서포터 순환의 v1 포함 여부를 묻는데, P4-7 구현 우선순위 3번은 순환 표시를 전제한다. P1 결정에 따라 P4 순서를 조정한다.

## 6. 결정 요청

"다음"이라고만 답하면 아래 권장 기본값을 모두 채택한다.

| # | 결정 | 선택지 | 권장 기본값 | 이유 |
|---|---|---|---|---|
| 1 | 제공 자료 | 저장소 전체 / 시트 스냅샷 / 없음 | **없음** (기준 문서 규정) | 자료 없이도 P1·P2는 진행된다. 단, 저장소나 스냅샷을 주면 2절과 4절의 미확인이 대부분 해소되므로 P0을 다시 쓴다 |
| 2 | 레거시 이관 범위 | 전부 / 특정 날짜 이후 / 이관 안 함 | **전부 이관** (독립 환경 대조 통과 후, 없는 필드는 "미상"·"기록 없음") | 배치와 칭호가 모임 전체 누적 기준이라 일부만 옮기면 기존 참가자의 배치 상태와 칭호가 달라진다 |
| 3 | 운영자 모델 | — | 활성 운영자 1명, 조회자 N명 | 동시 편집 없이도 버전 검사로 여러 기기 문제를 처리한다 |
| 4 | 호스팅 모델 | — | 단일 멀티테넌트 | 불편 1·4의 원인을 없앤다 |
| 5 | 규모 가정 | — | 모임 50개 이하, 주 1~2회, 회당 3~8경기, 모임당 30명 이하 | 무료·저가 구간에서 운영 가능한 규모다 |
| 6 | 월 비용 상한 | — | 합산 월 2만 원 이하 | 개발자 1명이 수익 없이 유지할 수 있는 수준이다 |
| 7 | 운영자 인증 | — | 매직 링크 또는 OAuth 1종, 비밀번호 저장 없음 | 비밀번호 관리와 분실 지원 부담을 없앤다 |
| 8 | 시즌 | — | 겹치지 않는 날짜 구간, 통계 필터 전용 | 배치·칭호와 분리해 재계산 규칙을 단순하게 유지한다 |

결정 2의 반대 의견: 경기 수가 많고 이름 불일치가 심하면 정리 비용이 크다. → 답: 스냅샷 확인 후 수작업 매핑이 감당할 수 없는 규모로 드러나면 "특정 날짜 이후"로 줄이고, 그때 배치·칭호가 어떻게 달라지는지 참가자별로 미리 보여준다. 이관 실행 시점은 P4에서 따로 결정한다.
