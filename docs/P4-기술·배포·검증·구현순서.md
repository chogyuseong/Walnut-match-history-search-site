작성일: 2026-11-05 · 선행: P0~P3 문서

## P4-1. 기술 스택

### P2가 요구하는 것

한 요청 안의 원자적 다중 행 쓰기(시작), 조건부 유일 제약, 버전 비교 후 쓰기, 모임 단위 격리, 서버 권한 검사, 주 1~2회 쓰는 모임이 며칠 쉬어도 바로 열리는 것. 실시간 통신·서버 렌더링·별도 캐시 계층은 요구되지 않으므로 넣지 않는다.

### 후보 비교

| | A. Cloudflare Workers + D1 | B. Supabase(Postgres) + 정적 프런트 | C. 소형 서버 1대 + SQLite/Postgres |
|---|---|---|---|
| 데이터·트랜잭션 | [사실] D1 `batch()`는 SQL 트랜잭션이며 한 문장이 실패하면 전체를 되돌린다. 대화형 트랜잭션(BEGIN/COMMIT)은 문서에 없다 | Postgres 함수로 완전한 트랜잭션 | 완전한 트랜잭션 |
| 혼자 유지 | 서버 관리 없음. 배포는 명령 하나 | 서버 관리 없음. 권한을 행 수준 정책과 함수 양쪽에 써야 함 | 운영체제 갱신·백업·감시를 직접 |
| 비용 | [사실] 무료: 요청 10만/일, 호출당 CPU 10ms, D1 읽기 500만 행/일·쓰기 10만 행/일·5GB. 정적 자산 요청 무료. 유료 최소 월 5달러 | [사실] 무료: DB 500MB, **1주 비활성 시 일시 정지**, 자동 백업 미포함. Pro 월 25달러부터 | 미확인(제공사별). 월 고정비 발생 |
| 복구 | [사실] Time Travel 상시 켜짐, 무료 7일·유료 30일. 복구는 DB 전체를 덮어쓴다 | 무료는 백업 없음. Pro는 일일 백업 7일 | 직접 구성 |
| 이전 가능성 | SQLite 방언 SQL. 내보내기 가능 | 표준 Postgres | 표준 |
| 상한 2만 원 | 무료 또는 5달러로 충족 | 무료는 정지·무백업, Pro는 상한 초과 | [검증 필요] |

### 추천: A

- B의 무료 요금제는 주 1회 쓰는 모임이 한 주 쉬면 정지될 수 있고 백업이 없다. Pro는 비용 상한을 넘는다.
- C는 완전한 트랜잭션을 주지만 "개발자 한 명이 지속 운영"에서 서버 관리가 가장 큰 부담이다.
- A의 약점은 대화형 트랜잭션이 없다는 점이다. 시작 요청은 **읽기로 검증한 뒤, 버전 비교 문장을 포함한 `batch()` 하나로 쓰는** 방식으로 구현한다. 버전이 달라졌으면 batch 안의 보호 문장이 제약 위반으로 실패해 전체가 되돌려지게 한다.
- [검증 필요] 이 보호 문장 방식이 D1에서 의도대로 전체를 되돌리는지는 확인하지 않았다. **구현 첫 작업으로 스파이크**를 두고, 실패하면 모임별 Durable Object(SQLite 저장, [사실] 무료 요금제 사용 가능)로 쓰기를 직렬화하거나 C로 바꾼다.

반대: 특정 회사의 실행 환경에 묶인다. → 답: 서버 코드는 표준 요청·응답 처리와 SQL뿐이고, 데이터는 백업 형식(P4-3)으로 언제든 내보낸다. 이전 비용은 DB 접근 계층 교체에 한정된다.

### 구성

| 층 | 선택 | 근거 |
|---|---|---|
| 프런트 | TypeScript + React + Vite, 단일 페이지 앱. 서버 렌더링 없음 | 초안·추천·추첨이 기기에서 돈다. 생태계가 가장 넓다 |
| 백엔드 | Workers 위의 얇은 라우터(Hono), 직접 작성한 SQL | 쓰기 경로가 열 개 남짓이다 |
| DB | D1 한 개, 모든 표에 모임 ID | 모임 50개에 DB를 나눌 이유가 없다 |
| 인증 | OAuth 1종, 서버가 서명한 세션 쿠키(HttpOnly) | 메일 발송 서비스가 필요 없고 한 번 눌러 끝난다 |
| 테스트 | Vitest(단위·로컬 workerd 통합), Playwright(너비별 흐름) | 로컬에서 실제 실행 환경과 같은 D1을 쓴다 |
| 배포 | Wrangler로 Workers와 정적 자산을 함께 배포 | 산출물이 하나다 |

- 버전: 각 도구의 현재 안정 버전 번호는 이 문서에서 **확인하지 않았다**. 구현 첫 작업에서 공식 릴리스 페이지를 확인해 잠금 파일로 고정한다. 실험 표시가 붙은 기능은 저장 경로에 쓰지 않는다.
- 인증 수단: 카카오 로그인을 우선 검토한다(국내 지인 모임, 모바일에서 한 번 누름). 식별자만 받고 이메일은 받지 않는다. [검증 필요] 카카오 개발자 포럼에는 개인 개발자의 비즈 앱 전환·이메일 항목 심사 사례가 엇갈려 올라와 있다(2026-11-05 검색). 식별자만 쓰는 경우의 요건은 공식 가이드로 확인하지 못했다. 막히면 Google 로그인으로 바꾼다.
- 외부 의존: Cloudflare 장애 시 서비스 전체가 멈춘다. 초안은 기기에 있어 편성과 명단 텍스트 복사는 계속된다. 무료 한도를 넘으면 D1이 오류를 돌려주므로([사실]) 일일 요청·쓰기 수를 주 1회 확인하고, 한도의 50%에 닿으면 유료(월 5달러)로 전환한다.

## P4-2. 로컬 실행과 배포 산출물

- 로컬: `npm run dev` 하나로 로컬 Workers와 로컬 D1이 뜬다. [사실] 로컬 D1은 운영 DB와 분리되어 있고 `--local`로 마이그레이션을 적용한다.
- 합성 데이터: `npm run seed`가 가짜 이름 30명과 경기 120개(배치 경계, 진영 미상, 제외, 대기 포함)를 넣는다. 실제 이름·전적은 쓰지 않는다.
- 설정: 운영 주소·OAuth 비밀값은 저장소에 없고 배포 환경의 비밀 저장소에만 있다. 로컬 기본값은 가짜 로그인 제공자를 가리킨다.
- 산출물: Worker 묶음 1개 + 정적 자산 디렉터리 + 번호가 붙은 SQL 마이그레이션.
- DB 변경 순서: **확장 → 앱 배포 → 정리**. 새 열·표를 먼저 추가하고(이전 앱이 계속 동작), 앱을 배포한 뒤, 다음 배포에서 쓰지 않는 것을 지운다.
- 앱 롤백과 DB 복구는 별개다. 앱은 이전 버전으로 되돌린다. 마이그레이션은 앞으로만 간다. 롤백 가능 조건은 "직전 앱 버전이 현재 스키마에서 동작"이며 배포 전 통합 테스트로 확인한다.
- DB 전체 복구(Time Travel)는 **모든 모임을 함께 되돌리므로** 서비스 전체 사고에만 쓴다. 한 모임의 복구는 백업 파일로 한다.

## P4-3. 백업·복원·이주

- 백업 파일(JSON): 형식 버전, 생성 시각, 모임 ID·이름, 범위, 경기 수, 참가자, 경기·명단, 변경 이력, 세션, 순환 주기·사건, 설정 버전. **제외**: 계정, 운영자 권한, 조회 토큰, 세션 쿠키, 요청 기록.
- 운영자는 "모임" 탭에서 언제든 내려받는다(출시 필수).
- 서비스 측 백업: Time Travel 7일 + 주 1회 전체 내보내기를 서비스 운영자가 수동으로 받아 보관한다. 자동화는 모임 수가 늘어 수동이 부담될 때 한다.
- **같은 모임 복구**: ID를 그대로 쓰고 그 모임의 경기·참가자·이력을 파일 내용으로 바꾼다. 운영자와 토큰은 바뀌지 않는다.
- **새 모임 가져오기**: 모든 ID를 새로 만들고 파일 안의 참조(명단→참가자, 사건→경기)를 대응표로 바꾼다.
- 적용 절차: 파일 전체를 먼저 검증(형식 버전, 경기 수 일치, 모든 참조 해소, 경기당 10명·팀당 5명) → 대상 모임과 영향 범위("경기 212개가 198개로 바뀝니다") 확인 → 현재 상태 자동 백업 → 모임을 점검 상태로 전환(쓰기 거절) → 한 batch로 적용 → 진행 상태 버전을 올림 → 점검 해제. 검증에 실패한 파일은 아무것도 바꾸지 않는다. 버전이 올라가므로 열려 있던 탭의 요청은 거절된다.
- v1에서 복원은 서비스 운영자가 스크립트로 수행한다(운영자용 복원 화면은 후속).
- 레거시 이주: 시트 내보내기 → 변환 스크립트(이름 대응표는 사람이 검토) → 백업 형식 파일 → **빈 로컬 환경**에 가져오기 → 경기 수, 사람별 승·패, 기존 화면의 통계와 대조. 배치는 10판 기준으로 다시 계산된 결과를 사람별로 나열해 보여준다. 운영 전환은 대조 통과 뒤 **별도 승인**을 받는다. [사실] 시트 구조가 미확인이라 변환 스크립트 설계는 스냅샷을 받은 뒤에 한다.

## P4-4. 운영·지원

| 상황 | 사용자가 해결 | 서비스 운영자 개입 |
|---|---|---|
| 로그인 실패 | 다시 시도, 다른 브라우저 | 제공자 장애 공지 |
| 운영자 교체 | 인수 링크 발급·수락 | — |
| 운영자 부재 | — | 모임원 2명 이상의 요청과 조회 링크 보유 확인 뒤 수동 이전. 7일 대기 |
| 가져오기 오류 | 오류 줄 번호를 보고 파일 수정 | 형식 문의 응답 |
| 실수로 전적 제외 | 제외 목록에서 복구 | — |
| 저장 불확실 | "확인하기" | 요청 ID로 로그 조회 |
| 충돌 | 최신 확인 후 다시 저장 | — |
| 장기 미사용 모임 | — | 12개월 미접속 시 운영자에게 알리고 보관. 삭제는 요청이 있을 때만 |
| 반복 요청·비용 증가 | — | 계정·IP별 요청 수 제한, 한도 50%에서 유료 전환 |

- 안내 형식: 화면 상태 → 확인할 것 → 조치 → 성공 확인 → 안 되면 다음 조치.
- 로그: 요청 ID, 작업, 시각, 모임 ID, 버전, 결과, 오류 분류. 이름·토큰·세션은 남기지 않는다.
- 측정 후보(모두 **가설·목표이며 실제 값은 없다**): 첫 경기 완료 비율, 다음 내전 재사용 여부, 경기당 조작 수, 정정에 걸린 시간, "결과 확인 불가" 발생 수, 끝내 미입력으로 남은 대기 경기 비율, 지원 요청 수, 모임당 비용.
- 유료화는 재사용과 유지 비용이 확인된 뒤에 검토한다. 내보내기, 전적 제외 복구, 권한 보호는 유료 기능으로 만들지 않는다.
- [검증 필요] Riot 개발자 문서는 플레이어에게 서비스를 제공하는 제품의 등록과 비제휴 고지 문구를 요구한다(P1 확인). 출시 전에 등록 절차와 고지 문구 원문을 다시 확인한다.
- [검증 필요] 로그인 식별자와 참가자 닉네임을 저장하므로 개인정보 처리방침과 삭제 요청 경로가 필요하다. 법률 검토는 미수행이다.

## P4-5. 검증 시나리오

종류 약어: **단**(단위) · **통**(로컬 workerd + D1 통합) · **독**(독립 배포 환경) · **기**(실제 기기) · **관**(사용자 관찰) · **리**(코드 리뷰). 모두 미수행이며 "독"과 "기"는 통합 통과 뒤에 한다.

### 경기·진영·저장

| # | 초기 상태 | 요청 순서 | 서버 결과 | 화면 기대 | 종류 |
|---|---|---|---|---|---|
| 1 | 3경기 진행 중, 4경기 초안 | 초안의 팀 변경 → 3경기 결과 저장 | 3경기 명단 불변, 결과는 3경기에 | 요약에 시작 때 명단 | 통·기 |
| 2 | 진행 중 | 팀 A 승, 진영 레드 | 승리 팀 A, 팀 A의 진영 레드 | "팀 A 승 · 레드", 팀 B는 블루 | 통 |
| 3 | 결과 창, 팀 A·블루 선택 | 승리 팀을 B로 변경 | 요청 없음 | 진영 선택이 비워지고 저장 비활성 | 단·기 |
| 4 | 진영 미상으로 확정 | 진영만 레드로 정정 | 승패 불변, 진영 통계에 포함, 이력 1행 | 영향 안내 "개인 승패는 유지" | 통 |
| 5 | 시작 응답 유실 | 같은 요청 ID로 재전송 2회 | 경기 1개, 순환 사건 2개 | "확인하기" 뒤 진행 화면 | 통 |
| 6 | 초안에 무효 참가자 1명 | 시작 | 거절. 경기·명단·사건·버전 모두 불변 | 누구 때문인지 표시, 초안 유지 | 통 |
| 7 | 결과 저장 응답 유실 | 확인하기 → 재시도 | 결과 1회만 기록, 이력 1행 | "저장됨"은 확인 뒤에만 | 통·기 |
| 8 | 1경기 확정 | 같은 명단·같은 승패를 새 요청 ID로 시작·확정 | 2경기 생성 | 목록에 두 경기 | 통 |

## P4-6. 사용자 관찰 계획 (사람이 수행)

- 대상: 이 서비스를 처음 보는 내전 운영자 3~5명과 각 모임의 참가자 1명.
- 운영자 과제(설명 없이): 10명 입력 → 팀·서포터 결정 → 경기 시작 → 승리 팀·진영 저장 → 진영 오입력 정정 → 다음 경기 준비 → 이전 기록 확인.
- 참가자 과제: 받은 링크로 자기 팀·포지션 확인.
- 기록 양식(과제마다): 멈춘 지점, 한 질문, 잘못 누른 것, 되돌아간 횟수, 걸린 시간, 정정 성공 여부. 추가로 다음 판 준비에서 고른 방식(같은 팀 / 포지션 유지 / 다시 짜기)을 센다.
- 출시 판단은 네 질문을 따로 답한다: 기술적으로 안전한가(P4-5 통과) / 설명 없이 쓰는가(관찰) / 다음 내전에서 다시 쓰는가(2주 뒤 접속) / 비용과 지원을 감당하는가(측정). 앞의 하나가 통과했다고 뒤의 것을 통과로 보지 않는다.

## P4-8. 마지막 질문

- **사용자가 하지 않아도 되는 일**: 시트 연결과 재연결, 저장 경로 고르기, 매번 10명 재입력, 명단을 채팅에 옮겨 적기, 틀린 결과를 지우고 다시 넣기, 서포터를 누가 했는지 기억하기.
- **대신 이해해야 하는 것**: ① "이 기기에만 있어요"와 "저장됨"의 차이 ② 팀 A·B와 블루·레드가 다르다는 것 ③ 결과 없는 경기는 통계에 아직 없다는 것.
- **편익이 더 큰 근거**: 세 개념은 모두 화면의 글자 한 줄로 드러나고, 각각이 기존 불편(저장 완료 판단 불가, 명단 불일치, 기록이 사라진 듯 보임)의 원인을 없앤다. 다만 이것은 설계상의 추론이며 관찰로 확인하지 않았다.
- **실패 가능성이 큰 이유 세 가지**: ① 자동 수집을 하는 경쟁 서비스가 이미 있어 수동 입력이 번거롭게 느껴질 수 있다. ② 로그인이 10명이 기다리는 순간에 끼어든다. ③ 운영자 한 사람에게 의존해 그 사람이 그만두면 모임 전체가 떠난다.
- **가장 적은 비용으로 확인할 방법**: P1의 가설 1·5(운영자 5명 재현, 기존 사용자에게 통계 사용 여부 질문)는 개발 없이 된다. 그다음은 구현 0~2번까지만 만든 상태로 실제 내전 1회에 쓰게 하는 것이다.
- **설계를 철회할 관찰 결과**: 운영자 5명 중 4명 이상이 기존 방식으로 충분하다고 하거나 이미 자동 수집 도구에 정착해 있을 때. 첫 내전 뒤 2주 안에 다시 연 모임이 절반에 못 미칠 때. 결과 대기 경기의 절반 이상이 끝내 입력되지 않을 때(이 경우 대기 기능만 철회).
- **첫 구현에서 완성할 흐름**: 이름 10개 → 팀 구성 → 이 팀으로 시작 → 승리 팀·진영 저장 → 오늘의 결과 확인 → 틀린 진영 정정.
- **의도적으로 보류할 기능**: 결과 이미지, 조합 다양성, 운영자용 복원 화면, 참가자 계정, 중복 참가자 합치기, 고정 팀 시리즈, 집계 캐시, 실시간 갱신, Riot API 연동.
- **사용자 결정이 필요한 항목**: 아래 결정 요청.

| 6 | 서비스 측 백업 | Time Travel 7일 + 주 1회 수동 전체 내보내기 | 모임 50개 이하에서는 수동 절차로 충분하다 |

결정 4의 반대 의견: 순환(3번)은 출시 필수가 아니므로 첫 범위에서 빼면 더 빨리 관찰할 수 있다. → 답: 타당하다. 빨리 관찰하는 것이 우선이면 **0·1·2·4번만** 먼저 만들고 3번을 뒤로 미루는 안을 고를 수 있다. 권장 기본값을 0~4로 둔 이유는 제품 한 문장이 서포터 차례를 약속하기 때문이다.
