# 내전로그 제품 완성도 개선 작업 요청

이 저장소의 제품 엔지니어로 일해 주세요. 내전로그의 사용자는 경기 직후 휴대폰으로 결과를 입력하는 운영자와, 공유받은 링크에서 내 자리나 지난 경기를 찾는 참가자입니다. 이번 작업의 목표는 두 사람이 이미 한 일을 반복하는 순간을 줄이는 것입니다. 우선순위는 **기록 보존 → 탐색 맥락 보존 → 화면 간 일관성** 순입니다.

## 시작할 때

1. `CLAUDE.md`, `package.json`, `배포-이어하기.txt`의 최신 항목을 읽고 현재 브랜치와 작업 트리를 확인하세요. 첫 방문 기능 미리보기, 초성·날짜·메모 검색, 최근 검색어, 기록 필터 주소 복원, 결과 임시 저장, 편성 넘기기는 이미 있습니다.
2. 아래 세 과제를 코드에서 확인하세요. 관찰한 사실과 아직 재현하지 않은 가설을 구분하세요. 각 과제에 대해 사용자 행동, 현재 결과, 기대 결과를 한 줄씩 쓰세요. 이미 만족하는 조건은 기존 코드나 테스트 위치를 적고 넘어가세요.
3. 한 번에 실행할 기본 범위는 가장 높은 우선순위의 재현 가능한 과제 하나입니다. 해당 과제를 구현하고 검증까지 마치세요. 나머지 과제는 다음 작업자가 바로 이어갈 수 있게 재현 경로와 완료 기준을 남기세요. 심각한 문제가 발견되면 실제 영향과 재현 근거로 순서를 조정하세요.

## 1순위 · 작성하던 경기 결과를 믿고 이어 쓰기

**시작점** — `src/web/resultDraft.ts`의 읽기 함수는 JSON 파싱 후 저장 시각과 3일 만료를 확인합니다. `src/web/screens/ResultSheet.tsx`에서 복원할 때는 챔피언 목록이 객체라고 가정하고 순회합니다. 쓰기 함수는 기기 저장소 오류를 잡아 입력을 계속하게 합니다. 실제로 어떤 경우에 사용자가 입력을 잃거나 창을 열 수 없는지 먼저 재현하세요.

- 로컬 경기 하나에서 승리 팀·메모·챔피언을 입력하고 창을 닫았다 다시 여세요. 같은 경기에 정상 초안, 만료된 초안, 저장 시각은 유효하지만 챔피언 필드가 빠진 초안을 각각 준비하세요. 실제 진입점에서 ‘이어 쓰기’를 눌러 결과를 관찰하세요.
- 읽기 경계에서 승리 팀과 진영의 허용값, 메모와 챔피언 목록의 자료형을 확인하세요. 안전하게 복원할 수 있는 메모·선택은 살리고, 신뢰할 수 없는 승패 정보는 운영자가 다시 선택하게 하세요. 잘못된 초안 하나가 다른 경기·모임의 초안이나 결과 입력 화면에 영향을 주지 않아야 합니다.
- 저장소 쓰기가 거절된 상황에서는 현재 창의 입력을 유지하세요. 실제 복구 가능 여부에 맞게 안내하고, 정상 입력 때마다 토스트를 띄우지 마세요. 초안의 기기 저장과 서버의 경기 결과 확정이 화면에서 구분되어야 합니다.
- 다른 운영자가 명단을 교체한 경우와 이미 결과를 확정한 경우를 나누어 보세요. 현재 명단에 있는 참가자만 복원하고, 서버의 최신 상태와 기존 버전 충돌 처리를 따르세요. 응답이 끊긴 경우의 저장 여부는 서버 상태로 확인하세요. 같은 경기 결과를 자동으로 다시 제출하지 마세요.
- **완료 기준** — 정상 초안은 그대로 복원되고 저장 성공 후 지워집니다. 손상된 초안으로 열어도 결과 창이 동작하며, 승리 팀을 고르지 않고 확정할 수 없습니다. 저장소 차단 상태에서도 현재 창 안에서 결과를 입력할 수 있습니다. 순수 읽기 검증은 단위 테스트로, 창 열기부터 복원까지는 기존 `e2e/browse-memory.spec.ts`를 활용해 검증하세요.

## 2순위 · 검색 결과의 21번째 경기에서 돌아오기

**시작점** — `src/web/screens/Search.tsx`는 경기 결과를 20개씩 표시합니다. 검색어는 주소에 남지만 표시 개수는 컴포넌트 상태에 있습니다. 기록 목록에서 구현한 복원 동작은 `src/web/screens/Records.tsx`, `src/web/scrollMemory.ts`, `e2e/browse-memory.spec.ts`에서 비교하세요.

- 동일한 메모로 찾을 수 있는 경기 25개 이상을 로컬에 준비하세요. 검색 → 더 보기 → 21번째 이후 경기 열기 → 브라우저 뒤로 가기를 실행하세요. 검색어, 표시 개수, 방금 누른 경기의 가시성, 키보드 초점 중 어느 것이 사라지는지 확인하세요.
- 돌아왔을 때 같은 경기를 다시 찾아 스크롤할 필요가 없어야 합니다. 검색어를 바꾸거나 다른 모임으로 이동하면 앞 목록의 펼침 상태가 따라가지 않아야 합니다. 스크롤 좌표를 먼저 복원했다가 목록이 뒤늦게 늘어나는 순서 문제도 확인하세요.
- 검색어 입력에 따라 `newestFirst(matchesInScope(...))`가 다시 실행되는 경로가 있습니다. 긴 기록에서 문제가 있는지 동일 데이터와 브라우저 조건으로 측정하세요. 개선이 필요하면 정렬을 스냅숏 변경 시점으로 분리하는 작은 변경부터 비교하세요. 측정에는 입력 후 결과가 그려질 때까지의 시간, 데이터 건수와 반복 횟수를 적으세요.
- **완료 기준** — 모바일에서 뒤로 한 번이면 이전 대상이 보이고, 키보드 사용자도 그 지점에서 탐색을 이어갈 수 있습니다. 운영자·모임 링크·예시 화면의 주소와 한글 조합 중 Enter 동작을 보존하세요. 기존 `e2e/search-jump.spec.ts`와 새 회귀 사례 하나로 확인하세요.

## 3순위 · 화면을 넘겨도 통계 숫자의 뜻이 이어지게 하기

**시작점** — ‘기록’에서는 오늘·시즌·전체 범위를 고를 수 있고, 검색은 전체 누적 기록을 사용합니다. 공통 기준 표시는 `src/web/screenKit.tsx`, 통계 집계는 `src/shared`에 있습니다. 먼저 같은 참가자에 대해 각 화면이 답하는 질문을 적으세요.

- 확정 경기와 미확정 경기를 모두 가진 참가자, 아직 배치 중인 참가자, 확정 경기가 없는 참가자를 준비하세요. ‘기록 → 개인 통계 → 두 사람 비교’와 ‘검색 → 참가 경기 보기’를 각각 따라가세요.
- 각 화면에서 기간, 경기 수의 분모, 승률, 배치 상태, 뒤로 돌아온 범위를 작은 표에 기록하세요. 서로 다른 범위를 보여 주는 것이 의도라면 그 이유를 사용자가 이동 직후 읽을 수 있는지 확인하세요. 예를 들어 오늘 2경기에서 누적 40경기로 전환된다면 숫자 옆이나 제목에서 그 전환이 드러나야 합니다.
- 같은 범위인데 값이 다르면 집계 규칙부터 추적하세요. 값은 일치하고 설명만 부족하면 가장 가까운 기존 라벨을 고치세요. 확정 경기가 없는 사람의 승률이 0% 패배 기록처럼 읽히지 않는지도 확인하세요.
- **완료 기준** — 동일한 범위와 대상에서는 숫자가 일치하고, 범위가 바뀌면 사용자가 화면에서 이유를 알 수 있습니다. 모임 링크에서 운영자 전용 티어가 노출되지 않아야 합니다. 계산식 변경이 필요하다고 판단하면 기존 기록에 미치는 영향을 먼저 제시하세요.

## 구현과 인수 확인

- 기존 컴포넌트·집계 함수·디자인 토큰을 재사용하세요. 화면을 수정하면 390×844에서 먼저 흐름을 끝까지 실행한 뒤 768×1024와 1440×900에서 확인하세요. 다크·라이트 테마, 긴 한글 이름, 키보드 초점, 고정 하단 메뉴에 가려지는 주 행동을 점검하세요.
- 성능과 기록 복원 실험은 로컬 합성 데이터로 실행하세요. 첫 화면 번들 예산은 `npm run check:bundle`의 실제 기준으로 판정하세요. 배포용 데이터베이스에 테스트 경기를 만들 필요가 없습니다.
- 바꾼 코드에 따라 타입 검사, 린트, 관련 단위 테스트와 E2E, 빌드, 번들 검사를 실행하세요. CSS 변경이 있으면 `npm run audit:design`도 실행하세요.
- 최종 보고는 **사용자에게 달라진 행동 / 재현 전후 / 변경 파일 / 검증 결과 / 남은 과제** 순서로 작성하세요. 실행하지 못한 검사는 이유를 적고, 수치는 직접 측정한 것만 쓰세요. 배포까지 요청받은 경우 저장소의 스테이징 → 운영 절차를 따라 실제 주소에서 변경한 흐름을 확인하세요.
