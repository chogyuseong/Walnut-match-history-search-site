## P1-1. 사용 장면 5개 (모두 가설)

아래는 관찰이나 인터뷰가 아니라 설계자가 세운 가설이다. 따옴표 안의 말은 "할 법한 말"이다.

**장면 1 — 첫 사용 운영자의 첫 경기**
- 누가·기기·시점: 모임에서 팀을 짜 오던 사람. PC 앞에서 롤 클라이언트와 디스코드를 켠 채 휴대폰으로 연다. 10명이 음성 채널에 모여 기다리는 중이다.
- 하려는 것: 지금 있는 10명의 팀과 포지션을 빨리 정해 방에 초대한다.
- 멈추는 곳: 가입·모임 만들기·실력 그룹 입력을 먼저 요구받는 순간. 또는 이름 10개를 하나씩 입력해야 하는 순간.
- 할 법한 말: "일단 팀부터 짜고 싶은데 뭘 이렇게 물어봐. 그냥 카톡 사다리 타자."

**장면 2 — 2주차 반복 사용**
- 누가·기기·시점: 같은 운영자, 휴대폰, 두 번째 내전 날 시작 직전.
- 하려는 것: 지난번 사람들에서 두 명만 바꿔 바로 시작한다.
- 멈추는 곳: 다시 로그인해야 하거나, 지난 참가자가 안 보여 이름을 처음부터 넣어야 할 때. 지난주 마지막 경기가 "진행 중"으로 남아 새 경기를 막을 때.
- 할 법한 말: "저번에 넣었는데 왜 또 넣어. 저번 판 아직 안 끝난 걸로 돼 있네?"

**장면 3 — 결과 저장 직후 진영 오입력 발견**
- 누가·기기·시점: 운영자, 휴대폰, 다음 판 밴픽이 시작된 직후.
- 하려는 것: 방금 블루로 저장한 승리 팀이 사실 레드였다는 것을 고친다.
- 멈추는 곳: 방금 저장한 경기를 찾을 수 없거나, 고치면 승패까지 뒤집힐까 불안할 때. 삭제 후 재입력밖에 길이 없을 때.
- 할 법한 말: "진영만 바꾸고 싶은데 이거 누르면 전적 꼬이는 거 아냐?"

**장면 4 — 참가자가 링크로 자기 포지션 확인**
- 누가·기기·시점: 참가자, 휴대폰 또는 디스코드 내장 브라우저, 방 초대를 기다리는 중.
- 하려는 것: 내가 어느 팀이고 어느 라인인지 확인한다.
- 멈추는 곳: 로그인을 요구받거나, 열린 화면이 지난 판 명단인지 이번 판인지 알 수 없을 때.
- 할 법한 말: "나 어디야? 이거 아까 판 아니야?"

**장면 5 — 자정 넘긴 마지막 경기**
- 누가·기기·시점: 운영자, PC, 00:40. 23:50에 시작한 경기가 방금 끝났고 모두 바로 나간다.
- 하려는 것: 마지막 결과를 넣거나, 내일 넣는다.
- 멈추는 곳: 결과가 "오늘" 목록에 안 보이고 새 날짜로 갈라질 때. 내일 열었더니 어느 팀이 이겼는지는 기억나지만 진영은 기억나지 않을 때.
- 할 법한 말: "어제 5판 했는데 왜 4판이야? 블루였나 레드였나 모르겠는데."

[제안] 다섯 장면이 공통으로 요구하는 것은 ① 준비 없이 시작 ② 경기와 날짜의 분리 ③ 항목별 정정 ④ 가입 없는 조회 ⑤ 끝났지만 결과가 없는 경기를 다루는 방법이다. ⑤가 후보 B의 근거다.

### 읽는 법

- [제안] 기능 수로는 Scrim이 앞선다. 자동 수집은 수동 입력보다 정확하고 챔피언·KDA까지 남긴다. v2가 이길 수 있는 지점은 기능이 아니라 **준비물**이다: 설치 없음, 참가자 가입 없음, 휴대폰만으로 승리 팀과 진영을 두 번 눌러 기록.
- [제안] 따라서 v2의 존재 이유는 "자동 수집을 쓸 수 없거나 쓰기 싫은 모임이 충분히 있는가"에 달려 있다. 이것이 아래 가설 1이다.
- [사실: 사용자 제공, 2026-11-05. 독립 확인 미수행] 개인이 여는 5:5 사용자 설정 게임은 Riot의 공개 전적 기록에 남지 않는다. 따라서 ① 일반 전적 사이트에 내전이 보이지 않는 것은 정책 이전에 데이터가 없기 때문이고 ② 내전 기록은 누군가 직접 입력하거나, Scrim처럼 참가자 PC의 롤 클라이언트에서 읽어 오는 수밖에 없으며 ③ 범위 밖으로 둔 Riot API 연동은 후속에서도 내전 결과를 자동으로 가져오는 수단이 되기 어렵다. [검증 필요] 클라이언트에서 읽는 방식은 그 경기에 참가한 사람이 PC에서 수집기를 실행해야 할 것으로 보이나 확인하지 않았다.
- [제안] 이 사실은 v2의 전제를 강화한다. 수동 입력은 자동 수집의 열등한 대체재가 아니라, 설치 없이 기록을 남기는 유일한 방법이다.
- 반대 의견: 준비물이 적다는 것은 수기 운영도 마찬가지다. → 답: 수기와의 차이는 확정 명단이 남고 서포터 차례가 사람 기준으로 이어진다는 점이다. 이 차이가 체감되지 않으면 가설 3이 기각된다.

### 다섯 가설과 가장 싼 확인 방법

| # | 가설 | 가장 적은 비용으로 확인하는 방법 | 기각 신호 |
|---|---|---|---|
| 1 | 기존 방식에서 바꿀 만큼 불편이 크다 | 다른 지인 모임 운영자 5명에게 지난 내전의 팀 짜기부터 기록까지를 그대로 재현해 달라고 한다. 걸린 시간, 기록하지 않은 판 수, 다툼이 난 지점을 적는다. 개발 없음 | 5명 중 4명 이상이 "지금도 충분하다"거나 이미 Scrim·봇에 정착 |
| 2 | 운영자 혼자 도입할 수 있다 | 클릭 가능한 화면 시안(코드 없음)을 주고 설명 없이 "10명으로 첫 경기 시작"까지 가는지 본다 | 가입·모임 생성 단계에서 절반 이상 멈춤 |
| 3 | 기록이 없는 첫날에도 가치가 있다 | 이름 입력 → 팀·포지션 배정 → 명단 텍스트 복사만 되는 한 화면을 실제 내전 1회에 쓰게 한다. 저장 기능 없이도 끝까지 쓰는지 본다 | 두 번째 판부터 수기로 돌아감 |
| 4 | 다음 내전에서 다시 쓴다 | 가설 3의 모임에 재사용을 요청하지 않고 2주 뒤 접속 여부만 확인한다 | 재접속 없음 |
| 5 | 기록이 쌓이면 가치가 커진다 | 천안호두.GG 사용자에게 "지난달 어떤 통계 화면을 열었고 그걸로 무엇을 했는지" 묻는다. 기존 데이터가 있으므로 개발이 필요 없다 | 기억나는 화면이 랭킹 하나뿐이고 행동 변화가 없음 |

[제안] 가설 1과 5는 개발 전에 확인할 수 있으므로 P2와 병행해 사람이 수행하기를 권한다. 미수행 상태로 P2를 진행해도 설계는 막히지 않는다.

### 정책 확인 사항

[사실] Riot 개발자 문서(League of Legends, 2026-11-05 확인)에는 다음 문구가 있다.
- 플레이어에게 서비스를 제공하는 제품은 공식 API 사용 여부와 무관하게 등록해야 한다.
- Riot 로고·상표는 보도 자료집 범위에서 불가피한 경우에만 쓰고, 비제휴 고지 문구를 잘 보이는 곳에 둔다.
- 사용자 설정 게임의 경기 기록은 당사자가 동의하지 않으면 공개 표시할 수 없다.

[검증 필요] 세 번째 규칙이 API에서 가져온 데이터에만 적용되는지, 운영자가 손으로 입력한 기록에도 적용되는지는 미확인이다. v1은 API를 쓰지 않고 공개 전체 랭킹도 범위 밖이지만, 제품 등록 의무와 고지 문구는 P4-4에서 다시 확인한다.

## P1-3. 추가 후보 A~D 결정

분류 정의: **채택**(v1 상태 모델에 포함) / **제한 검증**(최소 형태로 넣고 관찰 결과로 유지 여부 결정) / **후속**(연결 지점만 설계) / **제외**.

### 결정 요약

| 후보 | 결정 | 목표 | 한 줄 이유 |
|---|---|---|---|
| A. 다음 판 준비 | **채택** (세 방식을 기본 1개 + 조정 2개로 축소) | 반복 입력 감소 | 참가자 10명 재입력이 가장 큰 반복 조작이다 |
| B. 결과 입력 대기 | **채택** (최소 형태) | 기록 누락 방지 | "끝났는데 진행 중"인 경기는 B가 없어도 생긴다. 이름을 붙여 다루는 편이 안전하다 |
| C. 명단 전달 | 링크·텍스트 **채택**, 결과 이미지 **후속** | 반복 입력 감소 | 참가자 조회 링크는 P2-9가 이미 요구한다. 이미지는 실패 경로가 많다 |
| D. 기록 변화 이유 | **채택** (경기별 이력 + 모임 변경 목록 한 화면), 통계 화면 연동 안내는 **후속** | 변경 이유 설명 | 정정 이력은 P2-7 때문에 어차피 저장한다. 보여주는 비용만 든다 |

### A. 다음 판 준비 — 채택

해법 비교:
1. 문구·기본값: "다음 경기 준비" 버튼이 직전 참가자를 미리 채운다 → 팀을 매번 다시 짜야 한다.
2. 통합: 방식 ①②③을 따로 고르게 하지 않고, **기본 동작 하나**(같은 팀, 포지션은 다시 무작위)와 조정 두 개("포지션 유지", "팀 다시 짜기")로 합친다. ← 선택
3. 새 기능: 세 방식을 각각 버튼으로 제공 → 선택지 세 개를 매 판 읽어야 한다.

기본을 ②로 두는 이유: [사실] 확정 규칙상 포지션은 고정분 외 완전 무작위다. 포지션을 그대로 두는 ①을 기본으로 삼으면 규칙과 어긋난다. [제안] 팀은 유지해 두면 버리는 데 한 번, 다시 만드는 데 여러 번이 든다. [검증 필요] 세 방식의 실제 빈도는 미확인이며 P4-6 관찰에서 센다. ③이 과반이면 기본을 바꾼다.

| 질문 | 답 |
|---|---|
| 제거되는 입력·판단 | 참가자 10명 재선택, 팀 재구성 |
| 새로 이해해야 하는 것 | "다음 경기 준비"는 초안이며 아직 시작이 아니다 |
| 기존 기능과 중복 | "지난 참가자 불러오기"와 겹친다 → 세션 안에서는 A, 세션 사이에서는 불러오기로 역할을 나눈다 |
| 데이터·권한·통계 영향 | 초안만 만든다. 통계 영향 없음. 운영자 전용 |
| 모바일 공간 | 결과 저장 직후 화면에 버튼 1개 |
| 지원 부담 | 낮음. "왜 포지션이 바뀌었나"는 문의 가능 → 초안에 "포지션은 새로 뽑았어요" 한 줄 |
| 최소 검증 | 복사 금지 항목이 새 초안에 하나도 없는지 통합 테스트 |
| 보류·삭제 조건 | 관찰에서 운영자가 초안을 매번 전부 다시 짜면 "참가자만 유지"로 축소 |

- 복사 가능: 참가자, 팀 구성, 명시적으로 고정한 포지션·조건, ("포지션 유지"를 켠 경우에만) 포지션.
- 복사 금지: 경기 ID, 승패, 진영 확정값, 요청 ID, 완료 상태, 순환 사용 사건, 이전 추첨 결과.
- 순환이 켜진 상태에서 "포지션 유지"를 고르면 직전 서포터가 그대로 남으므로, 시작 전에 반복 배정 여부를 검사해 알린다.
- "같은 팀"은 팀 A·B 구성이 같다는 뜻이다. 진영은 복사하지 않고 결과 저장 때 다시 묻는다.
- 다음 초안이 이미 있으면 버튼은 "다음 초안 열기"가 되고, 새로 만들려면 "현재 초안을 버리고 다시 만들기"를 따로 눌러야 한다.
- 합치거나 제거할 요소: 방식 선택 화면을 만들지 않는다. "참가자 초기화" 단독 버튼을 두지 않는다.
- 반대 의견: 팀을 유지하는 기본값은 매번 팀을 섞는 모임에 한 번의 추가 조작을 강요한다. → 답: 추가 조작은 "팀 다시 짜기" 한 번이고, 반대 기본값이면 재대결 모임은 10명을 다시 배치해야 한다. 비용이 비대칭이다.

### B. 결과 입력 대기 — 채택 (최소 형태)

해법 비교:
1. 문구: 진행 중 경기를 그대로 두고 "결과를 입력해 주세요"만 표시 → 다음 경기를 시작할 수 없다(진행 중 1개 제한 가정).
2. 통합: 다음 경기 시작 창에서 직전 결과를 강제로 묻는다 → 서두르는 운영자가 추측으로 입력하거나 경기를 취소한다. 틀린 기록이 생긴다.
3. 새 상태: "결과 입력 대기"를 둔다. ← 선택

새 상태를 고르는 이유: [제안] 장면 5처럼 끝났지만 결과가 없는 경기는 B가 없어도 "진행 중"이라는 틀린 이름으로 존재한다. B는 상태를 늘린다기보다 이미 있는 상황에 맞는 이름을 붙이고, 그 상태에서 무엇이 허용되는지를 정한다.

| 질문 | 답 |
|---|---|
| 제거되는 입력·판단 | 다음 판 직전에 결과를 급히 넣는 일, "취소할까 대충 넣을까" 판단 |
| 새로 이해해야 하는 것 | 결과 없는 경기는 통계에 아직 없다. 홈에 "결과 미입력 N경기"가 남는다 |
| 기존 기능과 중복 | "지난 경기 입력"과 혼동 가능 → 대기 경기는 명단이 이미 확정돼 있어 승리 팀·진영만 묻는다. 지난 경기 입력은 명단부터 넣는 별도 경로다 |
| 데이터·권한·통계 영향 | 확정 통계·배치 판수에 미포함. 서포터 사용 이력은 유지(차례는 시작 때 이미 소비됨). 운영자 전용 |
| 모바일 공간 | 진행 중 화면에 보조 행동 1개, 홈에 알림 1줄 |
| 지원 부담 | 중간. "판수가 안 맞는다"는 문의가 예상된다 → 오늘 목록에 대기 경기를 "결과 미입력"으로 함께 보여준다 |
| 최소 검증 | 대기 상태에서 다음 경기 시작, 대기 경기 결과 입력 후 배치 판수 증가, 순환 이력 불변 |
| 보류·삭제 조건 | 관찰에서 대기 경기의 절반 이상이 끝내 미입력으로 남으면, 시작 창에서 결과를 묻는 방식(해법 2)으로 바꾼다 |

- 승리 팀 미상과 진영 미상의 구분: 승리 팀을 모르면 경기는 **대기 상태에 머문다**(별도의 "승리 팀 미상 확정"은 만들지 않는다). 승리 팀은 알고 진영만 모르면 **진영 미상으로 확정**한다.
- 대기 경기를 끝내 기록하지 않으려면 "전적 제외"로 닫는다. 서포터 차례는 유지된다.
- 동시 경기 제한에 통합: 진행 중 1개 제한은 유지하고, 대기 경기는 그 제한에 포함하지 않는다. 대기 경기 수 상한은 P2에서 정한다.
- 합치거나 제거할 요소: 진행 중 화면의 "경기 취소"를 주요 위치에서 내린다. 날짜가 바뀌면 진행 중 경기를 자동으로 닫는 처리를 만들지 않는다.
- 반대 의견: 대기가 쌓이면 기록되지 않은 경기가 늘어 제품의 약속과 반대가 된다. → 답: 대기가 없으면 그 경기는 취소되거나 추측으로 입력된다. 대기는 누락을 눈에 보이게 만들고, 명단이 확정돼 있어 나중 입력이 두 번의 선택으로 끝난다. 미입력 비율은 측정 항목에 넣는다.

### C. 명단 전달 — 링크·텍스트 채택, 이미지 후속

해법 비교:
1. 문구: 화면을 캡처하라고 안내 → 캡처는 스냅샷인지 표시되지 않고 포지션이 잘린다.
2. 통합: 참가자 조회 화면(P2-9)의 주소를 그대로 공유 링크로 쓰고, 같은 내용의 텍스트 복사를 붙인다. ← 선택
3. 새 기능: 결과 이미지 생성 → 글꼴·긴 이름·기기별 저장 실패 처리가 따로 필요하다.

| 질문 | 답 |
|---|---|
| 제거되는 입력·판단 | 운영자가 10명의 팀·포지션을 채팅에 손으로 옮겨 적는 일 |
| 새로 이해해야 하는 것 | 링크는 최신 상태를, 복사한 텍스트는 복사 시점의 내용을 보여준다 |
| 기존 기능과 중복 | 조회 화면과 같은 데이터, 같은 공개 정책을 쓴다. 따로 만들지 않는다 |
| 데이터·권한·통계 영향 | 조회 전용 링크. 실력 그룹은 포함하지 않는다. 통계 영향 없음 |
| 모바일 공간 | 진행 중 화면에 "명단 공유" 1개. 누르면 링크 복사·텍스트 복사 |
| 지원 부담 | 낮음. 클립보드 실패 시 선택 가능한 텍스트 상자를 보여준다 |
| 최소 검증 | 디스코드·카카오톡 내장 브라우저에서 링크 열기, 클립보드 거부 시 대체 경로, 진영 미확인 시 팀 A·B 표기 |
| 보류·삭제 조건 | 관찰에서 참가자가 링크를 열지 않고 운영자에게 되물으면 텍스트를 기본으로 올리고 링크를 보조로 내린다 |

- 공유 내용: 모임 이름, 경기 번호, 상태, 팀별 이름·포지션, 최신 상태 링크. 텍스트 끝에 "○시 ○분 기준" 표시.
- 합치거나 제거할 요소: 별도의 "공유용 화면"을 만들지 않는다.
- 반대 의견: 채팅방에서는 이미지가 링크보다 눈에 잘 띈다. → 답: 텍스트 명단은 채팅에 그대로 보이므로 열 필요가 없다. 이미지가 필요하다는 관찰이 나오면 후속에서 추가하며, 그때도 이미지 실패가 경기 저장을 취소하지 않는다는 조건을 유지한다.

### D. 기록 변화 이유 — 채택 (축소)

해법 비교:
1. 문구: 통계 화면에 "기록이 수정되면 수치가 바뀔 수 있어요" 안내 → 어떤 경기가 왜 바뀌었는지 답하지 못한다.
2. 통합: P2-7이 저장하는 정정·삭제·복구 이력을 경기 상세와 모임 "변경 내역" 목록 하나로 보여준다. ← 선택
3. 새 기능: 과거 통계 화면을 저장해 전후를 비교 → 기준 문서가 금지한다.

| 질문 | 답 |
|---|---|
| 제거되는 입력·판단 | "내 승률이 왜 바뀌었지"를 운영자에게 묻고 운영자가 기억으로 답하는 일 |
| 새로 이해해야 하는 것 | 수치가 달라 보이는 이유는 두 가지다: 필터를 바꿨거나, 원본 경기가 바뀌었거나 |
| 기존 기능과 중복 | 경기 상세의 정정 기능과 같은 이력을 읽는다 |
| 데이터·권한·통계 영향 | 읽기 전용. 조회자도 볼 수 있으나 수정 권한은 없다. 실력 그룹 변경 이력은 공개 정책을 따른다 |
| 모바일 공간 | 경기 상세 하단 접힌 영역, 기록 화면에 "변경 내역" 진입 1개 |
| 지원 부담 | 지원을 줄이는 쪽이다 |
| 최소 검증 | 정정·삭제·복구 각 1회 후 목록에 영향받은 경기·시각·항목·현재 결과·링크가 나오는지 확인 |
| 보류·삭제 조건 | 관찰에서 아무도 열지 않으면 목록 화면을 없애고 경기 상세의 이력만 남긴다 |

- 합치거나 제거할 요소: 별도의 "감사 로그" 화면과 통계 스냅샷 저장을 만들지 않는다.
- 반대 의견: 지인 모임에서 누가 무엇을 고쳤는지 드러나면 분위기를 해칠 수 있다. → 답: 운영자가 1명이므로 변경 주체는 표시하지 않고 항목과 시각만 보여준다.

## 결정 요청

"다음"이라고만 답하면 권장 기본값을 모두 채택한다.

| # | 결정 | 권장 기본값 | 한 줄 이유 |
|---|---|---|---|
| 1 | 후보 A | 채택. 기본 동작은 "같은 팀, 포지션 다시 무작위", 조정은 "포지션 유지"와 "팀 다시 짜기" | 포지션 무작위 규칙과 맞고, 팀은 버리기가 다시 만들기보다 싸다 |
| 2 | 후보 B | 채택(최소 형태). 승리 팀을 모르면 대기에 머물고, 진영만 모르면 미상으로 확정 | 끝났지만 결과 없는 경기는 어차피 생긴다 |
| 3 | 후보 C | 링크·텍스트 채택, 결과 이미지 후속 | 조회 링크는 이미 필요하고 이미지는 실패 경로가 많다 |
| 4 | 후보 D | 채택(경기별 이력 + 변경 내역 목록). 변경 주체는 표시하지 않음 | 이력은 어차피 저장하므로 표시 비용만 든다 |
| 5 | 다중 운영자 전제 | 유지하지 않음. 활성 운영자 1명 (P0에서 채택한 값 재확인) | 동시 편집 충돌 설계를 빼도 여러 기기 문제는 버전 검사로 처리된다 |
| 6 | 서포터 순환의 v1 포함 | 포함. 단 P2-5에서 가장 단순한 해법을 고른다 | 제품 한 문장이 "서포터 차례를 정하고"를 약속한다. 빼면 수기 대비 차이가 줄어든다 |
| 7 | 가설 1·5의 사전 확인 | P2와 병행해 사람이 수행 | 개발 없이 확인할 수 있고 결과가 나쁘면 설계 범위를 줄일 수 있다 |

결정 6의 반대 의견: 순환은 P2에서 가장 복잡한 요구사항이며 출시 필수 기준에 해당하지 않는다. → 답: 맞다. 그래서 필수가 아닌 초기 편의로 분류했고, P2-5에서 예약 엔티티 없는 해법을 먼저 검토한다. 해법이 단순해지지 않으면 P2 결정 요청에서 "v1은 차례 표시만, 추첨은 후속"으로 축소안을 함께 낸다.
