# 이 저장소의 작업 규칙

이 파일과 `.claude/agents/`, `.claude/settings.json`은 git에 올라가 있어 클론하면 그대로 적용된다.
`.claude/settings.json`이 정하는 것: 메인 기본 모델 opus, effort medium, 모델을 적지 않은 서브에이전트의 기본값 sonnet. 프로젝트 설정이 개인 설정(`~/.claude/settings.json`)보다 우선하고 실행할 때마다 다시 적용된다. 서브에이전트는 각 정의 파일의 `model:`이 기본값보다 우선한다.
모델 분담은 개인 전역 규칙(`~/.claude/CLAUDE.md`)과 같다. 전역 규칙이 없는 PC에서 클론해도 같게 돌도록 아래에 다시 적고, `fast-worker`·`fable-designer`도 전역 정의와 같은 내용으로 저장소에 둔다. 둘 중 하나를 고치면 다른 쪽도 맞춘다.
화면 디자인 규칙은 저장소 맨 위 `CLAUDE.md`에 따로 있다.

## 모델 분담

- 메인(Opus 5.5, effort medium)은 대화, 계획, 구현 대부분, 디버깅, 결과 검토를 직접 한다. 코드를 읽고 동작을 분석하는 일(예: 서버 요청이 어디서 몇 번 나가는지, Cloudflare 무료 한도 점검)도 서브에이전트로 넘기지 않는다.
- `fast-worker`(Sonnet)에게 위임: 테스트·빌드 실행과 결과 정리, 정해진 대로의 반복 수정, 같은 패턴 일괄 변경.
- `Explore`·`log-reader`(Haiku): 파일 찾기, 테스트·빌드 로그 읽기처럼 결과가 틀려도 바로 알아챌 수 있는 일.
- `fable-designer`(Fable)는 사용자가 요청할 때만 쓴다. 메인이 판단해서 먼저 부르지 않는다. 필요해 보이면 부를지 사용자에게 묻는다. 파일을 고치지 않고 설계 문서만 낸다.
- 한두 줄 수정, 파일 한두 개 읽기처럼 위임하는 게 더 오래 걸리는 일은 직접 한다.
- 스펙이 명확해도 D1 마이그레이션이나 성능 최적화는 Sonnet에게 넘기지 않는다.
- 토큰 단가는 Opus가 Sonnet의 2배, Fable이 Opus의 2배다. 점수가 조금 높다는 이유만으로 상위 모델을 쓰지 않는다.
- 모델과 effort는 Claude가 스스로 바꿀 수 없다. 추론 강도는 기본값을 쓰고, 검증이 중요한 버그 수정이나 복잡한 전적·MMR 계산 로직처럼 어려운 작업이면 시작 전에 high로 올리자고 제안한다.

### 실패했을 때
1. 자체 검증 수단을 먼저 만든다(테스트, 빌드, 로컬 실행 `npm run dev`, API 호출 스크립트 등). 대개 effort를 올리는 것보다 싸고 빠르다.
2. 그래도 막히면 effort를 한 단계 올리자고 제안한다. 서브에이전트에게 맡긴 일이 막히면 그 작업만 high로 다시 맡기고 사용자에게 알린다.
3. Opus high로도 두 번 이상 막힌 설계 판단이면 `fable-designer`를 부를지 사용자에게 묻는다. 모델이 모르는 지식 문제는 effort로 풀리지 않으니 2단계를 건너뛴다.

### 자동 검증이 되는 작업
- 이 저장소의 자동 확인 수단: `npm run typecheck`, `npm run lint`, `npm test`, `npm run build`, `npm run check:bundle`, `npm run audit:design`, `npm run e2e`.
- 이 검사들의 실행과 결과 정리는 `fast-worker`에게 맡길 수 있다. 화면 모양·문구·정책 판단처럼 자동 확인 수단이 없는 일은 메인이 직접 본다.

### 대화 관리
- 할 일 묶음(5~10개)이 끝날 때마다 결과를 요약하고 멈춘다. 다음 묶음은 `/clear` 후 새로 시작한다.
- 긴 작업을 이어갈 때는 `/compact`를 쓴다. 모델을 바꿀 때도 캐시가 모델별로 따로라서 먼저 `/compact`를 하자고 알린다.

### 웹 화면 수정 규칙 (최우선)
- 화면(HTML/CSS/JS)을 수정하면 항상 모바일 폭(360~430px)에서도 깨지지 않는지 확인한다(가로 넘침, 낱말 중간 줄바꿈, 하단 탭에 가리는 버튼, 44px 터치 영역).
  - 예외: 경기 카드 이름 칸(`.mc-name-text`, 480px 이하)은 글자 단위로 두 줄까지 꺾는다. 390px에서 칸이 54px인데 5글자 이름은 61px이 필요해 줄바꿈을 피할 수 없고, 말줄임은 "가상선수…"처럼 앞이 같은 이름을 가려서다(2026-11-16 실측 후 사용자 결정).
- 확인 방법과 결과를 작업 요약에 반드시 적는다.

## 위임할 때 지시문에 반드시 넣을 것
서브에이전트는 이전 대화를 모른다. 지시문에 아래를 모두 적는다.
1. 목표: 무엇을 왜 하는지
2. 배경: 지금까지 결정된 사항, 관련 파일 경로
3. 제약: 건드리면 안 되는 것, 지켜야 할 규칙(아래 주석·이름 기준 포함)
4. 완료 기준: 어떻게 되면 끝인지
5. 보고 형식: 짧게 요약해서 보고

서브에이전트가 보고한 파일 위치·내용은 그대로 믿지 말고, 중요한 변경은 메인이 직접 파일을 열어 확인한다.

## 작업 방식
- 작업 시작 전에 계획을 짧게 보여주고, 단계마다 예상 시간을 적는다.
- 되돌리기 어려운 작업(파일 삭제, git push, DB 변경, 배포, 패키지 대량 설치)은 실행 전에 사용자에게 묻는다.
- 모든 응답과 문서는 한국어로 한다.
- 주석은 "나중에 고칠 사람" 기준으로 알기 쉽게 쓴다: 파일 맨 위에 무엇을 계산·그리는지와 어느 화면이 쓰는지, 함수에는 바꿀 때 주의할 점, 상수에는 값의 뜻. 숫자는 이름 붙인 상수로 뽑는다. "무엇을"보다 "왜·주의"를 적고 코드로 명백한 내용은 되풀이하지 않는다. 위임 지시문에도 이 기준을 넣는다.
- AI가 쓴 티가 나지 않게 쓴다: 되풀이 주석·틀에 박힌 docstring·주석마다 날짜 꼬리표 금지, `handleData`·`result`·`helper` 같은 무난한 이름 대신 도메인 말(`upsetWins`, `meetingDays`), 절대 안 오는 입력의 검증이나 습관적 try/catch 금지, 작은 일에 추상화를 만들지 않는다. 새 유틸을 만들기 전에 `src/shared`·`src/web/ui.tsx`의 부품을 먼저 찾는다.
- 구현 기록은 `docs/구현현황/`의 마지막 날짜 파일 끝에 덧붙인다(입구 `docs/구현현황.md`의 구간 목록 참고). 작업 일지처럼 문장으로 쓴다. 항목마다 같은 표·소제목 틀을 반복하지 않고, 그날 고민한 것·막힌 것·그렇게 정한 이유를 적는다. 과장·홍보 투는 쓰지 않는다.
- 저작권·상표·라이선스가 걸린 결정(남의 디자인 참고, 게임 이미지·로고, 외부 데이터)은 권리자의 정책 원문을 직접 읽어 조건을 인용하고 하나씩 대조한 뒤에 정한다. 확인 전에는 "된다"고 말하지 않고, 원문에서 확인하지 못한 항목은 따로 밝힌다.
- 비밀값(`SESSION_SECRET`, `PASSWORD_PEPPER`)과 복구 코드는 저장소에 적지 않는다. 비밀번호 관리자 'naejeon 운영' 항목에 둔다(`배포-이어하기.txt`).
