● 지금은 요청하신 대로 제가 팀 리더 역할을 하고, 실제 실행은 fast-worker라는
  하위 에이전트에게 맡기는 방식으로 일하고 있습니다.

  1. 계획: 작업을 단계로 나누고 누가 무엇을 할지 먼저 보여드립니다.
  2. 위임: fast-worker는 이 대화를 보지 못하고 제가 써 준 지시문만 알기 때문에,
     경로·정확한 내용·예외 상황 대처·보고 항목까지 지시문에 다 적어 보냅니다.

  3. 대기: 워커는 백그라운드에서 돌고, 끝나면 저에게 보고가 옵니다. 그 전에는
     결과를 추측해서 말하지 않습니다.

     행동은 제가 정합니다.
  5. 보고: 실제로 일어난 일을 그대로 전합니다.

  2. 후보 B(결과 입력 대기): 최소 형태로 채택을 권장합니다. 승리 팀을 모르면
     대기 상태에 머물고, 진영만 모르면 "미상"으로 확정합니다. 끝났지만 결과가
     없는 경기는 B가 없어도 "진행 중"이라는 틀린 이름으로 생기기 때문입니다.

  4. 후보 D(기록 변화 이유): 경기별 이력과 변경 내역 목록 한 화면으로 채택을
     권장합니다. 변경 주체는 표시하지 않습니다. 이력은 어차피 저장하므로
     보여주는 비용만 듭니다.
  5. 다중 운영자 전제: 유지하지 않고 활성 운영자 1명으로 가는 것을 권장합니다.

     축소안을 함께 내겠습니다.
  7. 가설 사전 확인: "기존 방식이 바꿀 만큼 불편한가"와 "기록이 쌓이면 가치가

  핵심 설계 판단

  - 초안은 서버에 저장하지 않고 기기에만 둡니다. "이 팀으로 시작" 요청이 명단
    전체를 싣고 가고 서버가 처음부터 검증합니다. 초안 자동 저장과 충돌 규약이
    통째로 사라지는 대신, 휴대폰에서 짠 초안을 PC에서 이어 쓸 수 없습니다.
  - 진영은 "팀 A의 진영" 한 칸으로만 저장합니다. 팀과 진영의 일대일 대응이
    구조적으로 보장되고, 진영을 고쳐도 승패가 바뀌지 않습니다.
  - 삭제는 "전적 제외"(복구 가능) 하나로 합칩니다. 경기 단위 영구 삭제는 두지
    않습니다.
  - 서포터 순환은 ③ 중간 해법입니다. 서버는 시작 시점에 양팀 서포터를 이력과
    대조해 차례를 소비하기만 하고, 추첨 결과는 기기 초안에 보관합니다. ②(매번
    재계산)는 "재클릭해도 같은 결과"와 "영향받은 팀만 재확인" 요구를 충족하지
    못해 탈락했습니다.
  - 통계는 저장하지 않고 확정 경기에서 매번 계산합니다. 배치·칭호는 정정이나
    복구 때 자동으로 맞춰집니다.
  - 버전 검사는 세 범위입니다. 진행 상태, 경기 하나, 설정으로 나눠서 과거 경기
    정정이 진행 중인 입력을 방해하지 않습니다.

  결정 요청

  1. 순환 해법: ③ 중간을 권장합니다. 요구를 모두 충족하면서 서버에 예약 상태를
     만들지 않습니다.
  2. 동시 진행 제한: 열린 세션 1, 진행 중 1, 결과 입력 대기 10, 초안 기기당 1을
     권장합니다. 조회 링크의 "현재 경기"가 하나로 정해집니다.
  3. 공개 정책 기본값: 실력 그룹 비공개를 권장합니다. 합계와 구성으로 개인
     그룹을 역산할 수 있어 그것도 조회자에게 내보내지 않습니다.
  4. 초안 저장 위치: 기기에만 보관을 권장합니다. 잃을 수 있는 것은 편성
     1~2분이고 기록은 아닙니다.
  5. 삭제의 의미: 전적 제외로 통합을 권장합니다. 실수로 지운 경기를 운영자가
     스스로 되살릴 수 있습니다.
  6. 추천 가정값: 가중치 4·3·2·1, 미지정은 지정된 참가자의 중앙값, 비교 순서는

     → 시드 순을 권장합니다.
  7. 칭호 구간 기본값: 승률 65/55/45/35 경계의 5구간을 권장합니다. 칭호 이름은
     임의로 만들지 않고 비워 뒀습니다.
  8. 세션 경계: 운영자가 닫거나, 마지막 활동 12시간 뒤 새 경기를 시작할 때 묻는

● 마지막 단계인 P4(기술·배포·백업·검증·구현 순서)를
  docs/P4-기술·배포·검증·구현순서.md에 작성했습니다. 3,494어절로 상한 4,000
  이내입니다. 이로써 P0~P4 설계 문서 5개가 모두 docs/에 있습니다. 구현, 테스트,
  배포는 하지 않았습니다.

  기술 스택 추천

  Cloudflare Workers + D1 + React 단일 페이지 앱을 추천합니다. 가격과 한도는
  오늘 공식 문서에서 확인했습니다.

  ┌───────┬──────────────────────┬────────────────────────┬────────────────┐
  │       │ Cloudflare Workers + │        Supabase        │ 소형 서버 1대  │
  │       │          D1          │                        │                │
  ├───────┼──────────────────────┼────────────────────────┼────────────────┤
  │ 무료  │ 요청 10만/일, DB     │ DB 500MB, 1주 비활성   │ 가격 미확인,   │
  │ 한도  │ 쓰기 10만 행/일, 5GB │ 시 일시 정지, 백업     │ 월 고정비 발생 │
  │       │                      │ 없음                   │                │
  ├───────┼──────────────────────┼────────────────────────┼────────────────┤
  │ 유료  │ 월 5달러부터         │ 월 25달러부터          │ —              │
  ├───────┼──────────────────────┼────────────────────────┼────────────────┤
  │ 서버  │ 없음                 │ 없음                   │ 직접           │
  │ 관리  │                      │                        │                │
  └───────┴──────────────────────┴────────────────────────┴────────────────┘

  - Supabase 무료 요금제는 주 1회 쓰는 모임이 한 주 쉬면 정지될 수 있고, 유료는
    월 2만 원 상한을 넘습니다.
  - 미확인 위험이 하나 있습니다. D1은 여러 문장을 한 묶음으로 실행하면
    트랜잭션으로 처리하지만, 중간에 읽고 판단하는 대화형 트랜잭션은 문서에
    없습니다. "이 팀으로 시작"의 전부 저장 또는 전부 실패를 버전 비교 문장으로
    구현할 계획인데, 의도대로 동작하는지는 확인하지 않았습니다. 그래서 구현 첫
    작업을 이 확인(스파이크)으로 잡았습니다.
  - 버전 번호는 확인하지 않았습니다. 구현을 시작할 때 공식 릴리스 페이지에서
    확인해 고정합니다.

  그 밖의 판단

  - DB 전체 복구는 모든 모임을 함께 되돌립니다. 한 모임의 복구는 백업 파일로
    하도록 분리했습니다.
  - 검증 시나리오는 39개이며 모두 미수행입니다.
  - 구현 순서는 문서의 우선순위 1~7 앞에 0번(스파이크와 골격)을 뒀습니다.
  - 실패 가능성이 큰 이유 세 가지: 자동 수집을 하는 경쟁 서비스가 이미 있다는
    점, 10명이 기다리는 순간에 로그인이 끼어드는 점, 운영자 한 사람에게 의존하는
    점입니다.

  결정 요청

  1. 기술 스택: Cloudflare Workers + D1 + React를 권장합니다.
  2. 스파이크 선행: 구현 0번에서 D1 원자성부터 확인하는 것을 권장합니다.
     실패하면 모임별 Durable Object나 소형 서버로 바꿉니다.
  3. 인증 수단: 카카오 로그인(식별자만, 이메일 미수집)을 권장하고, 요건이 막히면
     Google 로그인으로 바꿉니다. 식별자만 쓸 때의 카카오 요건은 공식 가이드로
     확인하지 못했습니다.
  4. 첫 구현 범위: 0~4번(골격, 경기 분리, 결과 입력, 서포터 순환, 저장
     확인·정정)을 권장합니다. 출시 필수 기준이 4번에서 모두 채워집니다. 빨리
     관찰하는 것이 우선이면 순환(3번)을 빼고 0·1·2·4번만 먼저 만드는 안도
     있습니다.
  5. 레거시 이관 실행 시점: 4번 완료 뒤 로컬에서 대조하고, 통과하면 별도 승인을
     받아 전환하는 것을 권장합니다. 정정과 복구가 있어야 이관 오류를 고칠 수
     있습니다.
  6. 서비스 측 백업: Time Travel 7일에 주 1회 수동 전체 내보내기를 권장합니다.

  설계 단계에서 끝내 확인하지 못한 것

  - 기존 서비스의 그룹 가중치, 추천 비교 순서, 칭호 구간과 이름
  - 레거시 시트 구조 (이관 변환 스크립트는 스냅샷을 받은 뒤에 설계합니다)
  - 카카오 로그인 요건, Riot 제품 등록 절차, 개인정보 처리 요건

  구현 0번을 막는 것은 D1 확인 하나뿐이고, 위 항목들은 1~3번 구현을 막지
  않습니다.

  "다음"이라고 하시면 위 기본값을 모두 채택한 것으로 설계를 마칩니다. 기준
  문서가 이번 작업을 조사와 설계로 한정했으므로, 구현은 따로 지시하실 때
  시작하겠습니다.

      69  ### 읽는 법

● 맞습니다. 그 사실은 설계의 결론을 바꾸지 않고 오히려 전제를 강화해서,
  docs/P1-문제·범위·후보.md에 반영했습니다. 제가 직접 확인한 것은 아니라서
  "사용자 제공, 독립 확인 미수행"으로 표시했습니다.

  - 일반 전적 사이트에 내전이 안 보이는 이유: 저는 Riot 정책(당사자 동의 없이는
    공개 표시 불가) 때문이라고만 적었는데, 그 이전에 공개 기록에 데이터가 없기
    때문입니다. 비교표의 해당 칸을 고쳤습니다.
  - Scrim이 수집기를 쓰는 이유: Scrim 페이지에 "롤 클라이언트가 들고 있는 내
    경기 기록을 수집기로 읽어와"라고 적혀 있습니다. 공개 기록에 없으니 PC의
    클라이언트에서 직접 읽는 것으로 보입니다. 그렇다면 그 경기에 참가한 누군가가
    PC에서 수집기를 실행해야 하는데, 이 부분은 확인하지 않았습니다.
  - 수동 입력의 위치: 수동 입력은 자동 수집보다 못한 대체재가 아니라, 설치 없이
    내전 기록을 남기는 유일한 방법이 됩니다.
  - Riot API 연동: 범위 밖(v1)으로 뒀는데, 후속에서도 내전 결과를 자동으로
    가져오는 수단이 되기는 어렵습니다.

  P4에 적은 실패 가능성 1번("자동 수집을 하는 경쟁 서비스가 이미 있다")은 여전히
  유효합니다. 다만 그 자동 수집에도 PC와 설치라는 조건이 붙는다는 점이
  분명해졌습니다.

> riot api연동하는이유가뭐야

● 연동하지 않습니다. Riot API 연동은 기준 문서의 "범위 밖" 목록에 v1 제외로 적혀
  있고, 설계 전체가 API 없이 동작하도록 되어 있습니다.

  다른 내전 도구들이 연동하는 이유는 보통 다음과 같습니다.

  - 솔로 랭크 티어 가져오기: 팀 밸런스의 초기값으로 씁니다. 롤 내전 도우미가
    "소환사 티어와 전적을 바탕으로" 팀을 짠다고 소개하는 방식입니다.
  - Riot ID 확인: 입력한 닉네임이 실제 계정인지 확인하고 프로필을 보여줍니다.
  - 토너먼트 코드로 결과 자동 수신: Riot이 승인한 제품만 쓸 수 있는 기능으로,
    코드로 만든 방의 결과를 서버가 받아옵니다. 검색에서 본 비공개 커뮤니티 봇
    하나가 이 방식을 쓴다고 소개했는데, 제가 승인 요건을 확인하지는 않았습니다.

  이 서비스에는 셋 다 필요가 없습니다.

  - 티어: 실력 그룹은 운영자가 정하는 4단계 운영 기준이고 공식 등급이 아니라고
    확정되어 있습니다. 솔랭 티어를 가져올 이유가 없습니다.
  - Riot ID: 참가자는 모임 안의 이름으로만 식별합니다. 지인 모임이라 계정 확인이
    필요 없습니다.
  - 결과 자동 수신: 말씀하신 대로 개인 사설 게임은 기록에 남지 않습니다.
    토너먼트 코드는 승인 절차가 필요하고, 받더라도 "설치와 연동 없이 시작"이라는
    이 서비스의 장점과 반대 방향입니다.

  API를 쓰지 않으면 API 키 관리, 호출 한도, 정책 심사 부담도 없습니다. 다만
  API를 쓰지 않아도 Riot 개발자 문서는 플레이어 대상 제품의 등록을 요구하므로,
  그 절차는 출시 전에 확인해야 합니다.

  제가 P1에 "Riot API 연동은 후속에서도 내전 결과를 가져오는 수단이 되기
  어렵다"고 적은 것은 연동을 권하는 말이 아니라, 나중에라도 넣을 이유가 약하다는
  뜻이었습니다.

     - 진영 미상으로 넣기: 개인 승패와 배치 판수에는 들어가고 진영 통계에서만

    기록이 없어요"만 나왔습니다.

  - 메뉴에 "분석" 탭 추가: 오늘 · 기록 · 분석 · 모임 순서입니다. 누르면 그래프
    분석(개인별·라인별·진영별 승률, 플레이어 × 라인)으로 바로 갑니다.
  - 홈 화면에 "전적 검색" 추가: 플레이어 이름을 넣으면 전체 누적 승률과 승패가
    나오고, 누르면 그 사람의 개인 통계로 갑니다.
  - 기록 탭: 이름 검색 칸이 항상 보입니다. 오늘 경기가 없으면 "전체" 범위로
    열립니다.

  통과했습니다.

  직접 보시려면

  띄워 두셨던 npm run dev 서버는 제가 테스트 과정에서 멈추게 만들어서
  종료했습니다. 다시 npm run dev를 실행하셔야 하고, 그래야 이번 변경도
  반영됩니다.

  저장된 경기가 없으면 검색과 분석에 보여줄 내용이 없습니다. 내용이 채워진
  화면을 보시려면 서버를 띄운 뒤 다른 창에서 npm run seed를 실행하고, 개발용
  로그인에 계정 이름 seed를 넣으시면 가상 선수 30명과 120경기가 들어간 모임이
  열립니다.
